# Spawn boundary

Module: `crates/agents` (the tool allowlist lives in `claude_code/`; the shim and the scan read the list of vendor program names that the Adapters supply, one function per Adapter, so no vendor name is written in the shim, the scan or `agent.spawn`'s caller rule; `claude` is the only name until another Adapter exists, and a name another vendor's Adapter adds joins the shim and the scan with no change to them), `crates/rup` (the MCP tool). Terms: Meta-agent, Home, Worktree (`CONTEXT.md`). Principles served: P2, P4 and P6 (`PRINCIPLES.md`). Design: `docs/spawn-boundary.md`. The point: the Daemon must be the one that starts an Agent's children, so it can give each a Worktree (G2) and a Home. What can be enforced differs by layer, and each clause says which it is. **Guarantee** means no path exists inside Claude Code's own tool set; it does not cover a tool the user's own MCP servers add (A11 never passes `--strict-mcp-config`). **Best effort** means a bypass exists and is named. Tests run a fake `claude` (`ROUNDUP_CLAUDE_BIN`, A4) and read argv and files; F1 is the one result that needed the real `claude`. Contract change (the committee approves it with the first Builder PR): `RailNode.stray` and the event `agent.stray` (F5), and `agent.spawn`'s caller rule (F3), with no new method.

**F1 what the real Claude Code does.** Given `spikes/spawn-boundary/REPORT.md`, written on 2026-10-02 from `run.sh` on Claude Code 2.1.283, then it records, for each case in its table, the setup and what was observed, in the author's reading of one run (the raw outputs were not kept; `run.sh` repeats it), so F1 has no test and is outside the coverage audit: hooks in `--settings` fire and block; a `Bash(claude:*)` deny rule stops `claude` and not `bash -c 'claude'`; `--tools` without `Bash` leaves no shell; `--disallowedTools Agent` and a `--tools` allowlist leave no `Agent` tool; `settings.env.PATH` makes a shim run for a direct `claude`; `--append-system-prompt-file`, `SessionStart` context and an MCP server all reach a headless run, the server before the first prompt; an allowlist keeps MCP tools. F2 to F5 are written from it. A clause the report contradicts on a later `claude` version is rewritten in the same PR as the code, and `run.sh` is how to re-observe it. The interactive case is not observed.

**F2 a Meta-agent has no shell (guarantee).** Given a Group with a Meta-agent made by `rail.promote` (A7), then Claude Code starts with `--tools Read,Grep,Glob` once in its argv, so the Agent has no `Bash`, no `Edit` or `Write`, no `Agent` (subagent) tool, and no tool Claude Code adds that is not in the list; the tools of the `roundup` MCP server (A11) are still offered, because the vendor's allowlist keeps MCP tools (F1). After a Daemon restart a Meta-agent's Agent comes back `done` with no Terminal (A8, A12) and nothing starts it again, so no argv is built; a later scenario that starts a stopped Agent must build this same argv, and F2 claims nothing about it. An Agent that is not a Meta-agent gets none of F2 to F5: its argv, settings and `PATH` are A4's and E1's, it keeps every tool, and it may run `claude -p` or any vendor CLI on purpose. The test puts a fake `claude` that prints `9.9.9` in a directory on the Daemon's own `PATH`, spawns an ordinary Agent whose fake program runs `claude --version` and `sh -c 'claude --version'`, and expects `9.9.9` both times; the Agent's settings file (A4) has no `env.PATH` entry. The allowlist is a constant in `claude_code/`. The test reads the argv for a promoted Meta-agent and for a spawned Agent. It cannot show the tool is absent: F1's report does, for the vendor version it ran on, in headless mode (F7 repeats it for the interactive TUI). The guarantee stops at Claude Code's own tools: a tool that a user's own MCP server adds can run a command or start a program under the hood, and nothing in F2 sees it. F5 is the detector for that, and F5 detects, it prevents nothing.

**F3 a Meta-agent starts children through `agent_spawn`.** Given a Meta-agent `m` and its `rup mcp <id>` on stdio (M1), when an MCP client lists tools, then `agent_spawn` is offered, named after `agent.spawn` with the dot replaced by `_`, taking `agent.spawn`'s own params type, `SpawnParams` `{cwd, prompt?, parent?}`, whose schema is derived from `crates/contracts` as M1 says; there is no `name`, and `cwd` is required (the Meta-agent says where). M1's list of 13 tools is what every Agent that is not a Meta-agent is offered, and it is unchanged, so `agent_spawn` is not in it; a Meta-agent is offered M1's 13 and `agent_spawn`. A call is made as `m`, and `agent.spawn` called by an Actor of kind `agent` has these rules: the call is `FORBIDDEN` unless the caller is a Meta-agent; `parent` is always `m`'s own node, a `parent` in the params is ignored (as T8 ignores a `creator`), so the child's Home is `m`; `cwd`, as in A4, must lie inside the Project; when the Project's `worktrees` setting is on, the child is provisioned a Worktree as G2 says. The result is the registered Agent, the same `RailNode` `agent.spawn` returns, with `id`, `parent: m` and `worktree` (null when the setting is off). Nothing of the child is started by the Meta-agent's own process. The Meta-agent's Brief (E1) names `agent_spawn` and `message_send` (B12) as the ways to start and to talk to a child, and says it has no shell. For a user or an Extension, `agent.spawn` is unchanged. Tests: an rmcp client as `m` and as an Agent that is not a Meta-agent, comparing `rail.tree` and `git worktree list` before and after.

**F4 a shim for the vendor CLIs (best effort).** Given `rail.promote` (A7) and no other path (an ordinary Agent gets no shim), then the Meta-agent's per-Agent settings file also has `env.PATH` set to `<Project folder>/.roundup/agents/<id>.bin` followed by the `PATH` the Daemon had, and that directory holds one executable per program name the Adapters supply (today `claude`) that prints `roundup: start an agent with agent_spawn (a Meta-agent) or ask the user` on stderr and exits 1. A test runs `PATH=<dir>:$PATH claude --version` and `sh -c 'claude --version'` with that directory first and gets the message and exit 1 (the second is a local test of how a child inherits `PATH`; only the first was observed with the real `claude`, F1), and runs `/bin/echo` and a command named `git` unchanged. It does not stop an absolute path to the real binary, a renamed copy, or a program the Agent writes itself; that is stated here, not hidden. The Daemon's own start of an Agent uses the absolute path of `claude` (A4), so the shim never blocks roundup. It exists for what F2 does not cover: a tool a user's own MCP server adds, or an allowlist someone widens later; with F2 alone a Meta-agent has no shell to resolve a name.

**F5 a stray child is flagged (detection only).** Given a Meta-agent whose Terminal's process tree holds a process whose program name is one the Adapters supply (today `claude`) and that is not the Agent's own and not a Terminal the Daemon registered, then within `ROUNDUP_SCAN_MS` (default 2000, a test shortens it) its node in `rail.tree` has `stray: [{pid, command}]`, one `agent.stray {id, stray}` event is emitted, the Agent's Kind and Status are unchanged, and nothing interrupts the user (P3). When the process exits the list empties and `agent.stray` is emitted once more. A Terminal started with `rail.spawnTerminal` that runs a program named `claude` is not flagged, because the Daemon registered it. A renamed copy of the binary is not flagged: this is detection by name, a best effort that cannot see everything, and it prevents nothing. A process's program name is the basename of its `argv[0]` or of its executable path, and, when `argv[0]` is an interpreter (`sh`, `bash`, `node`, `python`), the basename of its first non-option argument; it is read with `ps -o pid=,ppid=,comm=,args=`, which macOS and Linux both have. Only a Meta-agent's tree is scanned. The test starts a fake `claude` that runs a child script named `claude` under `sh` and checks `rail.tree` and the event stream, on macOS and Linux. A second test has the fake `claude` start a fake MCP server (a child of the Agent's process, as Claude Code starts one) whose tool, when called, forks an unregistered program named `claude`; the scan flags it as `stray`, which is the case F2 does not stop. The Rail's badge for `stray` is a webview scenario, F6, reserved. Cost: `just perf`'s 10-idle-Agents metric starts no Meta-agent and so cannot see the scan; its cost is not measured by a gate. The Builder reports in the PR the CPU time of the scan's `ps` runs over 60 seconds with one Meta-agent.

**F7 the interactive Meta-agent (observed 2026-10-02).** Given a boxd VM (name `ru-spike-<x>`, auto-destroy, no window and no keystroke on the user's machine), the real Claude Code started in a pty under `tmux` with the argv and settings F2 and F4 build for a Meta-agent, then `spikes/spawn-boundary/REPORT.md` gains, for the interactive TUI and not headless: whether `echo hi` can be run (no `Bash` tool is offered), whether the `Agent` tool is absent, whether `claude --version` through the shim prints the message, and whether a project `.claude/settings.json` or a user `~/.claude/settings.json` that allows `Bash(*)` gives the Meta-agent a shell despite `--tools`. Each row is marked observed with the date and `claude` version, or `not run`. Observed, with the screens in `spikes/spawn-boundary/raw-interactive/` and `run-interactive.sh` to repeat it (the run began on 2.1.283 and `claude` updated itself to 2.1.287 after the first case): with `--tools Read,Grep,Glob` there was no shell and no `Agent` tool, also with a project and with a user settings file that allowed `Bash(*)`; with `--tools Read,Bash` and the shim first on `PATH`, a direct `claude --version` printed `use agent_spawn` and exited 1. Not observed: a `bash -c` child in the TUI, an absolute path, the sandbox. The user's own `!` command in the prompt runs a shell in their session, not one the Agent can start. A result that contradicts F2 on a later `claude` version rewrites F2 in the PR that implements it. F7 has no test and is outside the coverage audit as F1 is; a queue row re-runs it when the pinned `claude` version changes.
