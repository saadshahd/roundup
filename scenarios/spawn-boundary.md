# Spawn boundary

Module: `crates/agents` (the tool allowlist and the shim live in `claude_code/`, the scan and `agent.spawn`'s caller rule are vendor-neutral), `crates/rup` (the MCP tool). Terms: Meta-agent, Home, Worktree (`CONTEXT.md`). Principles served: P2, P4 and P6 (`PRINCIPLES.md`). Design: `docs/spawn-boundary.md`. The point: the Daemon must be the one that starts an Agent's children, so it can give each a Worktree (G2) and a Home. What can be enforced differs by layer, and each clause says which it is. **Guarantee** means no path exists inside Claude Code's own tool set; it does not cover a tool the user's own MCP servers add (A11 never passes `--strict-mcp-config`). **Best effort** means a bypass exists and is named. Tests run a fake `claude` (`ROUNDUP_CLAUDE_BIN`, A4) and read argv and files; F1 is the one result that needed the real `claude`. Contract change (the committee approves it with the first Builder PR): `RailNode.stray` and the event `agent.stray` (F5), and `agent.spawn`'s caller rule (F3), with no new method.

**F1 what the real Claude Code does.** Given `spikes/spawn-boundary/REPORT.md`, written on 2026-10-02 from `run.sh` on Claude Code 2.1.283, then it records, for each of ten cases, the setup and what was observed: hooks in `--settings` fire and block; a `Bash(claude:*)` deny rule stops `claude` and not `bash -c 'claude'`; `--tools` without `Bash` leaves no shell; `--disallowedTools Agent` and a `--tools` allowlist leave no `Agent` tool; `settings.env.PATH` makes a shim run for `claude` and for `bash -c 'claude'`; `--append-system-prompt-file`, `SessionStart` context and an MCP server all reach a headless run, the server before the first prompt; an allowlist keeps MCP tools. F2 to F5 are written from it. A clause the report contradicts on a later `claude` version is rewritten in the same PR as the code, and `run.sh` is how to re-observe it. The interactive case is not observed.

**F2 a Meta-agent has no shell (guarantee).** Given a Group with a Meta-agent made by `rail.promote` (A7), then Claude Code starts with `--tools Read,Grep,Glob` once in its argv, so the Agent has no `Bash`, no `Edit` or `Write`, no `Agent` (subagent) tool, and no tool Claude Code adds that is not in the list; the tools of the `roundup` MCP server (A11) are still offered, because the vendor's allowlist keeps MCP tools (F1). The same argv rule holds for a Meta-agent that is started again after a Daemon restart. An Agent that is not a Meta-agent gets none of F2 to F5: its argv, settings and `PATH` are A4's and E1's, it keeps every tool, and it may run `claude -p` or any vendor CLI on purpose. The test spawns one and runs `claude --version` through its settings' `PATH`, getting the real answer. The allowlist is one Daemon constant. The test reads the argv for a promoted Meta-agent and for a spawned Agent. It cannot show the tool is absent: F1's report does, for the vendor version it ran on.

**F3 a Meta-agent starts children through `agent_spawn`.** Given a Meta-agent `m` and its `rup mcp <id>` on stdio (M1), when an MCP client lists tools, then `agent_spawn` is offered, named after `agent.spawn` with the dot replaced by `_`, taking `{prompt, cwd?, name?}`. A call is made as `m`, and `agent.spawn` called by an Actor of kind `agent` has these rules: the call is `FORBIDDEN` unless the caller is a Meta-agent; `parent` is always `m`'s own node, a `parent` in the params is ignored (as T8 ignores a `creator`), so the child's Home is `m`; `cwd` defaults to the Project folder and, as in A4, must lie inside it; when the Project's `worktrees` setting is on, the child is provisioned a Worktree as G2 says. The result is the registered Agent, the same `RailNode` `agent.spawn` returns, with `id`, `name`, `parent: m` and `worktree` (null when the setting is off). Nothing of the child is started by the Meta-agent's own process. The Meta-agent's Brief (E1) names `agent_spawn` and `message_send` (B12) as the ways to start and to talk to a child, and says it has no shell. For a user or an Extension, `agent.spawn` is unchanged. Tests: an rmcp client as `m` and as an Agent that is not a Meta-agent, comparing `rail.tree` and `git worktree list` before and after.

**F4 a shim for the vendor CLIs (best effort).** Given `rail.promote` (A7) and no other path (an ordinary Agent gets no shim), then the Meta-agent's per-Agent settings file also has `env.PATH` set to `<Project folder>/.roundup/agents/<id>.bin` followed by the `PATH` the Daemon had, and that directory holds one executable per vendor CLI name (`claude`, `codex`, `gemini`) that prints `roundup: start an agent with agent_spawn (a Meta-agent) or ask the user` on stderr and exits 1. A test runs `PATH=<dir>:$PATH claude --version` and `sh -c 'claude --version'` with that directory first and gets the message and exit 1, and runs `/bin/echo` and a command named `git` unchanged. It does not stop an absolute path to the real binary, a renamed copy, or a program the Agent writes itself; that is stated here, not hidden. The Daemon's own start of an Agent uses the absolute path of `claude` (A4), so the shim never blocks roundup. It exists for what F2 does not cover: a tool a user's own MCP server adds, or an allowlist someone widens later; with F2 alone a Meta-agent has no shell to resolve a name.

**F5 a stray child is flagged (detection only).** Given a Meta-agent whose Terminal's process tree holds a process whose executable name is `claude`, `codex` or `gemini` and that is not the Agent's own and not a Terminal the Daemon registered, then within `ROUNDUP_SCAN_MS` (default 2000, a test shortens it) its node in `rail.tree` has `stray: [{pid, command}]`, one `agent.stray {id, stray}` event is emitted, the Agent's Kind and Status are unchanged, and nothing interrupts the user (P3). When the process exits the list empties and `agent.stray` is emitted once more. A Terminal started with `rail.spawnTerminal` that runs `codex` is not flagged, because the Daemon registered it. A renamed copy of the binary is not flagged: this is detection by name, a best effort that cannot see everything, and it prevents nothing. The scan reads the process table once per tick for all Agents, not once per Agent. The test starts a fake `claude` that runs a child script named `codex` and checks `rail.tree` and the event stream. The Rail's badge for `stray` is a webview scenario, F6, reserved. Cost: the Builder measures idle CPU and RSS with ten idle Agents under `just perf` and reports the numbers in the PR; `docs/perf.md`'s budget is the limit.
