# Rail uses the shared tree and sortable

Specification for #1607. Implementation owns `apps/desktop/src/rail/`, deletes `apps/desktop/src/keys/railStep.ts`, edits only the `.rail*` rules in `apps/desktop/src/styles.css`, and edits only the `copy.ts` entries the Rail uses. It does not edit `ui/`, other `keys/` files, other lanes, `tokens.css`, manifests or lockfiles (policy). A capability `ui/` lacks becomes a native prerequisite Issue against the UI epic, never a local copy (policy).

Direction: #1629, #1627, #1630 and #1869 (the registry #1608 specified) are implemented; #1984 delivered the shared TreeView and Sortable (U483 to U485 in `scenarios/ui-buttons.md`), which this lane consumes. The owner's closing comment on #1852 cancels semantic Tokens as a prerequisite: keep the current Token names and add no raw visual values (policy). The `u52x_` observers below are the implementation's acceptance, not tests this specification PR claims to hold.

**U520 The Rail is a tree.** Given a three-level Rail (Project → Workstream → Agent, with a sibling after the first Workstream), when Tab enters it, then focus is the first row, and Down, Up, Right, Left, Home, End and typed letters behave as U483's three-level walk does: Right expands a collapsed branch, then moves to its first child; Left collapses an expanded branch, then moves to its parent; Home and End reach the first and last visible row; typing jumps to a row by its name (`u520_three_level_keyboard_walk`, planned in `apps/desktop/src/rail/`, real Ark TreeView in headless Chromium). Selecting a row by keyboard shows its Terminal as a click does and calls no method of its own (U41, `scenarios/ui.md`). A leaf Agent with Pads expands them on Right and folds them on Left (U41, U58). Rows folded into U8's `✓ n done` line are not rows until the line is opened, so Right never lands on one (`u520_done_line_is_not_a_row`).

Given the open Rail, when its accessibility tree is read, then there is one `tree` with an accessible name, each row is a `treeitem` at its level with `aria-expanded` matching its fold, leaves carry none, and every button in a row has an accessible name that is not a native `title` (`u520_tree_semantics_and_names`). An axe check of the Rail reports no violation (`u520_axe_clean`).

Implementation composes `ui/TreeView` for navigation and ARIA and keeps `RailRow` as the caller-rendered row; it deletes `keys/railStep.ts` and the Rail's own arrow, Home, End and typeahead handling, adds no parallel interaction state machine, and keeps U31's guards (a key in the rename field never moves the row; Enter on the fold button does not select the row), now proven by `u31_arrow_down_in_the_rename_field_does_not_cancel_the_rename` and `u31_enter_on_the_collapse_button_does_not_select_the_row` in `apps/desktop/src/rail/u31_rail_keyboard.test.tsx` (policy, diff inspection). `U41`'s F2, `⌘1`, `⌘2` and `⌘J` stay on the registry (`apps/desktop/src/keys/u41_rail_keys.test.tsx`).

**U521 Rail controls use shared accessible behaviour.** Given the Rail with every row kind, when each icon-only button is hovered and keyboard-focused independently, then it has a nonempty accessible name and a linked visible shared Tooltip showing that name (`u521_icon_controls_show_their_names`). Every icon-only button is `ui/IconButton`, every tooltip `ui/Tooltip`, every menu `ui/Menu` and every confirmation `ui/Dialog` or `ui/AlertDialog` (policy, inspect source and rendered controls). A Rail row carries no shared Tooltip: a truncated name, a status, the need-you count, the folded-agents count and a Pad name are not tooltip content (U2228c).

Given focus in the Rail or an owned layer (the jump list, attention key, add-Agent picker), when an existing Rail shortcut is pressed, then the registry selects only that scope's action, an open Help suppresses the underlying actions, and disposal leaves no stale callback (`u521_shortcuts_follow_focus`, real registry). The Rail's own `keydown` listeners in `Rail.tsx`, `Jump.tsx` and `AttentionKey.tsx` move onto the registry; keys inside Ark components (menu arrows, dialog Escape, tree navigation) come from Ark (policy). Every App-authored string and accessible name in `rail/` comes from `copy.ts`, as user labels (`u521_copy_preserves_content`; names and returned errors stay verbatim).

**U522 Rail reordering uses the shared Sortable.** Given the Rail and a row dragged by pointer, when the drop commits, then `rail.move {id, parent, index}` is called once with the parent and index of U22, with U22's CONFLICT, outside-the-Rail cancel, Escape cancel, edge scroll, daemon-gone and no-drag-on-a-button behaviour kept (`u522_pointer_move_calls_rail_move`, `u522_cancel_calls_nothing`, `u522_conflict_restores_the_row`, `u522_edge_scroll_reaches_an_offscreen_row`). Given the keyboard lift of a row, when it is moved and dropped, then the same single call is made and focus stays on the row (`u522_keyboard_move`). Given a real file dragged over a row, then the U348 drop targets and U420 landing still work and no reorder session starts (`u522_file_drop_coexists`, the file-drop proofs of `apps/desktop/src/app/u348_file_drop.test.tsx`).

U22's drop line's depth (a sideways move changes the parent) needs reparenting that U484's flat order does not state. If Sortable cannot carry the depth, implementation files a native prerequisite against the UI epic and keeps `drag.ts` for that part only until it lands; it never grows a second engine (policy). `rail/drag.ts` and `THRESHOLD_PX` are deleted when the prerequisite holds; U22's consumer-owned 4 px threshold is superseded by the Sortable's activation (policy).

Delete `rail/styles.css` and `.rail*` rules in `styles.css` that only patched hand-written focus, open-state, press or drag behaviour (the `:has()` press and selection rules), keep document layout and focus visibility, and move the remaining `.rail*` rules into `rail/styles.css` (policy, `wc -l` before and after in the PR). Delete tests that pin one computed style or exercise deleted behaviour, and for each name the test that still proves its then-clause or the retired clause (rule 10). Tests are named after their scenario.

## Size and order

If the diff passes about 2,000 lines (rule 3), the tree (U520, U521) lands first and the build run files the drag move (U522) as a second Issue natively blocked by this one (policy). The implementation Issue is natively blocked by every unmerged prerequisite, never by a not-planned Issue.
