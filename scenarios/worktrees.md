# Worktrees

Module: `crates/agents` (`src/worktree.rs`, which runs the `git` command; `git` on `PATH` is the one requirement), with end-to-end tests in `crates/rup/tests`. Terms: Worktree, Base, Landing (`CONTEXT.md`). Principles served: P2 (`PRINCIPLES.md`), P4 (provisioning is vendor-neutral, in `crates/agents`, never in `claude_code/`) and P5. Design: `docs/worktrees.md`. Tests use a real `git` in a temporary repository, a fake `claude` (`ROUNDUP_CLAUDE_BIN`, A4), no network. Errors: no new `rpc::code` constant. Each code below is an existing constant (`INVALID_PARAMS` for `not_a_git_project` and `no_base`; `NOT_FOUND` for `no_worktree` and `worktree_missing`; `CONFLICT` for `worktree_unlanded`, `worktree_dirty`, `landing_conflict`, `check_failed`, `check_missing`, `base_moved` and `base_dirty`; `INTERNAL` for `worktree_failed`) whose message starts with the lowercase name, a colon and a space (`no_base: HEAD is detached`); a test asserts the constant and that prefix. Contract change (the committee approves it in its own PR, rule 4): the methods and fields named below are new, and the contract PR changes every caller of `RailNode`.

**G1 the `worktrees` setting.** Given a Project, when `project.setWorktrees {on, check}` arrives (`on` a boolean, `check` a command line or `null`), then the setting is stored and `project.get` returns it; a Project that never had it set returns `{on: false, check: null}`. It survives a Daemon restart. With `on: false`, `agent.spawn` behaves exactly as A4 says and the Agent's node has `worktree: null`. A `check` that is the empty string is `INVALID_PARAMS`. `on: true` with `check: null` is allowed, because isolation needs no check, but G4 then refuses to land.

**G2 spawn provisions a Worktree.** Given `worktrees` on and a Project that is a git repository on a branch with at least one commit, when `agent.spawn {cwd, prompt}` arrives (A4), or `rail.promote` starts a Meta-agent's Agent in the Project folder (A7), then before the Agent starts the Daemon makes the branch `roundup/agent-<id>` at the Project's current commit and a git worktree for it at `<Project folder>/.roundup/worktrees/agent-<id>`, adds `.roundup/` to the repository's `.git/info/exclude` if it is not there, and starts the Agent with that Worktree as its working directory (the same subpath of it when `cwd` was a subfolder of the Project). The node's `worktree` is `{path, branch, base}` where `base` is the branch that was checked out in the Project. It is stored with the node and `rail.tree` returns it. Two Agents spawned back to back, and two Meta-agents promoted back to back, have different working directories (P2's observer); a promote whose Worktree fails leaves the Group a plain Group with its children where they were, and, like a failed spawn, leaves no branch and no worktree directory. A failed call emits no event. A Terminal spawned with `rail.spawnTerminal` is not given a Worktree. When any step fails, then `agent.spawn` fails with its own error code and nothing is left: no node, no branch, no worktree directory, and `git worktree list` and `git branch` equal what they were before the call. The codes are `not_a_git_project` (the folder is not a git work tree, or has no commit), `no_base` (HEAD is detached) and `worktree_failed` (git failed; the message holds git's own text).

**G3 a Worktree's status.** Given an Agent with a Worktree, when `agent.worktreeState {id}` arrives, then it returns `{ahead, behind, dirty}`: `ahead` is the number of commits on the Agent's branch that the Base does not have, `behind` the number on the Base that the branch does not have, and `dirty` is true when the Worktree has any staged, unstaged or untracked change outside `.roundup/`. A fresh Worktree is `{0, 0, false}`. After one commit in it the result is `{1, 0, false}`, after one commit on the Base `{1, 1, false}`, and writing an untracked file makes `dirty` true with the counts unchanged. The call changes nothing: the branch, the Base and the files are the same after it. For an Agent or Terminal with `worktree: null` it fails with `no_worktree`; when the directory is gone from disk it fails with `worktree_missing` naming the path, and the node stays.

**G4 landing.** Given an Agent with a clean Worktree (`dirty` false), when `agent.land {id}` arrives, then the Daemon rebases the Agent's branch onto the Base's current commit, runs the Project's `check` command in the Worktree, and fast-forwards the Base to the branch; it returns `{base: <commit>}` and `agent.worktreeState` then returns `{0, 0, false}`. It never writes the Base any other way, and it never commits for the Agent: before the fast-forward it checks that the Project folder has the Base checked out, and when it has another branch checked out or the Base no longer exists the call fails with `base_moved` and changes nothing. The checks run in this order, so one code wins when several hold: `no_worktree`, `check_missing`, `worktree_dirty`, `base_moved`, the rebase (`landing_conflict`), the check (`check_failed`), then the fast-forward (`base_dirty`). Each failure leaves the repository as it was before the call, and names its code: `check_missing` (the Project's `check` is `null`; nothing ran, because Landing without a check would break P5's "check green, then fast-forward"; the user sets one with `project.setWorktrees`), `worktree_dirty` (the Worktree has changes; nothing ran), `landing_conflict` (the rebase hit a conflict; the Daemon aborts it, the branch is where it was, and the error's message lists the conflicted paths; it never picks a side), `check_failed` (the check exited non-zero; the message holds its last 20 lines of output; the Base is unchanged and the Daemon resets the branch to the commit it had before the call and restores the Worktree's files; a check that leaves the Worktree dirty is also `check_failed`, with the message `check left changes`), `base_moved` (above), and `base_dirty` (the Project's own checkout has changes and the fast-forward would touch them; nothing changed). An Agent with `worktree: null` fails with `no_worktree`. The tests make a conflict between the Base and the branch, a failing check (`false`), a passing check (`true`) and a dirty Project checkout, and compare `git rev-parse` of both branches and `git status` before and after each failure.

**G5 removal never loses work.** Given an Agent with a Worktree, when `rail.remove {id}` arrives (A16), then if the Worktree is clean and the branch has no commit the Base lacks (`ahead` is 0), the Agent is stopped and removed as A16 says, and its worktree directory and its branch are deleted, so `git worktree list` and `git branch` equal their state before the spawn (P5's observer). If the Worktree is dirty, or the branch is ahead of the Base, then `rail.remove` fails with `worktree_unlanded` before it stops anything: the node, the Agent's status, the directory, the branch and every file are unchanged, and the message says `dirty`, `ahead` or both with the counts. `agent.discard {id}` is the deliberate way to drop work: it stops the Agent, deletes the node, the directory and the branch whatever their state, and returns `null`, and for a Meta-agent it treats the children as A16 does; a Terminal or an Agent with `worktree: null` fails with `no_worktree`. A directory that is already gone from disk is not an error for either call: git's record of it is pruned, and the branch is judged as before: `rail.remove` still refuses with `worktree_unlanded` (`ahead` N) when the branch is ahead of the Base, and otherwise deletes the branch, then removes the node; `agent.discard` deletes both whatever their state. A Group or Meta-agent removed with `rail.remove` follows A16 for its children and leaves their Worktrees alone; only the removed node's own Worktree is considered.

**G6 the Daemon finds its Worktrees again.** Given Agents with Worktrees, when the Daemon is stopped and started again on the same Project, then `rail.tree` returns each node's `worktree` as before, `agent.worktreeState` answers for each from the directories on disk, and no Worktree, branch or file changes. A Daemon killed between making the branch and starting the Agent must leave nothing a restart cannot clear: the node is stored before `git` runs and is marked unfinished until the Worktree exists and the Agent's Terminal is about to start, and on start a node still unfinished is rolled back: its directory and branch are deleted (they hold no commit of the Agent's), and the node is removed when it was made by `agent.spawn`, or left as the plain Group it was when it was made by `rail.promote` (A7), with its children where they were, so `git worktree list` and `git branch` equal their state before the spawn. The test puts a `git` wrapper first on `PATH` that runs the real `git worktree add`, touches a marker file and then blocks (every other `git` command passes through to the real one); it waits for the marker, kills `rupd` with SIGKILL as D6 does, kills the blocked wrapper, starts `rupd` again with the real `PATH`, and compares both lists with their state before the spawn. A worktree that git lists but that no node names (made by the user or another tool) is never reported as an Agent's, never touched by G4 or G5, and never deleted. Each Agent's Worktree is found again by the `worktree_path` stored on its node, never by where the node sits in the Rail: the test starts the Daemon with the same nodes moved under other parents and gets the same results. A node whose directory the user deleted keeps its node and answers `worktree_missing` (G3).

**G7 a Rail move never touches a Worktree.** Given an Agent with a Worktree whose uncommitted edits, an untracked file and one commit are in place, and a running fake `claude` that has the Worktree as its working directory, when the Agent's node is moved with `rail.move` (A6) under another Group or Meta-agent, or to another index under the same parent, then only the node's `parent` and `order` change. The node's `worktree` (`path`, `branch`, `base`), the Agent's working directory, the git worktree list, the branch and the Base's commit are the same bytes after the move; `git diff`, `git diff --cached` and `git status --porcelain=v2` run in the Worktree print the same bytes before and after; the fake `claude` (which logs its pid and working directory at start and again after the move) is not restarted and sees the same working directory and the same files. `agent.worktreeState` (G3) returns the same result. A move that A6 refuses (into the node's own descendant, or under a plain Agent or Terminal) is `CONFLICT` as before and changes nothing, Worktree included. A Rail has one Project, because each Daemon serves one Project and ids are per Project, so a move to a node of another Project cannot be asked: a `parent` that names no node here is `NOT_FOUND` with nothing changed, and a Worktree belongs to one repository for the same reason. When the Group an Agent sits under is removed (A16) its Agents move to the removed node's parent as A16 says and every Worktree is left as G7's first sentences require; there is no operation that merges Groups, so none is specified. Every file path, relative or absolute, in the Agent's working directory means the same file after a move as before.
