# Permission Decisions

Module: `crates/agents` (Decisions), `crates/rup` (`rup permission`), `spikes/hooks-permission`. Ids: every `H` heading in the file.

A Claude Code permission prompt becomes a Decision the user answers from the App. Read `docs/permission-decisions.md`, ADR 0006 and the Decision entry in `GLOSSARY.md` first. Claude Code's hook reply is read from `spikes/hooks-permission/REPORT.md` (H1), never from memory. Tests run with a fake `claude` that calls the hook command in its `--settings` file the way Claude Code does (the payload on stdin, the reply read from stdout); no test needs the real one.

**H1 the reply is recorded from the real tool.** Recorded by architect-swarm against `claude` 2.1.287 on 2026-10-02 and committed as `spikes/hooks-permission/REPORT.md` with this PR (the raw run files held local paths and are not kept). It states, each as a line `finding <n>: <text>`: the payload fields; that an allow or deny written as `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` (deny adds `message`) runs or stops the tool and that a deny message reaches the model; that `interrupt` aborts the whole run in print mode; that `{}`, empty output, exit 1, invalid JSON, `behavior:"ask"` and a refused connection all fall through to Claude Code's own dialog without an error to the user; that the dialog is drawn while the hook still runs; that answering the dialog first leaves the hook running and its late reply ignored, while Esc on the dialog sends the hook SIGTERM and fires no hook event; that timeouts of 86400 and 999999999 are accepted; and that `--permission-prompt-tool` is called in print mode only and ignored by the interactive UI. H1b (findings 8 to 11, on a boxd VM with 2.1.283) adds: Claude Code asks for permissions one at a time even when two tools come in one message; Esc sends the hook SIGTERM and a SIGKILL about 1.5 s later; a hook whose `timeout` expires gets SIGTERM, the dialog stays open and nothing is shown to the user; the `Notification` arrives about 6 s after the hook starts and so cannot mark the dialog opening. H1c (VM, 2.1.283) adds: a hook's allow or deny that arrives while the dialog is drawn closes the dialog by itself within about 25 ms and runs or skips the tool, with the deny message reaching the model (the exact allow and deny strings are in its finding lines); `PermissionRequest` also fires for `AskUserQuestion` with `tool_input.questions`, a hook that prints nothing shows its choice UI, and a hook's allow neither answers nor closes it. H1d (VM, 2.1.283, findings 19 to 23) adds: answering "No" sends the hook SIGTERM about 60 ms later and fires no hook event, exactly like Esc, so the two cannot be told apart; "Yes", "Yes, and always allow" and Tab-amend with text leave the hook running unsignalled and the tool runs at once (a `PostToolUse` follows); after a No the next prompt submits normally. Not observed: whether "always allow" persists, two dialogs open at once, what `AskUserQuestion` returns after an answer, and macOS (the runs were on Linux). Tests of H2 to H10 take their strings from the report and put them in test fixtures.

**H1b the remaining unobserved items are recorded.** Given the installed `claude` on macOS and a throwaway directory with a temporary `CLAUDE_CONFIG_DIR`, when the spike script runs the Esc, answer-first, No and timeout cases again on macOS, and one case each for whether "always allow" persists, what `AskUserQuestion` returns after an answer, and whether Esc on its choice UI changes the title, then `REPORT.md` gains a `finding <n>:` line for each, citing the run and naming the `claude --version`. It needs a login and a network, so it is a spike and not part of `just check`. No scenario waits on it: a macOS difference becomes a fix.

**H2 a permission request opens one Decision.** Given an Agent whose per-Agent settings run `rup permission <agent-id>` for `PermissionRequest` (H9), when the fake `claude` runs that command with the payload on stdin and it stays open, then the Daemon opens exactly one Decision for the Agent: `decision.list` returns `{id, agent, tool, args, opened_at, answerable}`, where `tool` is the payload's tool name, `args` is its tool input as text cut at 2000 characters with a final `…` when longer, and `answerable` is true; one `decision.opened` event carries the same Decision. The Daemon also hands the payload to the adapter as the Signal A1 and A2 already read, so the Agent's Kind is `needs-you` with the label A1 gives, and exactly one Decision is open for it. For the tool `AskUserQuestion` (H1c: its choice UI is the Terminal's, and no hook reply answers it) the Decision is opened with `answerable` false, `tool` `AskUserQuestion` and `args` the questions as text; `agent.permission` returns at once with an empty `output`, so `rup permission` prints nothing on stdout, writes one line `answer in the Terminal` to stderr and exits 0, as H1c observed for a hook that prints nothing; the Kind is `needs-you` with the label A1 gives (the question) and H7 clears the Decision. A second request from the same Agent while a Decision is open replaces the Decision (a new `id`, `decision.opened`, and the old Decision gets `decision.cleared` with outcome `replaced`; the Kind stays `needs-you`), and the first `rup permission` exits 1 with `superseded` on stderr and nothing on stdout, so Claude Code falls back to its own dialog. The tests use `decision.list`, the events and the exit code. Contract change (the committee approves it): `agent.permission {id, payload}` (called by `rup permission`; it returns when the Decision is answered or cleared, with `{output}` for stdout, or an error), `decision.list` (no params, returns the open Decisions), the events `decision.opened` and `decision.cleared`, and the `Decision` type; see H3 for `decision.answer`.

**H3 the user's answer goes through the hook.** Given an open Decision, when the user calls `decision.answer {id, answer, proof}` with `allow` or `deny` (`proof` as H4 gives), then `rup permission` prints on stdout exactly the reply H1 records for that answer, nothing else, and exits 0; the Decision is gone from `decision.list`; `decision.cleared` carries outcome `allow` or `deny`; and the dialog closes by itself (H1c), and the adapter folds the Observation `Answered` (H9), so the Agent's Kind is `working` at once (it continues: an allow runs the tool, a deny lets Claude Code go on with the message). An unknown or already cleared `id` is `NOT_FOUND`; an `answer` that is neither word is `INVALID_PARAMS`; a Decision that is not `answerable` (H8) is `INVALID_PARAMS`. The reply text is built in `crates/agents/src/claude_code/` and `rup` prints it unchanged, so nothing outside that module names a vendor string. Contract change: `decision.answer {id, answer, proof}` returns `null`.

**H4 nothing answers a Decision but the user.** The Daemon accepts `decision.answer` only from a caller that shows a `proof`: a random secret the App creates when it starts, hands to the Daemon on its stdin, and keeps in the webview's memory. The Daemon removes it from every environment it builds for an Agent, a Terminal and an MCP server, so a process inside an Agent's Terminal, which can connect to `RUPD_SOCKET` and call `daemon.identify` as `user`, cannot know it. Given an open Decision, then each of these leaves it open and its `rup permission` still waiting: `decision.answer` with a missing or wrong `proof` (error `FORBIDDEN`), including one sent on a connection that never called `daemon.identify` and one sent by a fake `claude` child process from inside the Agent's Terminal using the environment it inherited; `decision.answer` by an Actor of kind `agent` or `ext`; a Signal, a `terminal.write` or an MCP tool call from any Agent, whatever its text says; and an hour of an injected clock passing. A test reads the environment the fake `claude` and its Terminal receive and finds no `proof`. A Daemon started without an App (no proof on stdin) answers every `decision.answer` with `FORBIDDEN`. The `rup mcp` server lists no tool that answers or lists Decisions. The Daemon never calls `decision.answer` itself and has no setting that does (the test greps `crates/` for a second caller). Contract change: the `proof` parameter and the `rupd` stdin handshake. App seam change (`scenarios/app.md`, both sides in one PR, approved by an architect other than the author): the Tauri command `daemon_proof` with no arguments returns the `proof` string to the webview, which keeps it in memory; it is the only way the webview learns it.

**H5 an open Decision survives a webview reload.** Given an open Decision and a client that disconnects (a reloaded webview) and a new client that connects and calls `decision.list`, then it returns the same Decision, with the same `id` and `opened_at`, and `decision.answer` from the new client, which gets the `proof` back from the App, prints the reply on the still-waiting `rup permission`. The Daemon keeps Decisions in memory only. Quitting the App ends the Daemon and every Agent with it (D1, S3), and with the Agent the hook that waits for the answer, so no Decision can outlive the App and none is written to disk; a Daemon started by S5 holds no Decision. The test replaces the client, not the Daemon, and a second test starts a new Daemon and finds `decision.list` empty.

**H6 an Agent that ends clears its Decisions.** Given an open Decision, when its Agent's Terminal exits or `agent.stop` is called (A3, A7), then within the bound the test names the Decision is cleared with outcome `agent-gone`, `decision.cleared` is emitted once, `decision.list` no longer has it, the Kind is the one A3 or A7 gives, and the waiting `rup permission` exits 1 with `the Agent ended` on stderr and nothing on stdout.

**H7 an answer given in the Terminal clears the Decision.** Given an open Decision, then each of these clears it with outcome `terminal`, emits `decision.cleared` once, and makes a later `decision.answer` for it `NOT_FOUND`: (a) the user answers the dialog with "Yes", "Yes, and always allow" or Tab-amend with text, the hook is not signalled and keeps running (H1d), and the tool runs, so a `PostToolUse` (or `PostToolUseFailure`, `Stop`, `UserPromptSubmit`) Signal follows and clears the Decision; the Daemon then closes the hook's connection and drops a late reply; the Kind is the one A1 gives for that Signal, `working` for the first, second and fourth; (b) the user answers "No" or presses Esc, the hook gets SIGTERM and its connection closes with no later Signal (H1, H1d: no hook event fires, and the two cannot be told apart): the adapter folds `Dismissed` (H9) and the Kind is `idle`, which corrects A2's "Esc on a dialog does not clear `needs-you`" for an Agent with an open Decision, and a `needs-you` Decision is never left behind a refused dialog; (c) the hook's `timeout` expires: Claude Code sends the hook SIGTERM at the timeout, the dialog stays open and shows nothing about it (H1b finding 10), so the connection closing at or after the `timeout` the settings name (H9) is not an Esc or a No: the Decision stays open with `answerable` false, `decision.opened` is not repeated, one line goes to stderr, and the Kind stays `needs-you`; the test uses an injected clock and a settings `timeout` of 4 s. Only a close that the hook's side makes counts as (b): a connection the Daemon itself ends (the empty reply for `AskUserQuestion` in H2, a reply to `decision.answer`, a superseded request) never clears a Decision. A Decision with no live hook (`answerable` false: `AskUserQuestion`, after (c), or an unreadable payload in H8) has nothing to SIGTERM, so a No or Esc in the Terminal leaves it open and the Kind `needs-you`, which matches A2's own gap for Esc on a dialog; it is cleared only by a Signal as in (a) (a `UserPromptSubmit` always clears it) or by H6, and meanwhile the Terminal still shows the dialog's own state. Whether the title star marks an Esc on the `AskUserQuestion` choice UI is not observed and goes to H1b. Every other Decision is cleared by `decision.answer`, (a) or (b), and no Agent is `needs-you` without an open Decision. The tests close the connection and feed the Signals from the fake `claude`.

**H8 the hook fails loud and never allows.** Given `rup permission <agent-id>`, when `RUPD_SOCKET` is unset or no Daemon listens, the payload on stdin is not JSON, or the Daemon answers `NOT_FOUND` for the id, then it prints one line on stderr naming the cause, prints nothing on stdout, and exits 1, whichever it was; Claude Code then shows its own dialog, which H1 records it does without telling the user why. When the Daemon is reachable but cannot build the reply (a payload it cannot read), it opens the Decision with `answerable` false and `tool` and `args` as far as they could be read, so the Agent is `needs-you` with a Decision that says to answer in the Terminal, and H7 clears it. When no Daemon answers at all, nothing can show it: the failure is the line on stderr that Claude Code prints, and the test asserts it. A Daemon that stops answering is not waited on past the hook's own `timeout`; the command exits 1 with `rupd did not answer` when the connection closes. It never exits 2 and never prints a decision it did not receive from the Daemon. The tests run the built `rup` against each case.

**H9 the Agent's settings route the request.** Given `agent.spawn` (A4), when the Daemon writes the per-Agent settings, then `PermissionRequest` runs `<rup> permission <agent-id>` with a `timeout` of 86400 seconds (H1 shows it is accepted; at expiry H7(c) holds), and every other event in `STATE_EVENTS` (`crates/agents/src/claude_code/launch.rs`) runs `rup signal <agent-id>` with the 5-second timeout. Amendments in the same PR: A4's "with a 5-second timeout" becomes "with a 5-second timeout, except `PermissionRequest`, whose hook has the timeout above", and A4's "one command hook runs `rup signal <agent-id>`" becomes "one command hook per event in `STATE_EVENTS`: `rup signal <agent-id>` for every event except `PermissionRequest`, which runs `rup permission <agent-id>`"; ADR 0006's input design and its "one command hook" sentence say the same; `launch.rs` loses `PermissionRequest` from the `rup signal` list. A1 gains two Observations, `Answered` (the user's `decision.answer` reached the hook: Kind `working`) and `Dismissed` (the hook's own side closed its connection with no later Signal, H7(b): Kind `idle`); both are produced by the Daemon's Decision store and folded by the same pure `observe` function, so the Kind still comes from Observations as `GLOSSARY.md` says. A2's sentence "Esc on a dialog fires no hook and no title in the fixtures, so it does not clear `needs-you`" is amended in this PR: for an Agent with a live `rup permission` hook, Esc or No gives `Dismissed` and so `idle`; for an Agent with no live hook (H7) it still does not clear `needs-you`. D2 is unchanged except that its fake `claude` calls `rup permission` for the `PermissionRequest` payload and the test calls `decision.answer` as the user before `PostToolUse`; the A1 and A2 replays of `spikes/hooks-state/` still pass because they feed Signals to `observe` directly. A `PermissionRequest` payload sent through `rup signal` or `agent.signal` is ignored: it would give `needs-you` with no Decision. `agent.permission` is the only producer of that Signal; A1 and A2 test the pure function `observe`, which still takes it, so their replays are unchanged.

**H10 permission Decisions never climb the escalation chain.** Given an Agent with a parent Agent in `rail.tree`, when it raises a permission request, then the Decision is open at once and visible to every subscribed client (`decision.opened`, `decision.list`), and no byte reaches the parent's Terminal and no Signal, Message or call reaches the parent: the test counts the parent's `terminal.write` calls and the events addressed to it, and both are unchanged. The Decision store has no Route, no Held state and no hop, and `decision.answer` needs the `proof` of H4, so no parent Agent can answer it however it is addressed. This differs from `ask_user` and Message questions, which follow the escalation chain of the mailbox series (child, Meta-agent, root, user's Inbox, with a bound per hop); once that series is on main its Route tests assert the same for a permission request.
