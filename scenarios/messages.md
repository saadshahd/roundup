# Messages between Actors (B1 to B18)

Messages let the user, Agents and Extensions send each other typed text. Design, contract and module split: `docs/messages.md`. Terms are in `CONTEXT.md`. A Message's status is one of `pending`, `held`, `delivered` and `dropped`; a `held` Message also names why (`ask-first` or `takeover`). Tests use a fake `claude`, the fake Terminal of `crates/terminal` and a fake clock; none needs a display or a network.

**B1 send.** Given an open Project with Agent `a`, when an Actor calls `message.send {to: "a", kind, body, replyTo?}`, then the result is a Message with the next id (1, then 2 and on, per Project), `from` the calling Actor (never a parameter, so nobody can forge it), `to` the Agent `a`, `kind`, `body`, `replyTo` or `null`, a `status` and `at`. The call emits `message.sent` and logs a `wrote` Touch (B11). `kind` is `note` or `question`; both are delivered alike, and B2's text names the kind, so the receiver can see it was asked; the Card of `CONTEXT.md` (`PRINCIPLES.md` P3) is a later series, and any other `kind` is `INVALID_PARAMS`. A `to` that names no Actor is `NOT_FOUND`. A `to` that is a Terminal, a Group or the sender itself is `INVALID_PARAMS`. An empty body, one larger than 8192 bytes, or a `replyTo` that names no Message is `INVALID_PARAMS`. A receiver whose Kind is `done` or `error` is `CONFLICT` (B9). A receiver with 32 Messages in `pending` or `held` is `CONFLICT` naming the bound. A rejected call changes nothing: no id is used, no event is sent and no Touch is logged.

**B2 auto delivery.** Given a Route from the sender to Agent `a` of `auto` (B5) and no Takeover of `a` (B6), when a Message is sent while `a` has Kind `idle`, then the Message is typed into `a`'s Terminal as one prompt, `[from <sender's name>, <kind>] <body>`, submitted as a spawn prompt is, its status becomes `delivered`, and `message.delivered` is emitted, in that order. When `a` has any other Kind, the status is `pending`, nothing is typed, and the Message is delivered the next time `a`'s Kind becomes `idle`. Exactly one Message is typed per `idle`: a second pending Message waits for the next one. `<sender's name>` is the Rail name for an Agent, `you` for the user and the Extension's id for an Extension.

**B3 ask-first.** Given a Route of `ask-first`, when a Message is sent, then its status is `held` with the reason `ask-first`, nothing is typed, `message.held` is emitted, and it stays so until the user acts. `message.deliver {id}` makes it `pending`, so B2 applies from there; `message.drop {id}` makes it `dropped` and emits `message.dropped`. Only the user may call either; any other Actor gets `FORBIDDEN`. Calling either on a Message that is not `held` is `CONFLICT`. A Held Message is never delivered or dropped by anything but the user's call.

**B4 drop.** Given a Route of `drop`, when a Message is sent, then the call succeeds and returns the Message with the status `dropped`; nothing is typed, and `message.dropped` is emitted. The sender is not told it was dropped by an error.

**B5 Routes.** Given no Route for a sender and receiver, then the delivery is `auto`. `route.set {from, to, delivery}` stores a Route for that pair, `delivery` being `auto`, `ask-first` or `drop`, and emits `route.changed`; `route.list` returns every stored Route. Only the user may call `route.set`; any other Actor gets `FORBIDDEN`, so a user's choice is never overridden by an Agent. A Route whose `to` is the user, or whose `from` equals its `to`, is `INVALID_PARAMS`. A change applies to Messages sent after it: a Message already `held` stays `held`, and one already `pending` stays `pending`.

**B6 Takeover.** Given the user calls `takeover.begin {agent}` for Agent `a`, then until `takeover.end {agent}` a Message to `a` from any Actor but the user is not typed: with an `auto` Route it is `held` with the reason `takeover`, and with an `ask-first` Route it is `held` with the reason `ask-first`; with a `drop` Route it is `dropped`, as B4 says. A Message the user sends to `a` is delivered as B2 says. When the Takeover ends, every Message `held` for the reason `takeover` becomes `pending` in id order and B2 applies; those held for `ask-first` stay `held`. `message.deliver` on a Message held for the reason `takeover` makes it `pending` at once and B2 applies though the Takeover goes on, because the user's call wins. Only the user may call `takeover.begin` and `takeover.end`, otherwise `FORBIDDEN`; a second `begin`, or an `end` with no `begin`, changes nothing and is not an error; an id that names no Agent is `NOT_FOUND`, and an Agent whose Kind is `done` or `error` is `CONFLICT`. A Takeover ends by itself when `a` exits, and a Daemon that starts again has none; in every case of an end, the Messages held for `takeover` become `pending` first, and only then do B8 and B9 apply to them. Each change emits `takeover.changed {agent, on}`.

**B7 order.** Given several Messages to one Agent, then they are typed in the order in which they became deliverable, ties broken by id: a `held` Message that is released (B3, B6) takes its place at the moment of release, behind the `pending` Messages already waiting. A `held` Message never blocks a later Message to the same Agent that is not held.

**B8 restart.** Given a Project whose Daemon was killed without warning and is started again (D6), then Routes, every Message and its status survive, and the next Message id continues the sequence. No Message is ever typed twice: the Daemon records a Message `delivered` just before it types it and, when the Terminal refuses the bytes, records it `dropped` with the reason `write failed`, so a Daemon killed in between leaves it `delivered` (at most once). A Message to an Agent whose Terminal did not survive (A12), in the status `pending`, becomes `dropped` with the reason `receiver gone`; one in the status `held` for the reason `ask-first` stays `held` and the user may still drop it; one held for `takeover` first becomes `pending`, because no Takeover survives a restart (B6), and is then `pending`, delivered by B2 if its Agent is there and dropped with `receiver gone` if not. Messages to the user keep their status. The reasons are listed by `message.get`.

**B9 receiver gone.** Given Agent `a` whose Kind becomes `done` or `error`, then every Message to `a` in the status `pending` becomes `dropped` with the reason `receiver gone`, one `message.dropped` each, in id order; Messages held for `takeover` are first `pending`, as B6 says of the Takeover's end, and so are dropped with the rest; Messages held for `ask-first` stay `held`; and a later `message.send` to `a` is `CONFLICT`. `message.deliver` on a `held` Message to such an Agent is `CONFLICT` and leaves it `held`.

**B10 to the user.** Given a Message whose `to` is the user, then it is `delivered` at once, whatever Routes exist, nothing is typed anywhere, and `message.delivered` is emitted. Such a Message sends no `agent.status` event and changes no Agent's Kind (`PRINCIPLES.md` P3), and `message.list {to: "user"}` lists it. What the webview shows of it is the Inbox's scenario, not this series.

**B11 Touch.** Given a Message with id `n`, then `message.send` logs a `wrote` Touch on `message:<n>` by the sender, `message.deliver` and `message.drop` log one by the user, `message.get {id}` logs a `read` Touch by its caller, and `message.list {to?, status?}` logs none; for an Agent it returns only the Messages that Agent sent or received. `provenance.history {item: "message:<n>"}` returns them in order, and `provenance.touched` lists them under each Actor. Reading is by Actor: an Agent may `message.get` a Message it sent or received, and any other Message is `FORBIDDEN`; the user may read any. `CONTEXT.md` now says a Touch is of a Todo, a Pad or a Message.

**B12 an Agent sends and reads.** Given `rup mcp <agent-id>` on stdio (M1), when an MCP client lists tools, then `message_send`, `message_get` and `message_list` are offered besides M1's, named after their methods with the dot replaced by `_`, with input schemas derived from the params types in `crates/contracts`. A call is made as that Agent, so `from` is its id and B11's rule on reading applies; an Agent cannot name another sender. `message_deliver`, `message_drop`, `route_set` and the `takeover` methods are not offered: they are the user's. Each tool call and its result are exactly the Daemon's result or error for the method, as M1 says.

## Escalation: a question bubbles up

A `question` sent to a Meta-agent that cannot answer passes up the Rail, one Meta-agent at a time, and lands in the user's Inbox at the end. Permission requests never take this path (B18). The chain of an Agent is the Meta-agents among its ancestors, nearest first (Groups hold no Agent and are skipped), then the user. Tests use the fake clock and Rail trees with nested Groups and two or three Meta-agents.

**B13 hops.** Given Agent `c` under Meta-agent `m1`, which sits in a Group under Meta-agent `m2` (the root), when `c` sends a `question` to `m1`, then the Message is the first hop. When `m1` has not answered within the bound (B14), the Daemon makes a second Message: `from` `c`, `to` `m2`, kind `question`, the same body, `replyTo` null, listing the first as `passedFrom` in `message.get`, and the first becomes `dropped` with the reason `passed` if it is still `pending` or `held`. When `m2` has not answered within the bound, a third goes to the user, as B15 says. Each hop is an ordinary Message, so B2, B5 and B6 apply to it. The chain is read once, when `c` sends; a Rail move afterwards does not change it. A `question` to an Agent that is no Meta-agent, or to the user, has one hop and never passes. A hop's Meta-agent may also pass it at once with `message.pass {id}`, which only the Agent that holds the hop may call (`FORBIDDEN` otherwise); the next hop is made as above and the call changes nothing else.

**B14 the per-hop bound.** Given a hop, then its bound is 60 000 ms of the Daemon's clock, counted from the moment the hop's Message is made. The test supplies the fake clock: 59 999 ms after, the hop has not passed; at 60 000 ms it has. No bound runs while the hop is `held` for `ask-first`, because the user decides that hop (B3); it starts when the user delivers it. A hop `held` for `takeover` keeps counting, so a Meta-agent under a Takeover passes the question on. After a restart (B8) every pending bound is read from the Messages' stored times: a hop whose bound has run out passes when the Daemon starts, once.

**B15 landing.** Given a question that has passed every Meta-agent of the chain, or whose chain had none, then the Daemon makes a Message to the user: `from` `c`, kind `question`, `replyTo` null, status `held` with the reason `escalated`, and no `message.delivered`. It never changes `c`'s Kind and rings nothing (B10, `PRINCIPLES.md` P3); `message.list {to: "user", status: "held"}` lists it. Only the user answers it: `message.send` from the user with `replyTo` that Message is delivered to `c` as B2 says, and the held Message becomes `delivered`; `message.drop` ends it as B3 says. `CONTEXT.md` calls this a Held Message, which now also means one waiting on the user's answer to an escalated question.

**B16 who is skipped, no loops.** Given a hop whose Agent is `done` or `error`, no longer in the Rail, or whose Route from `c` is `drop`, then the Daemon makes the next hop at once and the skipped one is `dropped` with the reason `receiver gone` or, for `drop`, B4's. A Meta-agent that is itself `c`, or that has been a hop for this question, is never made a hop again, and nothing goes down or across the Rail, so a question has at most one hop per Meta-agent of the chain and one landing. When every Meta-agent of the chain is skipped, the landing follows at once.

**B17 an answer stops the bubble.** Given a question with hops, when a hop's Agent sends a `note` whose `replyTo` is that hop's Message or any earlier hop's, then the note is delivered to `c` as B2 says, no further hop is made, a pending bound is cancelled, and a hop still `pending` or `held` becomes `dropped` with the reason `answered`. When the question has already landed, the held Message to the user becomes `dropped` with the reason `answered` and the user's own answer after that is delivered all the same. Each hop is typed at most once and the landing is made at most once (B8), including across a restart. Touches: each hop logs `wrote` on its own `message:<n>` by `c`, as B11 says; `message.pass` and a bound that runs out log `wrote` on the new hop by the Daemon's own id as Actor `rupd`, and `provenance.history` of the first hop lists them in order; reading a hop is B11's `read` rule.

**B18 permission requests do not bubble.** Given an Agent with a permission Card (the Card of `CONTEXT.md`), then it is never a hop: it goes to the Inbox at once, as H-series says, whatever Meta-agents sit above the Agent. A `message.send` from an Actor other than the user whose `replyTo` names a Message of kind `card` is `FORBIDDEN`, and nothing changes. The case waits for the Card store to be on main; until then its test is skipped, loudly.
