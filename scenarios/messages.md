# Messages between Actors (B1 to B18)

Messages let the user, Agents and Extensions send each other typed text. Design, contract and module split: `docs/messages.md`. Terms are in `CONTEXT.md`. A Message's status is one of `pending`, `held`, `delivered` and `dropped`; a `held` Message also names why (`ask-first`, `takeover` or `escalated`). Tests use a fake `claude`, the fake Terminal of `crates/terminal` and a fake clock; none needs a display or a network.

**B1 send.** Given an open Project with Agent `a`, when an Actor calls `message.send {to: "a", kind, body, replyTo?}`, then the result is a Message with the next id (1, then 2 and on, per Project), `from` the calling Actor (never a parameter, so nobody can forge it), `to` the Agent `a`, `kind`, `body`, `replyTo` or `null`, a `status` and `at`. The call emits `message.sent` and logs a `wrote` Touch (B11). `kind` is `note` or `question`; both are delivered alike, and B2's text names the kind, so the receiver can see it was asked; any other `kind` is `INVALID_PARAMS`. A `to` that names no Actor is `NOT_FOUND`. A `to` that is a Terminal, a Group or the sender itself is `INVALID_PARAMS`. An empty body, one larger than 8192 bytes, or a `replyTo` that names no Message is `INVALID_PARAMS`. A receiver whose Kind is `done` or `error` is `CONFLICT` (B9). A receiver with 32 Messages in `pending` or `held` is `CONFLICT` naming the bound. A rejected call changes nothing: no id is used, no event is sent and no Touch is logged.

**B2 auto delivery.** Given a Route from the sender to Agent `a` of `auto` (B5) and no Takeover of `a` (B6), when a Message is sent while `a` has Kind `idle`, then the Message is typed into `a`'s Terminal as one prompt, `[from <sender's name>, <kind>] <body>`, submitted as a spawn prompt is, its status becomes `delivered`, and `message.delivered` is emitted, in that order. When `a` has any other Kind, the status is `pending`, nothing is typed, and the Message is delivered the next time `a`'s Kind becomes `idle`. Exactly one Message is typed per `idle`: a second pending Message waits for the next one. `<sender's name>` is the Rail name for an Agent, `you` for the user and the Extension's id for an Extension.

**B3 ask-first.** Given a Route of `ask-first`, when a Message is sent, then its status is `held` with the reason `ask-first`, nothing is typed, `message.held` is emitted, and it stays so until the user acts. `message.deliver {id}` makes it `pending`, so B2 applies from there; `message.drop {id}` makes it `dropped` and emits `message.dropped`. Only the user may call either; any other Actor gets `FORBIDDEN`. Calling either on a Message that is not `held` is `CONFLICT`. A Held Message is never delivered or dropped by anything but the user's call.

**B4 drop.** Given a Route of `drop`, when a Message is sent, then the call succeeds and returns the Message with the status `dropped`; nothing is typed, and `message.dropped` is emitted. The sender is not told it was dropped by an error.

**B5 Routes.** Given no Route for a sender and receiver, then the delivery is `auto`. `route.set {from, to, delivery}` stores a Route for that pair, `delivery` being `auto`, `ask-first` or `drop`, and emits `route.changed`; `route.list` returns every stored Route. Only the user may call `route.set`; any other Actor gets `FORBIDDEN`, so a user's choice is never overridden by an Agent. A Route whose `to` is the user, or whose `from` equals its `to`, is `INVALID_PARAMS`. A change applies to Messages sent after it: a Message already `held` stays `held`, and one already `pending` stays `pending`.

**B6 Takeover.** Given the user calls `takeover.begin {agent}` for Agent `a`, then until `takeover.end {agent}` a Message to `a` from any Actor but the user is not typed: with an `auto` Route it is `held` with the reason `takeover`, and with an `ask-first` Route it is `held` with the reason `ask-first`; with a `drop` Route it is `dropped`, as B4 says. A Message the user sends to `a` is delivered as B2 says. When the Takeover ends, every Message `held` for the reason `takeover` becomes `pending` in id order and B2 applies; those held for `ask-first` stay `held`. `message.deliver` on a Message held for the reason `takeover` makes it `pending` at once and B2 applies though the Takeover goes on, because the user's call wins. Only the user may call `takeover.begin` and `takeover.end`, otherwise `FORBIDDEN`; a second `begin`, or an `end` with no `begin`, changes nothing and is not an error; an id that names no Agent is `NOT_FOUND`, and an Agent whose Kind is `done` or `error` is `CONFLICT`. A Takeover ends by itself when `a` exits, and a Daemon that starts again has none; in every case of an end, the Messages held for `takeover` become `pending` first, and only then do B8 and B9 apply to them. Each change emits `takeover.changed {agent, on}`.

**B7 order.** Given several Messages to one Agent, then they are typed in the order in which they became deliverable, ties broken by id: a `held` Message that is released (B3, B6) takes its place at the moment of release, behind the `pending` Messages already waiting. A `held` Message never blocks a later Message to the same Agent that is not held.

**B8 restart.** Given a Project whose Daemon was killed without warning and is started again (D6), then Routes, every Message and its status survive, and the next Message id continues the sequence. No Message is ever typed twice: the Daemon records a Message `delivered` just before it types it and, when the Terminal refuses the bytes, records it `dropped` with the reason `write failed`, so a Daemon killed in between leaves it `delivered` (at most once). A Message to an Agent whose Terminal did not survive (A12), in the status `pending`, becomes `dropped` with the reason `receiver gone`; one in the status `held` for the reason `ask-first` stays `held` and the user may still drop it; one held for `takeover` first becomes `pending`, because no Takeover survives a restart (B6), and is then `pending`, delivered by B2 if its Agent is there and dropped with `receiver gone` if not. Messages to the user keep their status. The reasons are listed by `message.get`.

**B9 receiver gone.** Given Agent `a` whose Kind becomes `done` or `error`, then every Message to `a` in the status `pending` becomes `dropped` with the reason `receiver gone`, one `message.dropped` each, in id order; Messages held for `takeover` are first `pending`, as B6 says of the Takeover's end, and so are dropped with the rest; Messages held for `ask-first` stay `held`; and a later `message.send` to `a` is `CONFLICT`. `message.deliver` on a `held` Message to such an Agent is `CONFLICT` and leaves it `held`.

**B10 to the user.** Given a Message whose `to` is the user, then it is `delivered` at once, whatever Routes exist, nothing is typed anywhere, and `message.delivered` is emitted. Such a Message sends no `agent.status` event and changes no Agent's Kind (`PRINCIPLES.md` P3), and `message.list {to: "user"}` lists it. What the webview shows of it is the Inbox's scenario, not this series.

**B11 Touch.** Given a Message with id `n`, then `message.send` logs a `wrote` Touch on `message:<n>` by the sender, `message.deliver` and `message.drop` log one by the user, `message.get {id}` logs a `read` Touch by its caller, and `message.list {to?, status?}` logs none; for an Agent it returns only the Messages that Agent sent or received. `provenance.history {item: "message:<n>"}` returns them in order, and `provenance.touched` lists them under each Actor. Reading is by Actor: an Agent may `message.get` a Message it sent or received, and any other Message is `FORBIDDEN`; the user may read any. `CONTEXT.md` now says a Touch is of a Todo, a Pad or a Message.

**B12 an Agent sends and reads.** Given `rup mcp <agent-id>` on stdio (M1), when an MCP client lists tools, then `message_send`, `message_get`, `message_list` and `message_pass` are offered besides M1's, named after their methods with the dot replaced by `_`, with input schemas derived from the params types in `crates/contracts`. A call is made as that Agent, so `from` is its id and B11's rule on reading applies; an Agent cannot name another sender. M1 lists the exact set of tools; this scenario narrows it by those four, and the test `m1_offers_one_tool_per_method_and_no_others` is amended to M1's methods plus the four, in the same PR as `scenarios/mcp.md`'s M1 text. `message_deliver`, `message_drop`, `route_set` and the `takeover` methods are not offered: they are the user's. Each tool call and its result are exactly the Daemon's result or error for the method, as M1 says.

## Escalation: a question bubbles up

A `question` sent to a Meta-agent that does not answer passes up the Rail, one Meta-agent at a time, and lands in the user's Inbox at the end. Permission requests never take this path (B18). Nothing here drops, delivers or releases a `held` Message: B3, B9 and B6 keep every `held` Message for the user or the Takeover's end, so a hop that is `held` waits, and the chain waits with it. Tests use the fake clock and Rail trees with nested Groups and two or three Meta-agents.

**B13 hops.** Given a `question` sent to a Meta-agent `m1`, then the chain is `m1`, then the Meta-agents among `m1`'s ancestors, nearest first (Groups hold no Agent and are skipped), then the user; the sender `c` is never a hop, so a Meta-agent that is `c` or `c`'s ancestor is left out. The chain is read once, when `c` sends, and a Rail move afterwards does not change it. The Message to `m1` is the first hop. When `m1` has not answered within the bound (B14), the Daemon makes the next: `from` `c`, `to` the next Meta-agent, kind `question`, the same body, `replyTo` null, with `passedFrom` the previous hop in `message.get`; a previous hop still `pending` becomes `dropped` with the reason `passed`, and one that was delivered stays so. A `question` to an Agent that is no Meta-agent, or to the user, has one hop and never passes. Each hop is an ordinary Message, so B1's bounds, B2, B5 and B6 apply to it. `message.pass {id}` passes at once: only the Agent the hop is `to` may call it, and only on a hop that is `pending` or `delivered`, otherwise `FORBIDDEN` or `CONFLICT`; it is offered to Agents as the tool `message_pass` (B12).

**B14 the per-hop bound.** Given a hop in the status `pending` or `delivered`, then its bound is 60 000 ms of the Daemon's clock from the moment the hop was made. The test supplies the fake clock: 59 999 ms after, the hop has not passed; at 60 000 ms it has. A hop that is `held`, for `ask-first` or `takeover`, has no bound: it waits for the user or the Takeover's end (B3, B6), and the bound starts when it becomes `pending`. After a restart (B8) every bound is read from the stored times, and a hop whose bound has run out passes once when the Daemon starts.

**B15 landing.** Given the last Meta-agent of the chain has passed, then the Daemon makes a Message to the user: `from` `c`, kind `question`, `replyTo` null, status `held` with the reason `escalated`, and no `message.delivered`. This is the one Message to the user that B10's "delivered at once" does not cover; a `question` that `c` sends to the user directly is B10's. It changes no Agent's Kind and rings nothing (`PRINCIPLES.md` P3); `message.list {to: "user", status: "held"}` lists it. Only the user answers it: `message.send` from the user with `replyTo` that Message is delivered to `c` as B2 says and the held Message becomes `delivered`; `message.drop` ends it as B3 says. A next hop whose Agent is gone or cannot take the Message (B16) never delays the landing.

**B16 skipped hops, no loops.** Given a next hop whose Agent is `done` or `error`, no longer in the Rail, whose Route from `c` is `drop` (B4) or which has 32 Messages `pending` or `held` (B1), then the hop is made `dropped` with that reason, or never made, and the next one follows at once. A Meta-agent is at most one hop of a question, and nothing goes down or across the Rail, so a question has at most one hop per Meta-agent of the chain and one landing.

**B17 an answer stops the bubble.** Given a question whose current hop is `delivered`, when that hop's Agent sends a `note` whose `replyTo` is the hop's Message, then the note is delivered to `c` as B2, B5 and B6 say, no further hop is made, and the bound is cancelled. A note from an earlier hop, or after the landing, is an ordinary note and stops nothing. Each hop is typed at most once and the landing is made at most once (B8). Touches: a hop made by `c`'s send logs `wrote` on its own `message:<n>` by `c` (B11); a hop made by a bound or by `message.pass` logs it by the Actor `rupd`; `provenance.history {item: "message:<n>"}` returns each hop's own Touches, and `passedFrom` links the hops.

**B18 permission requests do not bubble.** Given an Agent that has a Meta-agent above it and raises a permission request, then it reaches the user at once, with no hop and no Route, as H10 says, and nothing sent to the Meta-agent says it exists; only the user answers it, by H4's `proof`. This scenario states nothing about what a Card is. Its test waits for H10 and H4 to be on main; until then it is skipped, loudly.
