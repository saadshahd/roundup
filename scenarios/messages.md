# Messages between Actors (B1 to B28)

Module: `crates/messages` (with the tools in `crates/rup`). Ids: every `B` heading in the file.

Messages let the user, Agents and Extensions send each other typed text. Design, contract and module split: `docs/messages.md`. Terms are in `GLOSSARY.md`. A Message's status is one of `pending`, `held`, `delivered` and `dropped`; a `held` Message also names why (`ask-first`, `takeover` or `escalated`). Tests use a fake `claude`, the fake Terminal of `crates/terminal` and a fake clock; none needs a display or a network.

**B1 send.** Given an open Project with Agent `a`, when an Actor calls `message.send {to: "a", kind, body, replyTo?}`, then the result is a Message with the next id (1, then 2 and on, per Project), `from` the calling Actor (never a parameter, so nobody can forge it), `to` the Agent `a`, `kind`, `body`, `replyTo` or `null`, a `status` and `at`. The call emits `message.sent` and logs a `wrote` Touch (B11). `kind` is `note` or `question`; both are delivered alike, and B2's text names the kind, so the receiver can see it was asked; any other `kind` is `INVALID_PARAMS`. A `to` that names no Actor is `NOT_FOUND`. A `to` that is a Terminal, a Group or the sender itself is `INVALID_PARAMS`; only an Agent or the user can be its own receiver, so an Extension may send to an Agent that has its id. An empty body, one larger than 8192 bytes, or a `replyTo` that names no Message is `INVALID_PARAMS`. A receiver whose Kind is `done` or `error` is `CONFLICT` (B9). A receiver with 32 Messages in `pending` or `held` that are not pushed digests (B21) is `CONFLICT` naming the bound; pushed digests have their own bound (B22). A rejected call changes nothing: no id is used, no event is sent and no Touch is logged.

**B2 auto delivery.** Given a Route from the sender to Agent `a` of `auto` (B5) and no Takeover of `a` (B6), when a Message is sent while `a` has Kind `idle`, then the Message is written to `a`'s Terminal as one prompt, `[from <sender's name>, <kind>] <body>`, by `Agents::prompt` (H11, `scenarios/control.md`), the one function that writes a prompt; its status becomes `delivered`, and `message.delivered` is emitted, in that order. The Daemon calls only when `a` is `idle`, so `Busy` is a race (`a` left `idle` in between): nothing was typed, the Message goes back to `pending` for the next `idle`, and this is the one move from `delivered` to `pending`. `NotAccepted` makes it `dropped` with the reason `not accepted`, and `NotFound` with `receiver gone`; nothing is sent again. When `a` has any other Kind, the status is `pending`, nothing is typed, and the Message is delivered the next time `a`'s Kind becomes `idle`. Exactly one Message is typed per `idle`: a second pending Message waits for the next one. `<sender's name>` is the Rail name for an Agent, `you` for the user, the Extension's id for an Extension and `rupd` for the Daemon.

**B3 ask-first.** Given a Route of `ask-first`, when a Message is sent, then its status is `held` with the reason `ask-first`, nothing is typed, `message.held` is emitted, and it stays so until the user acts. `message.deliver {id}` makes it `pending`, so B2 applies from there; `message.drop {id}` makes it `dropped` and emits `message.dropped`. Only the user may call either; any other Actor gets `FORBIDDEN`. Calling either on a Message that is not `held` is `CONFLICT`. A Held Message is never delivered or dropped by anything but the user's call.

**B4 drop.** Given a Route of `drop`, when a Message is sent, then the call succeeds and returns the Message with the status `dropped`; nothing is typed, and `message.dropped` is emitted. The sender is not told it was dropped by an error.

**B5 Routes.** Given no Route for a sender and receiver, then the delivery is `auto`. `route.set {from, to, delivery}` stores a Route for that pair, `delivery` being `auto`, `ask-first` or `drop`, and emits `route.changed`; `route.list` returns every stored Route. Only the user may call `route.set`; any other Actor gets `FORBIDDEN`, so a user's choice is never overridden by an Agent. A Route whose `to` is the user, or whose `from` equals its `to`, is `INVALID_PARAMS`. A change applies to Messages sent after it: a Message already `held` stays `held`, and one already `pending` stays `pending`.

**B6 Takeover.** Given the user calls `takeover.begin {agent}` for Agent `a`, then until `takeover.end {agent}` a Message to `a` from any Actor but the user is not typed: with an `auto` Route it is `held` with the reason `takeover`, and with an `ask-first` Route it is `held` with the reason `ask-first`; with a `drop` Route it is `dropped`, as B4 says. A Message the user sends to `a` is delivered as B2 says. A Message from any Actor but the user that is `pending` for `a` when `takeover.begin` is called becomes `held` with the reason `takeover`, with one `message.held` each, before `begin` returns; no lock is held while a prompt is typed, so `begin` never waits. The cut is B8's record: a Message whose status `delivered` was recorded before `begin` stays `delivered`, and its one prompt may still be typed just after `begin` returns (B2's record is one conditional write, made only while the Message is still `pending` and no Takeover holds `a`; it types only if that write succeeded, so a `begin` that comes between B2's check and its record holds the Message and nothing is typed). `message.drop {id}` on a Message held for `takeover` is B3's: the user only, `dropped` (B3 gives no reason and this adds none), `message.dropped` emitted, the Takeover goes on and nothing is typed; a dropped Message is not among those released when the Takeover ends. Tests: `b6_pending_messages_are_held_when_a_takeover_begins`, `b6_a_message_recorded_delivered_before_begin_stays_delivered` (a fake Terminal that blocks the write, `begin` returns at once), `b6_begin_between_check_and_record_holds_the_message` (the fake store runs `begin` after B2's check and before its record: the Message is `held`, nothing is typed), `b6_drop_of_a_takeover_held_message`. When the Takeover ends, every Message `held` for the reason `takeover` becomes `pending` in id order and B2 applies; those held for `ask-first` stay `held`. `message.deliver` on a Message held for the reason `takeover` makes it `pending` at once and B2 applies though the Takeover goes on, because the user's call wins. Only the user may call `takeover.begin` and `takeover.end`, otherwise `FORBIDDEN`; a second `begin`, or an `end` with no `begin`, changes nothing and is not an error; an id that names no Agent is `NOT_FOUND`, and an Agent whose Kind is `done` or `error` is `CONFLICT`. A Takeover ends by itself when `a` exits, and a Daemon that starts again has none; in every case of an end, the Messages held for `takeover` become `pending` first, and only then do B8 and B9 apply to them. Each change emits `takeover.changed {agent, on}`.

**B7 order.** Given several Messages to one Agent, then they are typed in the order in which they became deliverable, ties broken by id: a `held` Message that is released (B3, B6) takes its place at the moment of release, behind the `pending` Messages already waiting. A `held` Message never blocks a later Message to the same Agent that is not held.

**B8 restart.** Given a Project whose Daemon was killed without warning and is started again (D6), then Routes, every Message and its status survive, and the next Message id continues the sequence. No Message is ever typed twice: the Daemon records a Message `delivered` just before it types it and, when the call fails as B2 says (`Busy` back to `pending`, `NotAccepted` or `NotFound` to `dropped`; a Terminal that refuses the bytes is `NotAccepted`, since no `UserPromptSubmit` Signal follows), so a Daemon killed in between leaves it `delivered` (at most once). A Message to an Agent whose Terminal did not survive (A12), in the status `pending`, becomes `dropped` with the reason `receiver gone`; one in the status `held` for the reason `ask-first` stays `held` and the user may still drop it; one held for `takeover` first becomes `pending`, because no Takeover survives a restart (B6), and is then `pending`, delivered by B2 if its Agent is there and dropped with `receiver gone` if not. Messages to the user keep their status. The reasons are listed by `message.get`.

**B9 receiver gone.** Given Agent `a` whose Kind becomes `done` or `error`, then every Message to `a` in the status `pending` becomes `dropped` with the reason `receiver gone`, one `message.dropped` each, in id order; Messages held for `takeover` are first `pending`, as B6 says of the Takeover's end, and so are dropped with the rest; Messages held for `ask-first` stay `held`; and a later `message.send` to `a` is `CONFLICT`. `message.deliver` on a `held` Message to such an Agent is `CONFLICT` and leaves it `held`.

**B10 to the user.** Given a Message whose `to` is the user, then it is `delivered` at once, whatever Routes exist (B15's escalated question is the one exception), nothing is typed anywhere, and `message.delivered` is emitted. Such a Message sends no `agent.status` event and changes no Agent's Kind (`PRINCIPLES.md` P3), and `message.list {to: "user"}` lists it. What the webview shows of it is the Inbox's scenario, not this series.

**B11 Touch.** Given a Message with id `n`, then `message.send` logs a `wrote` Touch on `message:<n>` by the sender, `message.deliver` and `message.drop` log one by the user, `message.get {id}` logs a `read` Touch by its caller, and `message.list {to?, status?}` logs none; for an Agent it returns only the Messages that Agent sent or received, and for an Extension only the ones it sent. `provenance.history {item: "message:<n>"}` returns them in order, and `provenance.touched` lists them under each Actor. Reading is by Actor: an Agent may `message.get` a Message it sent or received, and any other Message is `FORBIDDEN`; the user may read any. `GLOSSARY.md` now says a Touch is of a Todo, a Pad or a Message.

**B12 an Agent sends and reads.** Given `rup mcp <agent-id>` on stdio (M1), when an MCP client lists tools, then `message_send`, `message_get`, `message_list` and `message_pass` are offered besides M1's, named after their methods with the dot replaced by `_`, with input schemas derived from the params types in `crates/contracts`. A call is made as that Agent, so `from` is its id and B11's rule on reading applies; an Agent cannot name another sender. M1 lists the exact set of tools; this scenario narrows it by those four, and the test `m1_offers_one_tool_per_method_and_no_others` is amended to M1's methods plus the four, in the same PR as `scenarios/mcp.md`'s M1 text. `message_deliver`, `message_drop`, `route_set` and the `takeover` methods are not offered: they are the user's. Each tool call and its result are exactly the Daemon's result or error for the method, as M1 says.

## Escalation: a question bubbles up

A `question` sent to a Meta-agent that does not answer passes up the Rail, one Meta-agent at a time, and lands in the user's Inbox at the end. Permission requests never take this path (B18). Nothing here drops, delivers or releases a `held` Message: B3, B9 and B6 keep every `held` Message for the user or the Takeover's end, so a hop that is `held` waits, and the chain waits with it. Tests use the fake clock and Rail trees with nested Groups and two or three Meta-agents.

**B13 hops.** Given a `question` sent to a Meta-agent `m1`, then the chain is `m1`, then the Meta-agents among `m1`'s ancestors, nearest first (Groups hold no Agent and are skipped), then the user; the sender `c` is never a hop: if it appears in the chain it is skipped. The chain is read once, when `c` sends, and a Rail move afterwards does not change it. The Message to `m1` is the first hop. When `m1` has not answered within the bound (B14), the Daemon makes the next: `from` `c`, `to` the next Meta-agent, kind `question`, the same body, `replyTo` null, with `passedFrom` the previous hop in `message.get`; a previous hop still `pending` becomes `dropped` with the reason `passed`, and one that was delivered stays so. A `question` to an Agent that is no Meta-agent, or to the user, has one hop and never passes. Each hop is an ordinary Message, so B1's bounds, B2, B5 and B6 apply to it. `message.pass {id}` passes at once: only the Agent the hop is `to` may call it, and only on a hop that is `pending` or `delivered`, otherwise `FORBIDDEN` or `CONFLICT`; it is offered to Agents as the tool `message_pass` (B12).

**B14 the per-hop bound.** Given a hop in the status `pending` or `delivered`, then its bound is 60 000 ms of the Daemon's clock from the moment the hop was made. The test supplies the fake clock: 59 999 ms after, the hop has not passed; at 60 000 ms it has. A hop that is `held`, for `ask-first` or `takeover`, has no bound: it waits for the user or the Takeover's end (B3, B6), and the bound starts when it becomes `pending`. After a restart (B8) every bound is read from the stored times, and a hop whose bound has run out passes once when the Daemon starts.

**B15 landing.** Given the last Meta-agent of the chain has passed, then the Daemon makes a Message to the user: `from` `c`, kind `question`, `replyTo` null, status `held` with the reason `escalated`, and no `message.delivered`. This is the one Message to the user that B10's "delivered at once" does not cover; a `question` that `c` sends to the user directly is B10's. It changes no Agent's Kind and rings nothing (`PRINCIPLES.md` P3); `message.list {to: "user", status: "held"}` lists it. Only the user answers it: `message.send` from the user with `replyTo` that Message is delivered to `c` as B2 says and the held Message becomes `delivered`; `message.drop` ends it as B3 says. A next hop whose Agent is gone or cannot take the Message (B16) never delays the landing.

**B16 skipped hops, no loops.** Given a hop that ends without an answer, whether it is `dropped` for any reason but `answered` (receiver gone, `not accepted`, a restart's drop of a `pending` Message (B8), the user's `message.drop` of a hop held for `ask-first`) or `delivered` and its Agent then ends, then the next hop is made at once, with no wait for the bound; only a live Agent that does not answer makes the question wait the 60 000 ms of B14. Given a next hop whose Agent is `done` or `error`, no longer in the Rail, whose Route from `c` is `drop` (B4) or which has 32 Messages `pending` or `held` other than pushed digests (B1), then the hop is made `dropped` with that reason, or never made, and the next one follows at once. A Meta-agent is at most one hop of a question, and nothing goes down or across the Rail, so a question has at most one hop per Meta-agent of the chain and one landing.

**B17 an answer stops the bubble.** Given a question whose current hop is `delivered`, when that hop's Agent sends a `note` whose `replyTo` is the hop's Message, then the note is delivered to `c` as B2, B5 and B6 say, no further hop is made, and the bound is cancelled. A note from an earlier hop, or after the landing, is an ordinary note and stops nothing. Each hop is typed at most once and the landing is made at most once (B8). Touches: a hop made by `c`'s send logs `wrote` on its own `message:<n>` by `c` (B11); a hop made by a bound or by `message.pass` logs it by the Actor `rupd`; `provenance.history {item: "message:<n>"}` returns each hop's own Touches, and `passedFrom` links the hops.

**B18 permission requests do not bubble.** Given an Agent that has a Meta-agent above it and raises a permission request, then it reaches the user at once, with no hop and no Route, as H10 says. It is a Decision, which is not a Message: it has no Route, is never `held` and is not a hop, and nothing sent to the Meta-agent says it exists. Only the user answers it, by H4's `proof`. H10's test is this scenario's test.

## Child digests: a Meta-agent learns what its children did

A Meta-agent has no shell and reads children only through tools, so a child's state reaches it as a small fixed envelope, asked for or pushed on change, and never as Terminal output. Every cut or merge is marked in the text; nothing is dropped without a sign. Tests use the fake clock, a Rail with Meta-agent `m` and children `a`, `b` and `c`, and a fake Terminal that prints a unique word.

**B19 the envelope.** Given a Meta-agent `m`, then the digest of a child is exactly `{name, kind, last, todos, pads}`: `name` the child's Rail name, `kind` its Kind, `last` one line of at most 120 bytes, `todos` the number of open Todos whose Home is the child, and `pads` the names of the child's Pads written since the previous envelope about that child went to `m` (at most 4 names of at most 32 bytes each). `last` is the first line of the newest Message the child sent to `m`, or the child's Status label when it sent none; a line cut at 120 bytes, a name cut at 32 and a `pads` list cut at 4 each end in `[cut]`, and the whole entry is at most 512 bytes. No Terminal output is ever read: a fake Terminal that prints the word `ZEBRA` leaves it out of every envelope, whatever the child's Kind.

**B20 asking.** Given `m` with children, when `agent.digest {id: "m"}` arrives, then the result is `{children: [...]}` with one entry per direct child in Rail order (B19's shape), at most 20 entries, and a last entry `{more: n}` when `m` has more than 20. A caller that is neither `m` nor the user gets `FORBIDDEN`; an id that names no Agent is `NOT_FOUND`; an Agent that is no Meta-agent is `CONFLICT`. `rup mcp <m>` offers the tool `agent_digest` to Meta-agents only, taking no input (the shim fills `id` with its own Agent's id), and no other Agent's tool list has it; this narrows M1's closed list of tools in `scenarios/mcp.md` by that one tool for a Meta-agent, and `m1_offers_one_tool_per_method_and_no_others` is amended in the same form as B12's.

**B21 pushed on change.** Given `m` and a child whose Kind changes (an `agent.status` event) or whose Pad or Todo count changes, then the Daemon sends `m` one Message from `rupd`, kind `note`, whose body is `[digest]` and that child's one entry (B19). Route, Takeover and order are as for any Message (B2, B5, B6, B7): under a Takeover of `m` the push is `held` and released at the end like the rest. No push is made for a child that has no Meta-agent, and none for a change that leaves the entry as it was.

**B22 caps.** Given `m`, then (a) at most 8 pushes go to `m` in any window of 60 000 ms of the fake clock; the pushes after the eighth wait and, at the window's end, become one Message `[digest] [K updates held back]` with the newest entries of at most 8 affected children, newest change first (at most 4096 bytes), then one line `[+n more: <names>]` for the others, cut at 512 bytes and ending `[cut]` when longer; (b) at most 20 pushed digests are `pending` or `held` for `m` at once: when a twenty-first arrives, the oldest two merge into one Message beginning `[digest] [N earlier updates: #a #b]` with N their count (a merged one counts its own N), `a` and `b` the two merged Messages' ids, and the newest entry of each child they named; the two become `dropped` with the reason `merged` and stay readable by `m` through `message.get` (P7); (c) no cap loses a count: every pushed digest has a weight, 1 for a plain push and the sum of the weights it holds for a rollup (K) or a merge (N), and the total weight of the digests delivered or still waiting equals the number of changes that changed an entry (a change that leaves the entry as it was is not one, B21), which the test checks after a burst of 100 changes, with a Takeover of `m` for part of it, along with every pushed digest being delivered, still waiting, or named by a merge that is, and `message.get` opening each for `m`; (d) pushed digests count only against (b), not against B1's 32, so a push never gets `CONFLICT`, and `m` filled to B1's bound by other Messages (held under a Takeover, B6) still receives its pushes.

**B23 survive and gone.** Given pushes and a rollup that were `pending` when the Daemon was killed (D6), then after a restart they are delivered or dropped as B8 says, the K and N counts in their bodies are intact, and the 60 000 ms window starts again. A child that is removed or ends (`done`, `error`) gets one last push with its Kind, and a Meta-agent that is gone gets none (B9).

**B24 a Door's Brief describes its current role.** Given a Room whose Door starts by A7, its E1 Brief says it is the Room's coordinating Door, uses the available Todo tools to record and update work, reports the outcome to the user, and asks in its existing Terminal when the user's goal or a taste limit is unclear. It must not claim child spawning, inter-Agent messaging, awareness or a structured question tool that the current MCP does not offer. An ordinary Agent's Brief has no Door role guidance. The observer starts a real Daemon and a deterministic fake `claude`, starts a Room's Door, reads the Brief passed in argv, and uses that Agent's real `rup mcp` connection to create a Todo and update its body; the stored Todo's creator is that Door and the App renders the resulting title and body. The fake checks the Brief and performs the MCP exchange, so a database seed or a claimed terminal result cannot pass. Native proof uses a throwaway Project at 1280×800, with Room/Door labels; it does not claim Room-scoped Todo storage or delegation. No Todo comment method is introduced. Future coordination policy is retained: before spawning, resolve an unclear goal or taste limit; give a child fixed limits rather than a decision; require a done-when condition, owned files or directories and an observer. That policy becomes actionable with H14/F3 and is not evidence those capabilities shipped. B25's enforcement question remains open. The E1 Brief contents are owned by `awareness.md`. The user authorized the bounded E1/B24 implementation as one slice in PR #326; independent code review and rule 4 still apply.

**B25 (spike) the spec gate in the Daemon.** Question: should `agent.spawn` by a Meta-agent (F3) take `{doneWhen, owns, observer}` and answer `INVALID_PARAMS` without them? Pass: 20 recorded `agent_spawn` calls from a Meta-agent run on the fake `claude`, of which at most 4 (20%) would be refused on a missing field with B24's Brief in place; then the spike writes the contract text (rule 4). Fail: more than 4 would be refused, and B24's Brief stays the whole gate. No Builder starts on this id.

**B26 (spike) the Touch log records why a Message was held or dropped.** Question: should each status change of a Message also be a Touch with its reason? Today B8 and B9 keep status and reason in the Messages store, and a Touch is `{actor, verb, item, at}` with Verb `read` or `wrote` in the provenance store, a different store (D6's transaction cannot span both). Pass: a written design that names the actor and verb of an automatic change (nobody calls for an auto `delivered`), lists the reasons the series defines (`ask-first`, `takeover`, `escalated`, `receiver gone`, `not accepted`, `passed`, `answered`), says how a kill between the two writes leaves each Touch once and none missing, and gives the contract text (`Touch.reason`, rule 4). Reading a failed child's last Touch for the Meta-agent (the anchor's "inspect the last provenance entry") belongs to the same design. No Builder starts on this id.

**B27 (spike) small evaluators in the Daemon.** Question: can `rupd` call a small local model, an Evaluator, for three jobs with no frontier tokens: check that a Quote (U110) matches the Daemon's own Message records, answer a routine child `question` against the Meta-agent's Brief with a `--why`, and run the anti-slop and sound checks before `git`? Pass, for each job: p95 latency at most 200 ms and at least 18 of 20 recorded cases right; the model's size and licence are written down. When the Evaluator is absent the question goes on to B13's chain and nothing is answered silently. A fake Evaluator counts tokens, so a test proves none go to a frontier model. The Evaluator reads only the Daemon's own records, never a vendor transcript (P4). It is a new seam, so the spike ends with a proposal for the committee. No Builder starts on this id.

**Room/Door lifecycle boundary (B1/B6/B9).** The atomic Room implementation updates `crates/messages` receiver and Takeover predicates with its Agent/Rail callers. A stopped Door rejects sends and Takeovers under the existing receiver-gone behavior; an explicit successful start makes the same Door id reachable again. Messages already final before stop remain final after restart: never revive them or carry an old Takeover into the new run. An earlier Attempt's exit/events cannot drop Messages or alter Takeovers created for the new run. Real-Daemon/fake-Claude tests stop and restart one Door, attempt stopped sends/Takeovers, retain old final Messages, accept new-run `message.send` into pending or held state, and preserve that state and a new Takeover while releasing a delayed old exit. This observes acceptance and state only; actual automatic delivery into a Terminal remains unimplemented and outside this slice. M3/M5/M7 remain relevant safety laws, but `proofs/messages/model.bend` models `gone` as permanent and does not prove restart safety; do not cite its existing pass as a restart proof. This slice keeps the existing Message/Route/Takeover contract and finality laws; if implementation needs to change those contracts or proof laws, stop for a scoped architect amendment.

**B28 one failure fails one operation.** Given a panic or a store error inside one Messages operation (an RPC call, the status listener's `on_status`/`settle`, or the bound clock's pass of B14), then only that operation fails and the Daemon recovers without a restart, a module restart or any user action: (a) the store lock is never left poisoned, so the next call takes it; (b) the operation's SQLite transaction (`store.rs` runs each change as one) leaves all of its writes or none, and no `message.*` or `route.changed` event is emitted for a write that did not stay; (c) the cause is logged once to the Daemon's stderr as one line naming the operation (`message.send`, `on_status`, `settle`, `clock`) and the cause; (d) the caller gets `INTERNAL` whose message names the cause, never `message store poisoned` without one; (e) the background listener and the bound clock keep running: after a failure inside `on_status` or `settle`, the next `idle` of the Agent delivers its pending Message (B2), and a hop passes at B14's bound (59 999 ms not, 60 000 ms passed) under the fake clock. B8 holds: a failure never makes a Message `delivered` that was not typed, nor types one twice. B6 holds: no lock is held while a prompt is typed. Tests (policy: which of the two designs of #438 holds, recovering the guard or holding no lock across code that can panic, is the implementation's, and these observe only the result): `b28_a_panic_in_a_locked_operation_leaves_the_next_calls_working` (a store fake panics inside one locked operation; then `message.send`, `message.get`, `route.set` and `takeover.begin` each succeed), `b28_a_failed_operation_changes_nothing_listed` (`message.list` and `route.list` are equal before and after the failed call, and no event was emitted), `b28_a_failure_in_on_status_or_settle_does_not_stop_delivery_or_the_clock` (the failure injected in `on_status`, then in `settle`; the next `idle` delivers, and a hop passes at 60 000 ms of the fake clock), `b28_through_rupd_the_stderr_line_and_the_callers_error` (a real `rupd` with the failure injected: its captured stderr holds exactly one line naming the operation and the cause, the caller's error is `INTERNAL` naming the same cause, and the next call succeeds). Preserve: B1 to B27 are unchanged and there is no contract change; `INTERNAL` is `scenarios/rpc.md`'s code.
