# Messages between Actors (B1 to B12)

Messages let the user, Agents and Extensions send each other typed text. Design, contract and module split: `docs/messages.md`. Terms are in `CONTEXT.md`. A Message's status is one of `pending`, `held`, `delivered` and `dropped`; a `held` Message also names why (`ask-first` or `takeover`). Tests use a fake `claude`, the fake Terminal of `crates/terminal` and a fake clock; none needs a display or a network.

**B1 send.** Given an open Project with Agent `a`, when an Actor calls `message.send {to: "a", kind, body, replyTo?}`, then the result is a Message with the next id (1, then 2 and on, per Project), `from` the calling Actor (never a parameter, so nobody can forge it), `to` the Agent `a`, `kind`, `body`, `replyTo` or `null`, a `status` and `at`. The call emits `message.sent` and logs a `wrote` Touch (B11). `kind` is `note` or `question` (delivered alike; a `question` asks for a reply with `replyTo`); the Card of `CONTEXT.md` (`PRINCIPLES.md` P3) is a later series, and any other `kind` is `INVALID_PARAMS`. A `to` that names no Actor is `NOT_FOUND`. A `to` that is a Terminal, a Group or the sender itself is `INVALID_PARAMS`. An empty body, one larger than 8192 bytes, or a `replyTo` that names no Message is `INVALID_PARAMS`. A receiver whose Kind is `done` or `error` is `CONFLICT` (B9). A receiver with 32 Messages in `pending` or `held` is `CONFLICT` naming the bound. A rejected call changes nothing: no id is used, no event is sent and no Touch is logged.

**B2 auto delivery.** Given a Route from the sender to Agent `a` of `auto` (B5) and no Takeover of `a` (B6), when a Message is sent while `a` has Kind `idle`, then the Message is typed into `a`'s Terminal as one prompt, `[from <sender's name>] <body>`, submitted as a spawn prompt is, its status becomes `delivered`, and `message.delivered` is emitted, in that order. When `a` has any other Kind, the status is `pending`, nothing is typed, and the Message is delivered the next time `a`'s Kind becomes `idle`. Exactly one Message is typed per `idle`: a second pending Message waits for the next one. `<sender's name>` is the Rail name for an Agent, `you` for the user and the Extension's id for an Extension.

**B3 ask-first.** Given a Route of `ask-first`, when a Message is sent, then its status is `held` with the reason `ask-first`, nothing is typed, `message.held` is emitted, and it stays so until the user acts. `message.deliver {id}` makes it `pending`, so B2 applies from there; `message.drop {id}` makes it `dropped` and emits `message.dropped`. Only the user may call either; any other Actor gets `FORBIDDEN`. Calling either on a Message that is not `held` is `CONFLICT`. A Held Message is never delivered or dropped by anything but the user's call.

**B4 drop.** Given a Route of `drop`, when a Message is sent, then the call succeeds and returns the Message with the status `dropped`; nothing is typed, and `message.dropped` is emitted. The sender is not told it was dropped by an error.

**B5 Routes.** Given no Route for a sender and receiver, then the delivery is `auto`. `route.set {from, to, delivery}` stores a Route for that pair, `delivery` being `auto`, `ask-first` or `drop`, and emits `route.changed`; `route.list` returns every stored Route. Only the user may call `route.set`; any other Actor gets `FORBIDDEN`, so a user's choice is never overridden by an Agent. A Route whose `to` is the user, or whose `from` equals its `to`, is `INVALID_PARAMS`. A change applies to Messages sent after it: a Message already `held` stays `held`, and one already `pending` stays `pending`.

**B6 Takeover.** Given the user calls `takeover.begin {agent}` for Agent `a`, then until `takeover.end {agent}` a Message to `a` from any Actor but the user is not typed: with an `auto` Route it is `held` with the reason `takeover`, and with an `ask-first` Route it is `held` with the reason `ask-first`; with a `drop` Route it is `dropped`, as B4 says. A Message the user sends to `a` is delivered as B2 says. When the Takeover ends, every Message `held` for the reason `takeover` becomes `pending` in id order and B2 applies; those held for `ask-first` stay `held`. `message.deliver` on a Message held for the reason `takeover` makes it `pending` at once and B2 applies though the Takeover goes on, because the user's call wins. Only the user may call `takeover.begin` and `takeover.end`, otherwise `FORBIDDEN`; a second `begin`, or an `end` with no `begin`, changes nothing and is not an error; an id that names no Agent is `NOT_FOUND`, and an Agent whose Kind is `done` or `error` is `CONFLICT`. A Takeover ends by itself when `a` exits, and a Daemon that starts again has none. Each change emits `takeover.changed {agent, on}`.

**B7 order.** Given several Messages to one Agent, then they are typed in the order in which they became deliverable, ties broken by id: a `held` Message that is released (B3, B6) takes its place at the moment of release, behind the `pending` Messages already waiting. A `held` Message never blocks a later Message to the same Agent that is not held.

**B8 restart.** Given a Project whose Daemon was killed without warning and is started again (D6), then Routes, every Message and its status survive, and the next Message id continues the sequence. No Message is ever typed twice: the Daemon records a Message `delivered` just before it types it and, when the Terminal refuses the bytes, records it `dropped` with the reason `write failed`, so a Daemon killed in between leaves it `delivered` (at most once). A Message to an Agent whose Terminal did not survive (A12), in the status `pending`, becomes `dropped` with the reason `receiver gone`; one in the status `held` stays `held` and the user may still drop it. Messages to the user keep their status. The reasons are listed by `message.get`.

**B9 receiver gone.** Given Agent `a` whose Kind becomes `done` or `error`, then every Message to `a` in the status `pending` becomes `dropped` with the reason `receiver gone`, one `message.dropped` each, in id order; Messages in the status `held` stay `held`; and a later `message.send` to `a` is `CONFLICT`. `message.deliver` on a `held` Message to such an Agent is `CONFLICT` and leaves it `held`.

**B10 to the user.** Given a Message whose `to` is the user, then it is `delivered` at once, whatever Routes exist, nothing is typed anywhere, and `message.delivered` is emitted. Such a Message never changes an Agent's Kind and never rings, opens a Drawer or colours anything (`PRINCIPLES.md` P3); it only appears in the Inbox.

**B11 Touch.** Given a Message with id `n`, then `message.send` logs a `wrote` Touch on `message:<n>` by the sender, `message.deliver` and `message.drop` log one by the user, `message.get {id}` logs a `read` Touch by its caller, and `message.list {to?, status?}` logs none; for an Agent it returns only the Messages that Agent sent or received. `provenance.history {item: "message:<n>"}` returns them in order, and `provenance.touched` lists them under each Actor. Reading is by Actor: an Agent may `message.get` a Message it sent or received, and any other Message is `FORBIDDEN`; the user may read any. `CONTEXT.md` now says a Touch is of a Todo, a Pad or a Message.

**B12 an Agent sends and reads.** Given `rup mcp <agent-id>` on stdio (M1), when an MCP client lists tools, then `message_send`, `message_get` and `message_list` are offered besides M1's, named after their methods with the dot replaced by `_`, with input schemas derived from the params types in `crates/contracts`. A call is made as that Agent, so `from` is its id and B11's rule on reading applies; an Agent cannot name another sender. `message_deliver`, `message_drop`, `route_set` and the `takeover` methods are not offered: they are the user's. Each tool call and its result are exactly the Daemon's result or error for the method, as M1 says.
