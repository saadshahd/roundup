# Todos

Module: `crates/todos`. Ids: every `T` heading in the file.

**T1 create.** Given an empty Project, when the user calls `todo.create {title}`, then the result is a Todo with id 1, `done: false`, `blocked: false`; `todo.create` again gives id 2; each call emits `todo.created` and logs a `wrote` Touch on `todo:<id>` by the caller.

**T2 read.** Given Todos 1 and 2, when `todo.list` is called, then both come back in the Todo order (T10), which is id order until the user reorders; amended by T10 (`t2_` tests that read a list of Todos never reordered stay unchanged and green); `todo.get {id: 2}` returns Todo 2 and logs a `read` Touch by the caller; an unknown id is `NOT_FOUND`.

**T3 blocked is derived.** Given Todo 2 created with `blockers: [1]` and Todo 1 open, then Todo 2 has `blocked: true`. When Todo 1 is completed (`todo.complete`), then Todo 2 has `blocked: false` and `todo.unblocked {id: 2}` is emitted once, after `todo.updated` for Todo 1.

**T4 bad blockers.** Given Todos 1 and 2 where 2 is blocked by 1, when `todo.setBlockers {id: 1, blockers: [2]}` is called, then it fails with `CONFLICT` and nothing changes; an unknown blocker id fails with `NOT_FOUND`; a Todo cannot block itself (`CONFLICT`).

**T5 persistence.** Given Todos created, when the module is dropped and `Todos::open` is called again on the same directory, then every Todo, `done` state and blocker list is intact and the next id continues the sequence.

**T6 delete.** Given Todo 2 blocked by 1, when Todo 1 is deleted, then `todo.deleted {id: 1}` is emitted, Todo 2's blocker list no longer contains 1, `blocked` is false, and `todo.unblocked {id: 2}` is emitted.

**T7 update.** Given Todo 1, when `todo.update {id: 1, title: "x"}` is called, then the title changes, the body is untouched, `todo.updated` is emitted, and a `wrote` Touch is logged; an update with neither field is `INVALID_PARAMS`.

**T8 creator.** Given a Todo created by the user and one created by an Agent through its MCP server (A11), when `todo.create {title}` is called by each, then each Todo carries `creator`, an `Actor` as in `common`: the calling Actor, `{kind: user, id: "you", parent: null}` for the user. `todo.list`, `todo.get` and the `todo.created` event carry it; `todo.update`, `todo.complete` and `todo.setBlockers` never change it. The caller can also be an Extension (`ActorKind::Ext`); its Actor is stored as it is. A `creator` sent inside the params is ignored: when an Agent calls `todo.create {title, creator: <user>}`, the Todo's `creator` is that Agent. It persists across `Todos::open` (T5), and a `todos.db` written before this field, opened with `Todos::open`, returns `Actor::user()` as `creator` from `todo.get` for each old Todo; the Builder's test writes such a database by hand. Contract change (the review run's approve covers it, the Contract recipe of `.agents/builder.md`): `Todo` gains `creator: Actor`, and `CreateParams` is unchanged, so the MCP tool schema (built from `CreateParams`) and the App seam (which passes results through unchanged) need no edit. The Builder owns, and lists in the PR, every place that builds or reads a `Todo`: `crates/todos/**` (the `Todo` literal in `store.rs`, its schema and a migration, `create` reading the calling Actor), `crates/contracts/**` with `contracts/generated/todo/Todo.ts`, the `Todo` uses in `crates/rup/tests/e2e.rs`, and the webview's fixtures that build a `Todo` (`src/testing/stores.ts`, `src/testing/seeds.ts`, `src/todos/testHarness.tsx` and the tests that name a `Todo` field). After `rail.remove` (A16) of an Agent, the Todos it created still read with the same `creator`; this is T8's test, since A16 does not know `creator`. The Builder starts after A15 and A16 merge, because A15 also edits `crates/rup/tests/e2e.rs` and A16 edits `src/testing/seeds.ts`; the Builder changes only the lines of those files that build or read a `Todo` (A16's `rail.remove` handler in `seeds.ts` stays as it is), and this PR is then the only one that edits those webview files until it merges; U60 starts after it.

**T9 a rejected call leaves no trace.** Given Todos 1 and 2 and a subscribed client, when `todo.create` names a blocker that does not exist (`NOT_FOUND`), `todo.setBlockers` would make a cycle (`CONFLICT`, T4), `todo.update` has neither field (`INVALID_PARAMS`) or `todo.complete` names an unknown id (`NOT_FOUND`), then after each call `todo.list` is unchanged, no event arrived, no Touch was logged, and the next `todo.create` returns id 3: a failed create never uses an id. After deleting the newest Todo and reopening with `Todos::open`, the next create still does not reuse its id. Owns `crates/todos/**`. It keeps T4 and T5 green and narrows none: T5 says the next id continues the sequence, and T9 says what continues it.

**T10 the Todos have one order, the user's.** Narrows T2 (its "id order" becomes "Todo order"), U15, U60 and U53. Given Todos, then `todo.list` returns every Todo, open and done, in one order that the Daemon keeps; every other list of Todos is that order with some Todos left out, never a second order:
- A Todo from `todo.create` goes last, after every Todo, done ones included, whoever calls it (the user, an Agent through its MCP server (A11) or an Extension). With no reorder ever made the order is id order, so every scenario that creates Todos and reads them back (T1 to T9) is unchanged.
- Completing a Todo (T3) keeps its place; `todo.list` still returns it there, and the Shelf's `✓ n done` fold (U15) lists the done Todos in that order. No `todo.*` method re-opens a Todo today; if one is added, the Todo comes back in the place it kept.
- Deleting a Todo (T6) leaves the other Todos in their order. A blocker change (T3, T4) moves nothing: `blocked` and `waits on` are independent of order.
- The Shelf's open rows (U15), the open Todos under an Agent (U60), the `✓ n done` fold, `agent.context` and the `agent_brief` open Todos, and an Agent's `todo_list` over MCP all read this order. An Agent's `todo_create` appends; the order is the user's, so `todo.reorder` (T11) is not offered over MCP, as `todo.delete` is not.
- The order persists across `Todos::open` (T5). A `todos.db` written before this scenario opens in id order, and the Builder's test writes one by hand.
Contract change (the review run's approve covers it, the Contract recipe of `.agents/builder.md`): the order is the order of `todo.list`; `Todo` gains no field, so `contracts/generated/todo/Todo.ts` and the webview fixtures that build a `Todo` do not change. The Daemon stores a position per Todo (a migration for old databases) that no contract carries. Callers of `todo.list`, each of which keeps what it reads in the order it receives: `crates/rupd/src/lib.rs` (`agent.context`, which gives `context::compose` the Todos), `crates/agents/src/claude_code/brief.rs`, `crates/rup/src/mcp.rs` and `crates/rup/tests/mcp.rs`, `crates/rup/tests/e2e.rs`, and in the webview `src/todos/todoList.ts`, `src/todos/state.ts`, `src/rail/pads/AgentPads.tsx`, `src/testing/stores.ts` and `src/testing/fakeApp.ts`, each of which must keep the received order and not sort by id. Tests (`t10_`): a Todo created after a reorder goes last; completing the first Todo keeps its place in `todo.list`; deleting a middle Todo leaves the rest in order; a reorder persists across `Todos::open`; the old database opens in id order; `todo.list` through the MCP server shows the reordered order and `todo_create` appends; `agent.context` lists open Todos in that order. Observer: `cargo test -p todos t10_` and `cargo test -p rup t10_` pass; the mechanical pass condition is the array of ids read from `todo.list`, equal to the expected array in each case.

**T11 reorder.** Given Todos 1, 2, 3 and 4 in id order, when the user calls `todo.reorder {id: 3, before: 1}`, then `todo.list` returns ids `[3, 1, 2, 4]` and the call returns Todo 3, `todo.updated` is emitted once for Todo 3 and a `wrote` Touch is logged on `todo:3` by the caller. `before: null` puts the Todo after every other Todo: `todo.reorder {id: 1, before: null}` on `[1, 2, 3, 4]` gives `[2, 3, 4, 1]`. `before` may name a done Todo. Moving a Todo to the place it already holds (`before` is the Todo that follows it, or null for the last Todo) succeeds, returns the Todo, emits nothing and logs no Touch. Rejected calls follow T9: an unknown `id` or `before` is `NOT_FOUND`, `before` equal to `id` is `CONFLICT`; each leaves `todo.list` unchanged, emits no event and logs no Touch. A reorder changes no other field of any Todo: `done`, `blockers`, `blocked`, `creator` and `created_at` read as before. Reorder is the user's call: an Extension may call it; it is not an MCP tool (T10), and a test asserts that the MCP tool list lacks it. Contract change (the review run's approve covers it, the Contract recipe of `.agents/builder.md`): `todo.reorder` takes the new `todo::ReorderParams {id: u32, before: Option<u32>}` (`crates/contracts/src/todo.rs`) and returns `todo::Todo`; no new event, because `todo.updated` already makes every list refetch (U15). The Builder owns, and lists in the PR, every place that names a `todo.*` method or a `todo::` params type: `crates/contracts/src/methods.rs` (the method row) with `contracts/generated/todo/ReorderParams.ts` regenerated from `crates/contracts`, `crates/todos/src/lib.rs` (the handler) and `store.rs` (the position), `crates/rup/src/mcp.rs` (the comment above `offered_tools`, which now names `todo.reorder` among the methods left out) and `crates/rup/tests/mcp.rs` (the method list at line 154), `crates/rup/tests/e2e.rs`, `scenarios/mcp.md` (its list of Todo tools, which names `todo.reorder` as not offered), `scenarios/rpc.md` if it lists methods, and in the webview `src/testing/stores.ts` and `src/testing/fakeApp.ts`, which must answer `todo.reorder` the way the Daemon does; the App seam passes results through unchanged and needs no edit. `GLOSSARY.md`'s _Todo_ entry gains "in one order, the user's" in this specification PR. It keeps T1 to T9 green and narrows none. Tests (`t11_`): each sentence above, the failures with an unchanged `todo.list`, no event and no Touch, and the no-op; `todo.reorder` called through `rupd` reaches the webview as `todo.updated`. Observer: `cargo test -p todos t11_` and `cargo test -p rup t11_` pass; a `rup` run against a real `rupd` creates four Todos, calls `todo.reorder`, and prints the ids from `todo.list`, which equal `[3, 1, 2, 4]`.

**T12 a Todo has a Home.** Amended by T14 for an Agent under a Workstream (the sentences below that say `home: null` whoever calls hold for every other caller). Given the Project, then every Todo has one Home (`GLOSSARY.md`): a Workstream or the Project root. `Todo` gains `home: Option<String>`: `Some(<Rail id of a Workstream>)` (`NodeKind::Workstream`) or `None` for the Project root. `todo.create` gives every Todo `home: null`, whoever calls (the user, an Agent through its MCP server, an Extension; amended by T14: an Agent under a Workstream gets that Workstream): `CreateParams` is unchanged, a `home` sent inside the params is ignored as `creator` is (T8), and the MCP tool schema (M1) is unchanged (T14 sets an Agent's Workstream in the Daemon). `todo.list`, `todo.get` and the `todo.created` event carry `home`; `todo.update`, `todo.complete` and `todo.setBlockers` never change it. It persists across `Todos::open` (T5), and a `todos.db` written before this field, opened with `Todos::open`, returns `home: null` from `todo.get` for each old Todo: its schema gains a nullable `home` column by a migration that leaves every existing row `NULL`, and the Builder's test writes such a database by hand (as T8 does for `creator`). Blockers do not look at Homes: T3, T4 and T6 hold unchanged across Homes, so a Todo in one Workstream may be blocked by a Todo in another Workstream or at the Project root. Cross-Workstream dependency semantics (whether it should be allowed, shown or warned about) are out of scope for this delivery and stay open in `docs/wireframes.md`. The Shelf stays Project-wide (`GLOSSARY.md` Shelf): no Workstream-scoped filtering is added. Contract change (the review run's approve covers it, the Contract recipe of `.agents/builder.md`): `Todo` gains `home`; `crates/todos/**` (the `Todo` literal in `store.rs`, its schema and migration), `crates/contracts/**` with `contracts/generated/todo/Todo.ts`, the `Todo` uses in `crates/rup/tests/e2e.rs`, and the webview's fixtures that build a `Todo` (`src/testing/stores.ts`, `src/testing/seeds.ts`, `src/todos/testHarness.tsx` and the tests that name a `Todo` field) change in the same PR, and `docs/wireframes.md`'s capability matrix row "Workstream" is amended to say Todos have a Home. Tests (`t12_`): a Todo created by the user, by an Agent under no Workstream and by an Extension reads `home: null` from `todo.get`; a `home` in the params is ignored; the field is carried by `todo.list` and `todo.created`; it survives `Todos::open`; a hand-written old `todos.db` reads `home: null`; `todo.setBlockers` between Todos of two Homes succeeds (after T13). Observer: `todo.get {id}` on a real `rupd` for each of the three callers returns `home: null`, and again after the Daemon restarts on the same Project directory.

**T13 move a Todo.** Given Todo 1 at the Project root and a Workstream `r1` on the Rail (A16), when any caller (the user, an Agent or an Extension, whoever created Todo 1) calls `todo.move {id: 1, home: "r1"}`, then `todo.get {id: 1}` returns `home: "r1"`, `todo.updated {id: 1}` is emitted once (no new event: U15's refetch already follows it), a `wrote` Touch is logged on `todo:1` by the caller, and `creator`, `title`, `body`, `done`, `blockers` and `blocked` are unchanged; `todo.move {id: 1, home: null}` returns it to the Project root the same way. Moving a Todo to the Home it already has succeeds, changes nothing and emits no event and logs no Touch. A rejected call leaves no trace, as T9 says: an unknown Todo id is `NOT_FOUND`; a `home` that is no Rail node is `NOT_FOUND`; a `home` that is a Rail node but no Workstream (an Agent or a Terminal) is `INVALID_PARAMS`. `crates/rupd` owns the Daemon's side of T13: the `todo.move` handler and the Home reset on `rail.remove` (A16 is narrowed to say so). The Daemon checks the Workstream against the Rail before it asks `crates/todos`, which holds no Rail. `todo.move` is a Daemon method for the user and Extensions; M1's tool list is not amended, so an Agent cannot move a Todo in this delivery, and a later Issue adds `todo_move` to M1 by the Contract recipe. U60's placement rule is kept: a Todo under its creating Agent in the Shelf stays there whatever its Home. Removal of a Workstream: when `rail.remove` (A16) deletes a Workstream, every Todo whose `home` is that Workstream gets `home: null` in the same call, with `todo.updated` for each (in id order) after the Workstream is gone, and no Todo is deleted; a failed `rail.remove` leaves every Todo's Home as it was. Workstream nesting is open, so the Todo goes to the Project root, not to the removed Workstream's parent. Contract change (the review run's approve covers it, the Contract recipe of `.agents/builder.md`): a new RPC method `todo.move` with `MoveParams {id: u32, home: Option<String>}`, generated into `contracts/generated/todo/`; the App seam passes it through (its method list gains `todo.move`) and every caller is in the same PR; `GLOSSARY.md` _Home_ keeps its words and gains the method's name where it names the user's change. Laws M1 to M10 are not touched. Tests (`t13_`): the move to a Workstream and back; creator and blockers unchanged; a successful move logs one `wrote` Touch on `todo:1` by the caller (`t13_a_move_logs_one_touch_by_the_caller`) and emits `todo.updated` exactly once (`t13_a_move_emits_one_event`); the same-Home no-op; the three rejections each leave `todo.list`, events and Touches unchanged; a Todo created by an Agent and one by an Extension move as one by the user does; `a16_`-style tests in `crates/rup/tests/**` against a real `rupd`: after `rail.remove` of a Workstream, `todo.get` returns `home: null` for its Todos, the other Todos' Homes are unchanged, no Todo is deleted, and `todo.updated` arrives once per Todo of the Workstream in id order after `rail.tree` no longer holds the Workstream (`t13_workstream_removal_resets_homes_and_emits_in_id_order`); when `rail.remove` fails (the A16 kill-failure case, or an unknown id) every Todo keeps its Home and no `todo.updated` arrives (`t13_a_failed_rail_remove_leaves_every_home`). Observer: on a real `rupd`, `todo.move` then `todo.get` returns the new `home`, the same after the Daemon restarts, and `todo.list` after `rail.remove` of the Workstream shows `home: null` for each Todo that was in it.
