# Scheduled QA

Module: `loop/`. Ids: L66.

**L66 scheduled QA survives standby and fails visibly.** Given one normal coordinator VM with a reviewed checkout, a configured public roundup repository and Run's durable state, when `run loop/qa-coordinator.run.ts` registers `every("10 minutes", handler)`, then the platform wakes the VM for the schedule. Each tick checks one exact main SHA obtained by an unauthenticated read-only GitHub API call, in at most one disposable `ru-qa-scheduled` VM made with `--from-snapshot ru-toolchain --isolated --auto-destroy-timeout 540 --auto-suspend-timeout 0`. The QA VM clones public main, pins both HEAD and origin/main to that SHA, installs locked dependencies and invokes `loop/qa-sweep.sh`, which owns its port 5199 harness and captures 640×400 and 1280×800. No PR ref or GitHub login enters it. The coordinator records the SHA (null until resolved), UTC start/end, status, output path and cleanup outcome in durable state and its logs; output is copied before removal. Work has a 420-second deadline, copying and removal each have 30 seconds, and removal runs in finally even after uncertain creation. A live lease prevents overlap; a lease older than 500 seconds, a tick more than 60 seconds late, missing output, command failure, timeout or failed removal is red with an actionable persistent failure, never erased by a later tick. A stale lease attempts removal but never provisions a replacement. A check after a missed tick is also red even if the scheduler never wakes. Recovery requires stopping the job, confirming the named QA VM is absent, and explicitly acknowledging the failure. Fake command results prove success, overlapping ticks, restart with a stale lease, missed ticks, failed creation, API, sweep, copy, timeout and cleanup; no job is registered by the Builder. Principles: P2, P5.
