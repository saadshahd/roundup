# Loop rules

Module: `loop/rules.sh`, `loop/runs.sh`, `loop/retro.sh`, `loop/status.sh`, `loop/percy.sh` for L36, and the workflows each id names. Each id's cases are its `L<n>` tests in `loop/rules.test.sh`, `loop/merge-ready.test.sh`, `loop/percy.test.sh`, `loop/runs.test.sh`, `loop/retro.test.sh` and `loop/status.test.sh`.

| Exit | Means |
|---|---|
| 0 | holds |
| 1 | a rule is broken; stderr names it |
| 2 | bad input or usage, before any network call |
| 4 | `gh`, `git` or Jev failed, or `gh` exceeded `LOOP_GH_TIMEOUT` (20 s, fractions allowed); never read as a pass |

**L2 authorship.** `ci-trailers <pr>` passes when every commit carries `Author-Agent`, except a clean merge of `main` (L54) or a Copilot Autofix commit (L37), and no commit carries `Reviewed-by-Agent`: an approval is a verdict comment.

**L3 vocabulary.** `vocab` fails naming the word when a public Rust item, TS export or `contracts/` name holds a `GLOSSARY.md` _Avoid_ word, except under `crates/agents/claude_code/`.

**L23 Builder runs.** `build.yml` claims ready work Issues on dispatch and every five minutes, with at most four cloud Builders across ticks. Each row runs in `build-row.yml`, and its own completion job releases a Claim with no open PR, records an interrupted draft and dispatches L88 reconciliation without waiting for sibling rows. A dispatch with a PR number uses L88 to repair current conflicts, rejects, failed checks or interrupted drafts; stale dispatches start no agent. Claims remain atomic and an empty queue ends the chain. A merged PR is not completion evidence: ready spec-only or partial work remains eligible. A retained branch at exactly a merged same-repository PR head can be retired with an exact lease and claimed anew; a changed head cannot. Deleted branches do not suppress ready work. Each claimed row atomically creates its build branch and a unique `loop-row/<slug>` owner ref. Cleanup atomically releases only its own owner ref and deletes an unchanged build branch only without an open PR. An older cleanup cannot remove a new owner, including retries on unchanged main; pushed work is preserved. The owner records its GitHub run (empty for a local controller). Before queueing, reconciliation and the build queue recover cloud owners whose model job or workflow is terminal, including an owner whose build branch was deleted; local recovery stays with the controller that can observe its process. Owner refs without a live Builder remain visible on Status. Merged-head history is paginated. A closed, unmerged PR is not evidence of completion. Builder and Retro runs explicitly request `workflows: write` from the installed Claude App, plus `actions: read` and `checks: read` for CI evidence; the action retains its standard contents/pull-request/Issue publication rights. They request no check, status, administration or Actions write authority. Reviewer runs retain their separate read-only workflow token. Workflow edits remain subject to independent exact-head review and required gates; a publication-permission failure is an engineering blocker, not a product decision. Tests: `PublicationPermissions` in `loop/dispatch.test.py`.

**L24 review.** The reviewer action accepts reconciliation dispatches from `github-actions`, like the Builder action. `check` skips a draft's heads, so a Builder's red pushes hold no macOS runner, and runs on push to `main`. After `check` succeeds on a same-repo PR head, `runs.sh review-due <pr> <head>` exits 0 and prints the review run's task only when the PR is open at that head, is not a draft, has no verdict covering the head; else 1 naming why, and 4 on a `gh` failure. The task holds the body's `Scenarios:`, `Moves:` and `macOS:` lines, for `apps/desktop/src/`, `percy-review` on the head's Percy build (`percy.sh build <sha>`, waiting up to 10 minutes; none is a `NOTE`, a Percy API failure exits 4) against the scenarios' then-clauses and the `Moves:` checks, never the author's intent, and earlier verdicts; never the rest of the body. The review run is a Builder run, `.agents/builder.md` byte for byte and then the task, on Opus with a read-only token, answering `{verdict, findings}`. Its checkout of the head holds `main`'s `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.agents/` and `loop/` in place of the head's, and no other `CLAUDE.md` or `AGENTS.md`, so no PR instructs its own review; it reads the PR's changes to them through `gh pr diff`. `runs.sh verdict` posts the answer as `VERDICT:`, `Head:`, the findings and `Reviewed-by-Agent: reviewer-<run id>`, drops any findings line that would forge one of those fields, dispatches merge-ready, and on a first reject starts a fix run (L82). A review run that ends with no verdict runs once more on that head, counted by one comment marked `<!-- review-rerun <head> -->`; a second with none stops the PR (L81).

**L27 retro.** `retro.yml` runs daily. `retro.sh due` exits 0 when 20 PRs merged since the last merged `retro/` PR (or since `loop/retro.sh` was committed) and no `retro/` PR is open, else 1 naming the count. `report` prints the Retro's input: merged PRs by kind (product touches code, loop touches loop machinery, the rest spec), Ledger runs, failures, turns and weighted tokens by role and model (input 1, cache write 1.25, cache read 0.1, output 5), weighted tokens per merged product PR, each reject of a product PR classified, each PR whose verdicts it could not read, and the five costliest runs. `classify` asks Jev (`jev-1.13.0`) two Choices per reject, its kind (real defect, wording, process rule) and its failure class, each time with the options in a fresh random order, and prints each choice with its confidence; a Jev failure or an answer without choices exits 4. The Retro opens one PR on a `retro/` branch; it merges after independent review and required checks.

**L29 ledger.** Every Builder, Reviewer and Retro run, finished or not, leaves the artifact `ledger-<run id>-<attempt>-<role>-<slug>` holding one row `{role, subject, run, model, turns, exit, input, output, cache_write, cache_read, usage}` written by `main`'s `retro.sh ledger`: from the run's `result` entry, else from its assistant messages, each message id once; missing execution output reads `missing-output`, not proof the model never ran. `usage` is `recorded` when all token fields are present, `partial` when only some are present, and `unavailable` when none are present; actual zero is recorded. The action also outputs the run's final model explanation, labelled a model claim, with its result subtype and explicit missing/truncated indicators, for the completion job's end entry (L92); the artifact holds no explanation. Configured credentials and recognized credential formats are redacted before an 8000-character bound; raw transcripts and tool outputs are not retained or printed. Both the artifact action definition and extraction scripts come from main, including on old repair branches. Every configured model-visible credential reaches redaction; malformed output fails visibly. Tests: `loop/outcome.test.py` and the action extraction case in `loop/retro.test.sh`.

**L33 base.** `base <pr>` passes only when the PR's base is `main`.

**L34 Issue queue.** Work orders are GitHub Issues labelled `loop:work`, in the format of `.agents/data/work.md`. `ready` reads all pages and prints each Issue and its derived state; `--json` exposes structured records. Existing same-repository open `build/<Key>` PRs, or PRs explicitly naming the Issue with Refs/Closes/Fixes/Resolves, are in flight. An open Issue with `ready-for-agent` is ready only when every native blocked-by dependency is closed as completed; cancelled dependencies still block. Missing intake approval is unspecified. Invalid fields, duplicate Keys and dependency cycles block visibly. API errors or timeouts exit 4, never an empty queue. Test names and file tables have no scheduling or completion authority. A specification Issue may introduce its named scenario; an implementation task refuses an absent file or scenario heading. Provider selection uses the same Claims and capacity, allowing Codex-reserved work to wait for Codex instead of being consumed by Claude. Tests: `loop/orders.test.py`.

**L36 Percy build.** On every PR touching `apps/desktop/src/`, and on each such push to `main` as Percy's baseline, the `visual` workflow's `percy` job (`percy.sh snapshot`) pins the build's commit to the PR head (`PERCY_COMMIT`), so L24 finds it by that SHA, serves `just harness` and runs `percy snapshot` on each seed of `.agents/data/harness.md` at 1280 px wide in Chrome only; it fails without `PERCY_TOKEN`, when the harness never answers, when Percy fails, or when its output has no build link, and writes that link to the job summary.

**L37 Copilot attribution.** A commit with no `Author-Agent` is authored by `copilot` when it has the Copilot Autofix `Co-authored-by` trailer, GitHub committed it, and its signature verifies against GitHub's web-flow key in `loop/web-flow.asc` and no other key; anything short of all three still needs `Author-Agent`, and `copilot` can never be the approver.

**L42 delta.** `delta <base-dir> <head-dir>` prints `<step> <id> fixed|regressed|still-failing|still-passing` per check and fails on any `regressed`; a check missing on one side is exit 2, never a pass.

**L46 merge-ready.** `merge-ready <pr>` prints `ready <head SHA>` only when the PR is open, not a draft and based on `main`; `check` and `rules`, and `percy` for `apps/desktop/src/`, passed on that exact head, where a skipped run counts for nothing; every commit passes L2; no reject blocks the head; a `VERDICT: approve` names the head, or an ancestor followed only by clean merges of `main` (L54); and a Code or Loop PR has a `Scenarios:` line. A Code PR (`apps/`, `crates/`, `contracts/` or a Build file: `justfile`, a Cargo or pnpm manifest or lockfile, `rust-toolchain.toml`, `tsconfig.json`, `.oxlintrc.json`, `.fallowrc.json`, `.cargo/`, `tools/`) or Loop PR requires an independent current-head approval. A `crates/desktop/` PR needs a `macOS:` line. A verdict counts only from `github-actions[bot]` or a commenter with write access, and never from an author.

**L54 clean merge.** `clean-merge <commit>` passes for a merge of `main` that conflicts nowhere and changes nothing beyond the trial merge; such a merge needs no `Author-Agent`, and an approve of its first parent still covers it, so a human can merge `main` in from GitHub.

**L78 auto-merge.** Loop paths, including `.github/`, retain auto-merge and pass the same required checks plus independent current-head approval. A ready Loop-only PR is dispatched for review. Main’s instructions and skills are installed before the reviewer reads the proposed diff. Historical rejects never veto a corrected, independently approved head.

**L79 needs the user.** When any line of `merge-ready <pr>`'s output holds a reason only the user clears (a missing `macOS:` line), the merge-ready workflow labels the PR `flag:needs-user`, assigns the repository owner and keeps one comment, marked `<!-- needs-user -->`, asking each reason as a question; a later run edits that comment only when its questions change. A run with none of those reasons takes the label and the owner off and leaves other labels and assignees alone. On a draft or closed PR only L81's reason counts.

**L80 status.** `status.yml` runs every five minutes and on dispatch, with a separate daily report. Workflow-run events do not start full Status scans. An active scan finishes; pending refreshes coalesce without cancelling it. Motivation: 100 Status runs in under three minutes produced 98 cancellations and exhausted the installation API allowance. `status.sh issue` prints the number of the Status issue, the one open issue labelled `loop:status`; none or two exit 1. `status.sh page` prints its body: a marker, the time, and one table row each for Merged (PRs merged since 00:00 UTC and over 7 days), Tokens per merged product PR, Needs you (each open PR labelled `flag:needs-user`, with the questions of merge-ready's `<!-- needs-user -->` comment, L79), Blocked (each open PR, neither a draft nor labelled `flag:needs-user`, whose `merge-ready` status is not success and which nothing updated for 6 hours, with that status's description) Running / queued (active jobs with direct run links, and L82 diagnostic eligibility and retry times) and Watch (a `main` whose last push `check` did not succeed; a Claim with no open PR or exact merged head and no Builder job; failed, timed-out or unstarted `build`, `review` and `retro` runs of the last 24 hours, per workflow); an empty row reads `nothing`. A missing Ledger displays unavailable, never zero. Small nonzero token totals remain visible. Recorded weighted tokens per product PR are a lower bound with the product-PR denominator, usage-record count and partial-coverage label; they exclude unrecorded runs and local sessions and are not a monetary bill. Only `page --cost` counts tokens, by `retro.sh cost <since>` over 7 days with L27's weights and kinds; without it the page keeps the Tokens row of the previous body on stdin. The workflow writes the page as the issue's body, which notifies no one; at 08:03 UTC, or on dispatch with `daily`, it counts the tokens and also posts the page as one comment, which notifies the user the issue is assigned to. A `gh` or `git` failure exits 4 and leaves the body as it was.

**L81 stopped.** A Builder that stops on a product question leaves a draft with `Stopped: <the question>`, its consequence and a recommendation; merge-ready asks that question (L79). After a Builder or fix run ends, `runs.sh stopped <branch>…` gives an open draft with no Stopped line a marker naming the interrupted run and dispatches merge-ready. That interrupted-run marker triggers L88 repair without a needs-user notification. Ready PRs and explicit questions are left alone. The trusted completion job then observes GitHub: a draft or absent delivery exits 1 even when the model exited successfully; a ready PR reports that independent review and required gates still apply. A repair may observe its explicitly identified PR merged; historical merged PRs on a reused Builder branch cannot satisfy a new run. The observation names the actual head, claims no authorship and never grants approval or changes that head. Observation failure exits 4. The final explanation is posted to the Issue's Trail (L92). Tests: `loop/outcome.test.py`. A spent repair budget is visible on Status with the last run link; it is an engineering investigation, not a new product question. GitHub failures exit 4.

**L82 fix runs.** A PR gets two ordinary repair attempts, then diagnostic repair: inspect prior run logs and the Issue's Trail (L92), distinguish code, cancelled CI, setup/authentication and publication failure, and post the observed cause and changed approach as the `Changed:` entry before editing. Do not invent missing evidence. Reproduce and verify a bounded correction; a shared engineering blocker gets one linked, specified work Issue, not a user product question. At most six started model repairs fit in any rolling 24 hours across causes, heads and intervening reviews. After the third repair, an unchanged head and cause waits 15 minutes, doubling on further unchanged failures up to two hours; progress may remove that delay, never the rolling limit. Expired budget becomes eligible automatically on reconciliation. Legacy Claims retain their count, conservatively dated at their last owner; history and lifetime count survive reviews. Setup failure spends no model attempt and waits five minutes across changed heads too. A completed non-skipped model action is conservatively charged when more precise evidence is unavailable. Status names diagnostic eligibility or the next retry time with the last run link; eligibility is not a live owner.

Cancelled required Rust/web CI with no failed test lane is rerun by the trusted controller, at most twice per head across intervening reviews/repairs, without invoking a model or charging repair budget. A failed test lane still requires repair; running lanes wait. Persistent cancellation becomes diagnostic engineering repair. The same atomic per-PR Claim owns reruns, review and repair; reserve reruns before the mutation so an uncertain response cannot create unlimited reruns. Main's setup action configures repair runners even when the PR predates the Linux migration. Earlier rejects never veto a corrected head, and no retry bypasses required checks or independent approval. Tests: `loop/dispatch.test.py`; observer: cancelled-CI rerun without a model, diagnostic dispatch of a formerly exhausted PR, and its retained result.

**L83 spend cap.** The repository variable `LOOP_DAILY_TOKENS` caps recorded weighted tokens (L27's weights) over the last 24 hours; this is a lower bound, not a provider quota guarantee. `retro.sh spent` reads the last 24 hours of Ledger artifacts, including legacy names, and prints the rounded-up recorded weighted sum. Immutable artifact downloads are cached between trusted controller runs. Feedback controllers allow a cold scan up to ten minutes; a timeout fails closed before dispatch or ownership. Partial coverage is reported on stderr; entirely unavailable usage fails instead of becoming zero; `gh` failing exits 4, and the variable unset or no number exits 2, so nothing builds uncapped. While the sum is at or above the cap, `runs.sh queue` claims no row and the Status issue's Watch row says `spend cap reached: <sum> of <cap>`. Fix and review runs of open PRs still run, so no open PR waits on the cap.

**L84 Linux Builders.** Build and fix runs move to `ubuntu-latest` once a push to `main` passes `just check` there. `.github/actions/setup` installs Tauri's Linux packages (`libwebkit2gtk-4.1-dev`, `build-essential`, `libxdo-dev`, `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`) on Linux and GNU coreutils on macOS, and keys the Rust cache by the runner's OS. Each push to `main` also runs `just check` on `ubuntu-latest`, which saves the Linux cache; when it fails, the Status issue's Watch row says so. `check` on a PR stays on `macos-latest`, where the App ships, so no Linux green merges alone.

**L85 Issue time.** Status adds median and p90 hours over work Issues delivered in the last seven days, from the first `ready-for-agent` label event to the merge of their closing implementation PR. Report evidence coverage and missing timestamps; missing observations never count as zero.

**L82 pipefail.** Every workflow under `.github/workflows/` sets `defaults.run.shell: bash`, so GitHub runs each `run` step under `bash -eo pipefail` and a failing command left of a pipe fails the step.

**L86 journey priority.** GitHub work Issues hold a numeric Priority from 0 (first) to 100 (last). Eligible Issues sort by Priority then Issue number before capacity limits apply. Native dependencies, an open PR, a Claim and occupied slots are never overridden. `.agents/data/journey.md` retains the goal and required rendered/behavioral evidence, not a duplicate priority list. Each Builder completion independently releases ownership and reconciles without waiting for siblings. Tests: `loop/orders.test.py` and `loop/runs.test.sh`.

**L87 Codex Builder.** When `LOOP_CODEX_ENABLED=true`, one local Codex service adds a fifth Builder slot alongside the four GitHub Claude Builders. The service checks every five minutes, takes at most one eligible row through L23's queue and atomic Claim, and uses the same Builder prompt, journey priorities and PR gates. It asks L23 for a maximum of five, takes only its first eligible row, and waits if five GitHub Builders are already running. A local file lock prevents overlapping ticks; a recorded interrupted run is recovered before another Claim, matching both PID and creation time and enforcing its deadline. The controller uses its own clean checkout of main and each Attempt its own clone; no user worktree changes. Login must be ChatGPT; Codex inherits only runtime paths and locale, no API-key or GitHub credentials through its environment, user config or executable approval rules. Only the controller commits, pushes and opens the PR from the structured result. A partial implementation after timeout goes to the existing Claude fix run; an unresolved question is a draft with `Stopped:` and merge-ready dispatched; if no files changed, post the question on its Issue and remove its intake label without modifying the acceptance specification. Each run ends within two hours, preserves its output and token counts locally, and succeeds only with a ready PR. A failure retains a PR or releases its Claim, makes at most two attempts per row and main SHA, and waits an hour between failures. API failures remain failures. An expired login, sleeping Mac or disabled service leaves Claude’s four slots running; disabling the variable prevents the next local Attempt. `LOOP_CODEX_STATUS` records its last timestamp, row and result on the Status issue; a running record expires after the run deadline. Tests: `loop/codex.test.sh`. Codex token counts are separate from the GitHub artifact Ledger and do not imply plan quota remaining. Interrupted engineering drafts carry L81’s generic marker; after publishing released ownership, completion and crash recovery dispatch L88 reconciliation.

**L88 prompt ownership and recovery.** A reconciliation runs on work/feedback Issue and PR changes (Status bookkeeping Issues are excluded), main pushes, completed check/loop/build/review/visual runs and every five minutes. It dispatches review for an open ready same-repository Code or Loop PR with successful exact-head check, rules and (for UI) percy jobs and no current verdict; a merge conflict, current reject, failed check or interrupted draft on a `build/` branch dispatches repair. Other branches remain under their author’s control. Initial Builders and live local Codex Claims keep ownership until they finish. Every review and repair acquires the same durable per-PR Claim before invoking a model. A non-force ref update permits one owner; duplicate or stale dispatches invoke no agent. A completed owner permits L82’s bounded repair and CI recovery, and at most two review attempts per head; preflight/setup failures do not spend that budget. A stale reviewer posts no verdict on a newer head. Builder checkouts install a prepare-commit-msg hook from main that supplies a missing Author-Agent trailer and preserves existing attribution; rules failures are repaired before review, so metadata omissions do not spend review rejects. Earlier rejects do not block reviewing a corrected head; explicit product questions retain their existing gates. Conflicts merge main without force-pushing. Each Builder row reconciles at completion without waiting for its matrix siblings; reconciliation refills free build slots; empty queues do not continue the dispatch chain. Interrupted-run markers trigger repair without asking the user; explicit product questions retain the needs-user path. The Status issue links running and queued jobs and names diagnostic eligibility and retry times. A GitHub failure prints GitHub's own message with credentials redacted and exits 4. Tests: `loop/dispatch.test.py`.

A successful repair that leaves a ready PR requests independent review of that exact head and blocking verdict, even without a new commit. The request survives reviewer setup retries, but a different head or new/edited reject invalidates it. Failed/interrupted model runs and drafts cannot request review this way. Required CI still precedes review, the shared Claim admits one owner, and the old reject still blocks merge until an independent approval supersedes it (L88).

Reconciliation and regular Status refreshes check the authenticated token's REST and GraphQL budgets before a full scan. If either has fewer than 100 calls/points left, the workflow summary names the remaining budget and reset time, skips the scan, and leaves recovery to the next scheduled run. Failed budget reads remain errors, never an empty queue or approval. Daily reports run normally and fail visibly if unavailable; a periodic page refresh cannot replace a daily report. A full Builder queue skips order and PR-history reads; feedback sweeps exclude unclaimed ready work and bot-only Issues before per-Issue ownership reads (L88).

**L89 parallel CI.** `just check` remains the union of `check-rust` and `check-web`. CI runs those recipes concurrently, keeps Rust and the daemon smoke test on macOS, and runs web checks on Linux. The required `check` job succeeds only if both lanes succeed, and a draft invokes neither. Motivation: run 37831870531 spent about 105 seconds in Rust checks followed by 93 seconds in frontend tests. Tests: `loop/dispatch.test.py`; observer: both CI lanes and the final gate on the PR.

**L90 feedback to verified goals.** Prompt step outputs close their delimiter on its own line, including when the task JSON has no trailing newline. A new or substantively edited Issue from a repository owner or collaborator is feedback intake without the user adding a scheduling label. `loop:status`, `loop:work`, bot progress edits and an explicit `loop:report-only` instruction are not new feedback. Preserve the original human text and its revisions on the source Issue. Existing work Issues whose scope or dependencies still need triage are owned planning work; they do not wait indefinitely for the user to add an intake label. A historical sentence saying no implementation was performed is not an instruction to ignore future authorized intake.

A fresh planner inspects current behavior, accepted product/design documents, existing Issues, PRs and live Claims. It derives an observable goal and one bounded next batch of native child work Issues; each has an owner scope, acceptance observer, regressions and real blocked-by dependencies. Reuse owned work. Apply `widen` when a reported case exposes missing rule coverage, then `anchor` to make the resulting rule decidable; retain examples and counterexamples with the proposed rule. A consequential unresolved product choice may ask the user; ordinary design/engineering decisions use the recorded direction. Source feedback, goal, rule changes, delivery Issues and evidence remain linked.

Planning/rule changes require an independent exact-head review before child implementation is authorized. A merged plan lacking that approval publishes no children: reconciliation retains its Claim history and schedules a fresh proposal against current main, carrying the bypassed PR and head as recovery evidence and retaining a verification proposal’s original goals and predecessor; that proposal requires its own exact-head approval. The trusted controller publishes approved plans and scheduling changes; a model cannot approve its own plan or close its own feedback goal. A planning Claim is keyed by Issue, human-feedback revision and phase, with bounded recovery of an ended owner. Native child closure schedules a fresh verification run when it can reveal new evidence. The verifier observes the original goal on current main, retaining command/run/capture evidence and what remains unproved. It closes the parent only when every goal is proved; otherwise it produces the next bounded iteration. A merged child, matching test name, bot comment or green CI is not parent-goal completion. Changed human feedback invalidates stale planning/closure; model progress does not replan unchanged work.

Observer: the runtime tests are `l90_collaborator_feedback`, `l90_untrusted_author`, `l90_duplicate_and_competing_claims`, `l90_report_only`, `l90_bot_update`, `l90_changed_human_feedback`, `l90_reuse_owner`, `l90_reviewed_plan_publication`, `l90_cancelled_dependency`, `l90_independent_goal_verification`, `l90_failed_evidence_successor`, `l90_unreviewed_or_stale_closure`, `l90_refused_plan_recovers_and_the_sweep_continues` and `l90_one_source_failure_leaves_the_others_swept`. Execute one complete real feedback cycle through GitHub Issues and its independent review gates; record the source revision, plan, native children, delivery and verification evidence. Until that observer passes, feedback automation remains incomplete.

**L92 trail.** A work Issue's Trail is its comments marked `<!-- trail <run id> <attempt> -->` from `github-actions[bot]`, `claude[bot]` or a writer (a commenter with write access, as in L46); the marker from anyone else counts for nothing. After every cloud build or fix run, finished, failed, timed out or cancelled, the run's trusted completion job posts one end entry on the Issue the run served (for a fix run, the Issue L34 links to its PR): role, run link, cause (`build` or the cause of an L82 fix run), L81's observed delivery, the head the run left or `none`, the model result subtype and the final explanation, redacted and bounded as L29 requires. When the Issue already has entries, the run posts one `Changed: <what differs from the last attempt>, <the evidence for it>` entry before its first commit; a run that pushed commits without one gets `Changed: none` in its end entry. Build and fix tasks hold the Issue's last six entries, oldest first, and every comment a writer posted since the last end entry; review tasks never hold them (rule 5). After two consecutive end entries with the same cause and delivery and no new head, the next build run is a diagnostic run on the terms of L82 fix runs, and each further unchanged run waits 15 minutes, doubling up to two hours; at most six build runs per Issue start in any rolling 24 hours. A writer's edit of the Issue body or a writer's comment lifts the wait, never the rolling limit; a bot's edit or comment lifts nothing. Status names each waiting Issue with its next eligible time and a link to its last entry. The Trail is the one record of a run's final explanation and of a repair's observed cause and changed approach; the Ledger keeps its row. `retro.sh report` lists each Trail holding two consecutive same-cause entries with no new head, and the Retro answers each with a rule line or a regression test under an L scenario (L27). Codex runs keep L87's local records and post no entries. Failing to read or post an entry exits 4 and shows on Status; no run starts on a Trail it could not read.

Observer: cancel a cloud Builder run after a failed step; the next run's task holds that run's end entry, the next run posts a `Changed:` entry naming new evidence before its first commit, and it does not end with the same cause, delivery and head. Tests: `l92_end_entry_after_cancel`, `l92_untrusted_marker_ignored`, `l92_task_holds_last_six_and_writer_comments`, `l92_review_task_excludes_trail`, `l92_changed_before_commit`, `l92_changed_none`, `l92_repeat_diagnoses_then_waits`, `l92_writer_edit_or_comment_lifts_wait`, `l92_rolling_limit`, `l92_retro_lists_repeats` and `l92_read_failure_exits_4`.


**L93 run explanation.** Every workflow ends with an always-run Actions summary naming its purpose, trigger, job results, failed or skipped work, the run link and the next automatic step. The summary uses supplied job results without a checkout, action download or GitHub API scan. A no-op states that no work ran; success of a controller is not delivery. Agent runs show their bounded, redacted final explanation as a model claim beside independently observed delivery. Reconciliation records dispatch decisions and publication failures; a failed publication terminates only that publication, the sweep checks later feedback, and the run remains failed with each blocked Issue and PR named. Infrastructure/read failures remain errors. Tests: `loop/outcome.test.py`, `loop/feedback.test.py`. Every cycle, including planning and Retro evolution, executes ordinary engineering choices without approach confirmation; only L79/L81 decisions wait for the user (policy).
