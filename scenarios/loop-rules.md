# Loop rules

Module: `loop/rules.sh`, `loop/builder.py`, `loop/orders.py`, `loop/stall.py` for L94, `loop/percy.sh` for L36, and the workflows each id names. Each id's cases are its `L<n>` tests in `loop/rules.test.sh`, `loop/builder.test.py`, `loop/workflows.test.py`, `loop/orders.test.py`, `loop/stall.test.py` and `loop/percy.test.sh`.

| Exit | Means |
|---|---|
| 0 | holds |
| 1 | a rule is broken; stderr names it |
| 2 | bad input or usage, before any network call |
| 4 | `gh` or `git` failed, or `gh` exceeded `LOOP_GH_TIMEOUT` (20 s, fractions allowed); never read as a pass |

**L2 authorship.** `ci-trailers <pr>` passes when every commit carries `Author-Agent`, except a clean merge of `main` (L54) or a Copilot Autofix commit (L37), and no commit carries `Reviewed-by-Agent`: an approval is a verdict comment.

**L3 vocabulary.** `vocab` fails naming the word when a public Rust item, TS export or `contracts/` name holds a `GLOSSARY.md` _Avoid_ word, except under `crates/agents/claude_code/`.

**L23 Builder runs.** `build.yml` runs when `check` ends on `main` (claude-code-action rejects push events), hourly, on dispatch, and when an Issue adds work: a new or reopened Issue from the user (`saadshahd`) or a loop App, or a removed `flag:needs-user`. Its `pick` job runs one at a time: `builder.py pick` first starts a fix run (L82) for each open same-repository `build/` PR that conflicts with `main`, failed `check`, `rules` or `review` on its head, or stayed a draft with no `Stopped:` line for three hours; then it takes L34's ready rows that no queued or running `build #<issue> / build` job holds, in Priority order, until sixteen build jobs hold Issues. Each row calls `build-issue.yml`, whose `build` job runs one job per Issue at a time, on Sonnet, for at most two hours. `orders.py task` checks the Issue again before any model call; a refusal (exit 3) ends the job with no run and no strike. The prompt is `.agents/builder.md` byte for byte, a `## Task` heading, then the task, its delimiter on its own line even when the task has no trailing newline. A run worked when its model used a tool, read from the action's execution file; a usage limit or setup failure is a run that did not work and records nothing. After a run that worked, `builder.py built` hands an open `build/<Key>` PR to L81; with none, it reads the Issue. One a person closed, one closed after its `build/<Key>` PR merged, one whose Key starts `stall-` (L94 closes it on any merge), or one a dependency, PR or `flag:needs-user` holds, records nothing; one a bot closed without such a PR reopens and is struck. One still ready gets a `<!-- strike -->` comment linking the run, and so does the Issue of a Builder PR that used its three fix runs (L82), linking that PR; the third strike in 24 hours labels it `flag:needs-user` (L79), which holds it until the user removes the label. Each Issue's own `after` job in `build-issue.yml` runs `builder.py built` as soon as that Issue's build job ends, and when its model worked dispatches `build.yml` on `main` with its workflow token, so a freed slot fills without waiting on the run's other jobs, the next merge or the hour; a job whose model did not work dispatches nothing, so a usage limit ends the chain. Build and fix runs request `workflows: write` from the installed Claude App, plus `actions: read` and `checks: read` for CI evidence; the action keeps its standard contents, pull-request and Issue publication rights. They request no check, status, administration or Actions write authority. Review runs keep their separate read-only workflow token. Builder checkouts install a prepare-commit-msg hook from `main` (`author.sh`) that supplies a missing `Author-Agent` trailer and keeps existing attribution. A build run reads every comment on its Issue starting `<!-- fix-exhausted` as an approach already tried (`.agents/builder.md`) and takes another (policy). Tests: `l23` in `loop/builder.test.py` and `loop/workflows.test.py`.

**L24 review.** `check` skips a draft's heads, so a Builder's red pushes hold no macOS runner, and runs on push to `main`. When `check` succeeds on a same-repository PR head, `review.yml` runs from `main`'s definition, so no PR edits its own review; a newer head of the branch cancels an older head's review. `builder.py review-task <pr> <head>` prints the review run's task only when the PR is open at that head and not a draft, else exits 3 and no model starts. The task holds the body's `Scenarios:`, `Moves:` and `macOS:` lines; for `apps/desktop/src/`, `percy-review` on the head's Percy build (`percy.sh build <sha>`, waiting up to 10 minutes; none is a `NOTE`, a Percy API failure exits 4) against the scenarios' then-clauses and the `Moves:` checks, never the author's intent; and earlier verdicts; never the rest of the body. The review run is a Builder run, `.agents/builder.md` byte for byte and then the task, on Opus with a read-only token, answering `{verdict, findings}`. Its checkout of the head holds `main`'s `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.agents/` and `loop/` in place of the head's, and no other `CLAUDE.md` or `AGENTS.md`, so no PR instructs its own review; it reads the PR's changes to them through `gh pr diff`. `builder.py review-post` posts the answer as `VERDICT:`, `Head:`, the findings and `Reviewed-by-Agent: reviewer-<run id>`, drops any findings line that would forge one of those fields, and sets the commit status `review` on the head: `success` for approve, `failure` for reject. A reject on a `build/` PR starts a fix run (L82). A head that moved since posts nothing. A run whose model used no tool (L23) leaves `review` pending; each `pick` reruns that review run once it has ended, and after six attempts asks the user (L79) instead. A run that worked with no verdict sets `review` to `error`, asks the user and fails. Tests: `l24` in `loop/builder.test.py` and `loop/workflows.test.py`.

**L33 base.** `base <pr>` passes only when the PR's base is `main`.

**L34 Issue queue.** Work orders are open GitHub Issues, in the format of `.agents/data/work.md`, that the user (`saadshahd`) or a loop App (`claude[bot]` for a Builder's prerequisite, `github-actions[bot]` for a stall Issue) filed. Anyone else's Issue, a collaborator's included, is unspecified and never runs whatever its labels, since the repository is public. `orders.py ready` reads all pages and prints each Issue and its derived state; `--json` exposes structured records. Existing same-repository open `build/<Key>` PRs, or PRs explicitly naming the Issue with Refs/Closes/Fixes/Resolves, are in flight. An open work order is ready only when every native blocked-by dependency is closed as completed and it lacks `flag:needs-user` (L79), which holds it unless its Key starts `stall-`; cancelled dependencies still block. No intake label is needed. Invalid fields, duplicate Keys and dependency cycles block visibly. API errors or timeouts exit 4, never an empty queue. Test names and file tables have no scheduling or completion authority. A specification Issue may introduce its named scenario. An implementation Issue whose Specification file or a named scenario heading is absent from the checkout, or whose Scenarios line names no ID, runs as Mode `specify` first: its task asks for the scenarios and an Issue that names their IDs and keeps Mode `implement`, so the queue implements it once they merge. An Issue with no `Key:` line is a request, such as a bug report: Mode `specify`, Key `issue-<n>`, Priority 50, so a Builder specifies it before the queue builds it. Tests: `loop/orders.test.py`.

**L36 Percy build.** The `visual` workflow's `percy` job reports on every PR, so it can be required, and passes at once when the PR changes nothing under `apps/desktop/src/`. On a PR that does, and on each such push to `main` as Percy's baseline, it runs `percy.sh snapshot`, which pins the build's commit to the PR head (`PERCY_COMMIT`), so L24 finds it by that SHA, serves `just harness` and runs `percy snapshot` on each seed of `.agents/data/harness.md` at 1280 px wide in Chrome only; it fails without `PERCY_TOKEN`, when the harness never answers, when Percy fails, or when its output has no build link, and writes that link to the job summary.

**L37 Copilot attribution.** A commit with no `Author-Agent` is authored by `copilot` when it has the Copilot Autofix `Co-authored-by` trailer, GitHub committed it, and its signature verifies against GitHub's web-flow key in `loop/web-flow.asc` and no other key; anything short of all three still needs `Author-Agent`, and `copilot` can never be the approver.

**L41 tokens.** `tokens` scans every `.css` file and every `.ts` and `.tsx` file under `apps/desktop/src/` except `tokens.css`, `terminal/emulator.ts` and test files (`*.test.*`, `testing/`), and fails naming `<file>:<line> <property>` for each look literal. A look literal is a value that sets one of these without `var(--…)`: a colour (`color`, `background`, `background-color`, `border*`, `outline*`, `fill`, `stroke`, `caret-color`, `text-decoration-color`) holding a `#` hex, an `rgb(`, `rgba(`, `hsl(`, `hsla(`, `oklch(`, `color-mix(` or a bare colour name other than `transparent`, `inherit`, `currentColor`, `none`, `initial` or `unset`; a `font-size` or `border-radius` holding a number with a unit; a `box-shadow` other than `none`; or a `transition*` or `animation*` duration holding a number with `ms` or `s` other than `0s`. In a `.ts` or `.tsx` file only the text of `style={{…}}` objects is read, where `fontSize`, `borderRadius`, `boxShadow`, `color`, `background`, `backgroundColor` and `borderColor` hold the same values. A comment is not read. Exit 0 and no output when nothing is found, 1 with one line per literal, 2 with an argument. Tests (`l41_`, in `loop/rules.test.sh`, on a temporary tree whose `apps/desktop/src/` the script reads from `$PWD` the way `vocab` reads its tree): `l41_a_hex_colour_fails_naming_file_line_and_property`; `l41_rgba_hsl_and_a_bare_colour_name_fail`; `l41_a_unit_font_size_and_radius_fail`; `l41_a_box_shadow_and_a_duration_fail`; `l41_var_reads_pass`; `l41_transparent_inherit_currentcolor_none_and_0s_pass`; `l41_tokens_css_is_not_read`; `l41_emulator_ts_and_test_files_are_not_read`; `l41_an_inline_style_literal_fails_and_a_var_passes`; `l41_a_literal_in_a_comment_passes`; `l41_an_argument_exits_2`. `u130_` (`scenarios/ui-visual.md`) adds the `tokens` step to `.github/workflows/loop.yml` in the PR that leaves no literal.

**L42 delta.** `delta <base-dir> <head-dir>` prints `<step> <id> fixed|regressed|still-failing|still-passing` per check and fails on any `regressed`; a check missing on one side is exit 2, never a pass.

**L46 merge gates.** GitHub auto-merge merges a PR once ruleset `main-2` sees `check`, `rules`, `review`, `percy` and `macos-line` succeed on its head, each pinned to GitHub Actions, so no other app or person can post them; the ruleset has no bypass (policy). A Builder that leaves a ready PR arms auto-merge. `macos-line` runs `main`'s `builder.py macos-line <pr>` on every PR open, edit, push, reopen and ready: a ready PR that changes `crates/desktop/` with no `macOS: <what you saw>` line in its body fails and asks the user (L79); with the line it passes and takes `flag:needs-user` off when that question was the last one asked. A draft passes. Tests: `l46` in `loop/builder.test.py`.

**L54 clean merge.** `clean-merge <commit>` passes for a merge of `main` that conflicts nowhere and changes nothing beyond the trial merge; such a merge needs no `Author-Agent`, and an approve of its first parent still covers it, so a human can merge `main` in from GitHub.

**L79 needs the user.** A PR or Issue waits on the user through the label `flag:needs-user` and one `github-actions[bot]` comment marked `<!-- needs-user -->` saying what to decide; `builder.py` and `stall.py` (L94) add both once and ask nothing more while the label is on. Six things ask: (1) a draft with a `Stopped:` line (L81), (2) a build run that left a product question on its Issue, which labels it and comments itself (`.agents/data/work.md`), (3) a third build strike in 24 hours (L23), (4) a review run with no verdict or six that did no model work (L24), (5) a missing `macOS:` line (L46) and (6) a six-hour stall (L94). Open items labelled `flag:needs-user` are the whole list; the queue builds none of those Issues but a stall Issue (L34), and removing the label returns an Issue to the queue and starts a pick (L23). Only `macos-line` and `stall.py` (when a merge lands, L94) take their own label off; the user takes off the others. Every run executes ordinary engineering choices without approach confirmation; only these reasons wait for the user (policy).

**L81 stopped.** A Builder that stops on a product question leaves a draft with `Stopped: <the question>`, its consequence and a recommendation; after the run, `builder.py` asks the user (L79). After a build or fix run that worked (L23), a draft without a `Stopped:` line gets an `unfinished` fix run (L82), and so does one no run touched for three hours. A ready PR goes on to `check` and review. Tests: `l81` in `loop/builder.test.py`.

**L82 fix runs.** `fix.yml` runs from `main`'s definition when `check` or `loop` fails on a same-repository `build/` PR, and on dispatch with a PR, its head and a cause: `check`, `rules`, `review` (a reject), `conflict` or `unfinished`. One fix run per PR runs at a time. `builder.py fix-task` prints the task only when the PR is open at that head on a `build/` branch, else exits 3 and no model starts; the task names the cause, where the failed run's log is, the last verdict for a reject, and how the run ends. A fix run that worked posts a `<!-- fix-attempt -->` comment on the PR; with three there, the next cause starts no run and hands the PR to its Issue instead: `builder.py` posts one comment on the PR's work Issue marked `<!-- fix-exhausted #<pr> -->` holding the PR link, a line per cause (`check`, `rules`, `review`, `conflict` or `unfinished`) with its failing check or the review finding, and what each fix run changed (its commit subjects), then closes the PR unmerged, deletes `build/<Key>` and strikes the Issue as L23 does. It posts, closes and strikes once per PR, so a repeat of the cause adds nothing, and it sets no `flag:needs-user`. The closed PR keeps its diff at its link and in `refs/pull/<pr>/head`, and the comment names the head commit. The closed PR leaves the Issue with no open `build/<Key>` PR, so L34's ready row starts at most one fresh build run from `main` (L23; policy, as `pick` holds one job per Issue); the Issue stays ready unless the strike is its third in 24 hours. The close, the branch deletion and the strike bypass no required check or review status: nothing merges. The fix run pushes with the Claude App's token, so its push starts `check` and then review again. No retry bypasses a required check or the review status. Tests: `l82` in `loop/builder.test.py`: a fourth cause makes the comment, closes the PR, deletes the branch and strikes the Issue with no `flag:needs-user`, and a repeat does nothing more; the third strike in 24 hours still asks the user (`l23`).

**L84 Linux Builders.** Build and fix runs move to `ubuntu-latest` once a push to `main` passes `just check` there. `.github/actions/setup` installs Tauri's Linux packages (`libwebkit2gtk-4.1-dev`, `build-essential`, `libxdo-dev`, `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`) on Linux and GNU coreutils on macOS, and keys the Rust cache by the runner's OS. Each push to `main` also runs `just check` on `ubuntu-latest`, which saves the Linux cache. `check` on a PR stays on `macos-latest`, where the App ships, so no Linux green merges alone.

**L82 pipefail.** Every workflow under `.github/workflows/` sets `defaults.run.shell: bash`, so GitHub runs each `run` step under `bash -eo pipefail` and a failing command left of a pipe fails the step.

**L86 journey priority.** GitHub work Issues hold a numeric Priority from 0 (first) to 100 (last). Eligible Issues sort by Priority then Issue number before capacity limits apply. Native dependencies, an open PR and a running build job are never overridden. `.agents/data/journey.md` retains the goal and required rendered/behavioral evidence, not a duplicate priority list. Tests: `loop/orders.test.py` and `loop/builder.test.py`.

**L89 parallel CI.** `just check` remains the union of `check-rust` and `check-web`. CI runs those recipes concurrently, keeps Rust and the daemon smoke test on macOS, and runs web checks on Linux. The required `check` job succeeds only if both lanes succeed, and a draft invokes neither. Motivation: run 37831870531 spent about 105 seconds in Rust checks followed by 93 seconds in frontend tests. Tests: `loop/workflows.test.py`; observer: both CI lanes and the final gate on the PR.

**L93 run explanation.** Every workflow ends with an always-run Actions summary (`summary.yml`) naming its purpose, trigger, job results, the run link and the next automatic step, from the supplied job results without a checkout or GitHub API call. A run whose agent jobs all skipped says no agent work ran; a green workflow is not delivery (policy).

**L94 stall.** `stall.yml` runs `loop/stall.py` from `main` hourly and on dispatch. It calls no model, does not depend on `build.yml`, and holds `issues: write` and `contents: read` and `pull-requests: read` and `actions: read` and nothing else. Work waits when an open work Issue (L34) other than a stall Issue, or an open same-repository `build/` PR, lacks `flag:needs-user`. A stall is work waiting while no PR merged to `main` in the last 3 hours. The script exits 0 whether or not a stall exists, and 4 when `gh` fails, never reading that as no stall.
- *No work waits.* Nothing is opened or commented, however long `main` has been quiet (`l94_no_issue_when_no_work_waits`). A stall Issue open when this holds stays open until a merge (`l94_no_work_leaves_an_open_stall_open`).
- *A stall, none open.* It opens one Issue labelled `loop:work` with `Scenarios: L94`, `Specification: [scenarios/loop-rules.md](https://github.com/saadshahd/roundup/blob/main/scenarios/loop-rules.md)`, `Key: stall-<yyyymmdd-hh>` (UTC), `Priority: 0` and `Mode: implement`, so `orders.py ready` classifies it ready (L34) and a build run repairs the loop, never specifies (`l94_first_stall_opens_one_implement_issue`, which asserts that classification). Its body lists the last merge (PR, time), each waiting Issue and PR, and every build, fix and review run since that merge with its workflow, link, result and, for a run that ended on a usage limit or did no model work (L23), that cause (`l94_body_lists_merge_waiting_work_and_runs`).
- *A stall, one open.* The next hourly run comments on that Issue with the same lists and opens no second Issue, so at most one open `loop:work` Issue has a Key starting `stall-` (`l94_next_run_comments_not_a_second_issue`).
- *Six hours.* When the last merge is 6 hours old or more, the Issue gets `flag:needs-user` and one `<!-- needs-user -->` comment naming the stall, its age and the failing runs, and asks nothing more while the label is on (L79; `l94_six_hours_asks_the_user_once`). Before 6 hours it sets no `flag:needs-user` (`l94_before_six_hours_does_not_ask`).
- *A merge lands.* The first run after a PR merges to `main` since the Issue opened closes it as completed with a comment naming that PR, and removes `flag:needs-user` (`l94_first_run_after_a_merge_closes_the_issue`). A merge from before the Issue opened never closes it.
- *Independence.* The workflow file names no `build.yml`, `claude-code-action` or model, and its token grants are those above (`l94_workflow_calls_no_model_and_holds_only_issue_writes`).

Tests: `l94` in `loop/stall.test.py` against a fake `gh`, and `loop/workflows.test.py` for the last clause.
