# Todos and Pads over MCP

ADR 0007: the Daemon serves MCP to Agents through a stdio shim, so every call is a Touch by the calling Agent. The shim is `rup mcp <agent-id>` in `crates/rup`. Build it on the official Rust MCP SDK (`rmcp`), not a hand-rolled protocol. Tests start the built `rup` (`CARGO_BIN_EXE_rup`) against an in-process Daemon on a temp socket, as `crates/rup/tests/ping.rs` does, and speak MCP to it over stdio. No `claude` is involved, except M4's VM run.

**M1 tools.** Given `rup mcp <agent-id>` started on stdio with a Daemon answering at `RUPD_SOCKET`, when an MCP client initializes and lists tools, then the server is named `roundup` and offers one tool for each of these methods: `todo.create`, `todo.get`, `todo.list`, `todo.update`, `todo.complete`, `todo.setBlockers`, `pad.create`, `pad.read`, `pad.list`, `pad.write`, `pad.append`, `pad.setOwner`, `pad.delete`. Each tool is named after its method with the dot replaced by `_` (`todo_setBlockers`). Each input schema is derived from the method's params type in `crates/contracts`, and none is written by hand. `todo.list` and `pad.list` take `null` params, so their schema is `{"type": "object"}`, and the shim sends `null` to the Daemon. Three methods are not offered. `todo.delete`: a Todo has no owner to guard its deletion. `pad.export`: it writes outside the Project. `pad.setStorage`: storage is the user's Project setting.

**M2 a call is a Touch by that Agent.** When the client calls `todo_create {title: "x"}`, then the Todo exists, its `wrote` Touch has actor `{kind: agent, id: <agent-id>, parent: null}`, and the tool result's text is the method's JSON result. A Daemon error, such as `pad_write` on a Pad another Agent owns, comes back as a tool result with `isError: true`. Its text is the Daemon's error as JSON, `{code, message}` (`-32002` is `FORBIDDEN`). The shim maps no code to a name, so it needs nothing new in `crates/rpc`. After such an error the server keeps serving.

**M3 no Daemon, no hang.** When no Daemon answers at start, `rup mcp` exits non-zero with one stderr line naming the socket path. When the Daemon goes away later, the next call makes it exit non-zero; it never waits forever. Claude Code then reports the server as failed instead of hanging a turn.

**M4 the tool list is accepted by the real client.** Given `rup mcp <agent-id>` and the interactive Claude Code 2.1.288 as the client (the user's, read with `claude --version`), when `/mcp` reconnects to the `roundup` server and the client lists tools, then the reply passes the client's check and the Agent's `mcp__roundup__*` tools appear. Observed on that client after a reconnect: "Reconnected to roundup, but fetching tools failed: Invalid result for tools/list", with the first issue `expected number, received undefined` at path `ttlMs`, and a second issue (`code invalid_value`, `values [ publi…`) that the user's screen cut off, so its field is not yet known. The same reply is accepted by the headless `claude -p` 2.1.283, so only the interactive client at 2.1.288 is known to reject it. Three tests prove it. `m4_` over stdio checks that every `tools/list` reply (the full list, an empty list and a second page) carries a numeric `ttlMs`. A boxd VM run installs Claude Code 2.1.288 (`claude --version` printed in the PR body), starts it in a pseudo-terminal with `--mcp-config` for `rup mcp`, runs `/mcp` and reads the screen for the reconnect line; it must show the base binary rejected, naming every issue in full text, and the head accepted with `mcp__roundup__todo_list` listed, with no stub client. A run that cannot install that version or start `claude` fails and is never skipped. The same holds for every tool added later (`ask_user`, H14).
