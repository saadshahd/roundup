# UI: the Shelf reads at a glance and holds still (U112, U151 to U154, U157 to U159)

Module: `apps/desktop` (the webview). Ids: U112, U151 to U159. U151 to U154, U157 and U158 are from #398 (feedback: the Todos panel is too raw to use).

Rule (#398): Every Shelf row shows, at rest (no hover, no focus, Drawer closed), each fact the user decides on from that list: for a Todo, its status Glyph, `#<id>`, title, each open blocker and its Home. Every action that changes one of those facts (add, edit, block, unblock, complete, reorder, move) is reachable from the panel by a pointer-only path and by a keyboard-only path, in the row or in the item's Drawer, without typing an id from memory. Check: a harness test lists the facts in each row's DOM text with the pointer outside the list, and for each action drives both paths and reads the changed fact from the row.

**U112 hovering a Shelf row never moves a row.** Reported by QA (F7, sweep 2): hovering an open Todo row shows `complete` inline, the title wraps and the next row moves down 15 px. Given the Shelf's open Todos (U35), then showing or hiding `complete` on hover or focus changes no row's top edge, no row's height and no row's wrapping: the same rule U46 sets for the Rail's Live line, here for the Shelf. `complete` takes no width from the title: it overlays the row's right edge or sits in space reserved at rest, and the row's text at rest is unchanged (U35). The same holds for any other word a Shelf row shows on hover or focus. Tests (`u112_`) read the top edge, height and the title's line count of every row before and after hover and focus in the harness, on a list whose longest title nearly fills its row (hover held since #218; these tests pin it).

**U151 a Todo row shows every fact the user acts on, at rest.** Narrows U15 and U35. Given an open Todo in the Shelf's `todos` list (U15) or under its Agent (U60), with the pointer outside the list, no focus in it and the Drawer closed, then its row holds, top to bottom, and nothing else:
1. the row button, whose text is `<glyph> #<id> <title>` (U15), the Glyph being `·` or `⏸` as U15 says;
2. for a blocked Todo only, the `waits on #<id>, #<id>` line (U15, U35), its text unchanged and in its own element, `data-todo-waits`;
3. the Home line, in its own element, `data-todo-home`, plain text `in <home>` where `<home>` is `project root` or a Room's name (`nameOf`, no Daemon read). The Home is `home` of T12 and its Room value is U158's; the line reads `in project root` for `home: null`. The Home line is not a button and is not in the tab order; changing a Home is `move` (U152).
The light `complete` (U35) still shows only on hover or focus, out of the flow (U112). Amends U15 ("text at rest stays exactly `<glyph> #<id> <title>`" now holds for the row button, not the whole row) and U35's Narrowing the same way: "the second line's text stays exactly `waits on #<id>, #<id>`" holds for `data-todo-waits`, which the Home line never joins. U60's nested copy draws the same three parts. Narrows without contradicting: `u15_open_todos_are_listed_in_id_order_as_glyph_hash_id_title` and `u15_a_blocked_todo_has_the_pause_glyph_and_a_second_line_naming_its_open_blockers_in_id_order` read the row buttons' text and the `waits on` element's text, which do not change; `u35_an_open_rows_text_at_rest_never_includes_complete` reads `rowOf(3).textContent`, which becomes the row button's text in the same PR as the code, with `complete` still absent from the whole row. **U152 every Todo action has a pointer path and a keyboard path from the panel.** Given the Shelf, then each action below is done by the pointer alone and by the keyboard alone, from a row or its Drawer (U17), never by typing an id the user has to remember, and each changed fact is read back from the row (U151) after the Event and refetch of U15:

**U155 the user moves a Todo row up or down, by pointer and by keyboard.** Narrows U15, U35, U60 and U152. Given open Todos in the Shelf's `todos` list (U15) or under an Agent (U60), then a row moves within its own list, and only there, in the Todo order of T10:
- Pointer: pressing the row button and moving it 4 px or more vertically starts a drag; the row follows the pointer on the vertical axis, the other rows make room, and releasing calls `todo.reorder {id, before}` (T11) once. A press that moves less than 4 px is the click of U17 and opens the Drawer; a drag opens no Drawer. `Escape` during a drag, or a release outside the list, cancels it with no call and the row returns. A release over the row's own place calls nothing.
- Keyboard: with the row button focused, `⌥↑` moves the row above the open row before it in the same list, `⌥↓` below the open row after it, each calling `todo.reorder` once; the first row's `⌥↑` and the last row's `⌥↓` call nothing. Focus stays on the moved row's button, found by `#<id>` after the refetch (U138's rule: never left on the page body). The row button's accessible description says `Alt+Up or Alt+Down moves it`. A drag with the keyboard needs no pointer, as U152 requires.
- `before` is the next open row of the same list after the new place; for the new last row of the list it is the Todo that follows the list's last row in `todo.list` (skipping the moved Todo), or null when none does. So a move under an Agent changes no other Agent's or the Shelf's relative order, and Pads (U58) are not rows of this order and stay above the Todos.
- Blocked rows move like any other (T10); a Todo is never moved by completing or blocking another. The `✓ n done` fold is not reorderable: its rows take no drag and no `⌥` key, and its Todos read in the order of T10. At rest a row shows nothing new (U151 stays: no handle, no word); the row's cursor over a drag is `grab`, and no row moves on hover (U112).
- The list changes only when `todo.updated` arrives and `todo.list` is refetched (U15), so a row stays where it was dropped on screen while the call is in flight and is placed by the refetch; a failed `todo.reorder` shows `✕ <message>` in place of the row's `waits on` line (U35) and the list reads as `todo.list` does. Under `prefers-reduced-motion` a drag still follows the pointer (it is direct manipulation).
Tests (`u155_`): the fake App seam answers `todo.reorder` as T11 does; per list (Shelf, under an Agent) a drag of the third row above the first calls `todo.reorder {id: 3, before: 1}` once and the rows read `#3, #1, #2` after the Event; `⌥↓` on `#1` calls `{id: 1, before: 3}`; `⌥↓` on the last row and `⌥↑` on the first call nothing; focus is on `#3`'s row button after the refetch; `Escape` cancels; a 3 px press opens the Drawer and calls nothing; a drag in the `✓ n done` fold does nothing; a move under an Agent whose last row moves down sends the following Todo of `todo.list`; a failed call shows the message and keeps the order; the row's text at rest is unchanged. Observer: an agent-browser run in a dedicated headless session on the U26 harness (`tree-40`, three open Todos) at 1280 by 800 and 700 by 800, light and dark, drags the third row above the first with real pointer events and, in a fresh load, presses `⌥↑` twice on it; each run passes when the ids read from the DOM rows (the `#<id>` in each `[data-shelf-row]` button, in document order) are `[3, 1, 2]` and the ids read from `todo.list` over the Daemon are `[3, 1, 2]`, after a reload of the page and after a restart of `rupd` too, and `document.activeElement` is the moved row's button after the keyboard run. It repeats under an Agent that created the three Todos (U60, expanded).
