# Permission Cards

A Claude Code permission prompt becomes a Card the user answers from the App. Read `docs/permission-cards.md`, ADR 0006 and the Card entry in `CONTEXT.md` first. Claude Code's hook reply is read from `spikes/hooks-permission/REPORT.md` (H1), never from memory. Tests run with a fake `claude` that calls the hook command in its `--settings` file the way Claude Code does (the payload on stdin, the reply read from stdout); no test needs the real one.

**H1 the reply is recorded from the real tool.** Recorded by architect-swarm against `claude` 2.1.287 on 2026-10-02 and committed as `spikes/hooks-permission/REPORT.md` with this PR (the raw run files held local paths and are not kept). It states, each as a line `finding <n>: <text>`: the payload fields; that an allow or deny written as `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` (deny adds `message`) runs or stops the tool and that a deny message reaches the model; that `interrupt` aborts the whole run in print mode; that `{}`, empty output, exit 1, invalid JSON, `behavior:"ask"` and a refused connection all fall through to Claude Code's own dialog without an error to the user; that the dialog is drawn while the hook still runs; that answering the dialog first leaves the hook running and its late reply ignored, while Esc on the dialog sends the hook SIGTERM and fires no hook event; that timeouts of 86400 and 999999999 are accepted; and that `--permission-prompt-tool` is called in print mode only and ignored by the interactive UI. H1b (findings 8 to 11, on a boxd VM with 2.1.283) adds: Claude Code asks for permissions one at a time even when two tools come in one message; Esc sends the hook SIGTERM and a SIGKILL about 1.5 s later; a hook whose `timeout` expires gets SIGTERM, the dialog stays open and nothing is shown to the user; the `Notification` arrives about 6 s after the hook starts and so cannot mark the dialog opening. Not observed: option "No" and Tab-amend on the dialog, two dialogs open at once, and macOS (the runs were on Linux). Tests of H2 to H10 take their strings from the report and put them in test fixtures.

**H1b the remaining unobserved items are recorded.** Given the installed `claude` on macOS and a throwaway directory with a temporary `CLAUDE_CONFIG_DIR`, when the spike script runs one case each for option "No" and Tab-amend, and for the Esc, answer-first and timeout cases of H1b repeated on macOS, then `REPORT.md` gains a `finding <n>:` line for each, citing the run, naming the `claude --version`. It needs a login and a network, so it is a spike and not part of `just check`. No scenario waits on it: H7 and H8 hold with the Linux findings, and a macOS difference becomes a fix.

**H2 a permission request opens one Card.** Given an Agent whose per-Agent settings run `rup permission <agent-id>` for `PermissionRequest` (H9), when the fake `claude` runs that command with the payload on stdin and it stays open, then the Daemon opens exactly one Card for the Agent: `card.list` returns `{id, agent, tool, args, opened_at, answerable}`, where `tool` is the payload's tool name, `args` is its tool input as text cut at 2000 characters with a final `…` when longer, and `answerable` is true; one `card.opened` event carries the same Card. The Daemon also hands the payload to the adapter as the Signal A1 and A2 already read, so the Agent's Kind is `needs-you` with the label A1 gives, and exactly one Card is open for it. A second request from the same Agent while a Card is open replaces the Card (a new `id`, `card.opened`, and the old Card gets `card.cleared` with outcome `replaced`; the Kind stays `needs-you`), and the first `rup permission` exits 1 with `superseded` on stderr and nothing on stdout, so Claude Code falls back to its own dialog. The tests use `card.list`, the events and the exit code. Contract change (the committee approves it): `agent.permission {id, payload}` (called by `rup permission`; it returns when the Card is answered or cleared, with `{output}` for stdout, or an error), `card.list` (no params, returns the open Cards), the events `card.opened` and `card.cleared`, and the `Card` type; see H3 for `card.answer`.

**H3 the user's answer goes through the hook.** Given an open Card, when the user calls `card.answer {id, answer, proof}` with `allow` or `deny` (`proof` as H4 gives), then `rup permission` prints on stdout exactly the reply H1 records for that answer, nothing else, and exits 0; the Card is gone from `card.list`; `card.cleared` carries outcome `allow` or `deny`; and the Agent's Kind is `working` at once (it continues: an allow runs the tool, a deny lets Claude Code go on with the message). An unknown or already cleared `id` is `NOT_FOUND`; an `answer` that is neither word is `INVALID_PARAMS`; a Card that is not `answerable` (H8) is `INVALID_PARAMS`. The reply text is built in `crates/agents/src/claude_code/` and `rup` prints it unchanged, so nothing outside that module names a vendor string. Contract change: `card.answer {id, answer, proof}` returns `null`.

**H4 nothing answers a Card but the user.** The Daemon accepts `card.answer` only from a caller that shows a `proof`: a random secret the App creates when it starts, hands to the Daemon on its stdin, and keeps in the webview's memory. The Daemon removes it from every environment it builds for an Agent, a Terminal and an MCP server, so a process inside an Agent's Terminal, which can connect to `RUPD_SOCKET` and call `daemon.identify` as `user`, cannot know it. Given an open Card, then each of these leaves it open and its `rup permission` still waiting: `card.answer` with a missing or wrong `proof` (error `FORBIDDEN`), including one sent on a connection that never called `daemon.identify` and one sent by a fake `claude` child process from inside the Agent's Terminal using the environment it inherited; `card.answer` by an Actor of kind `agent` or `ext`; a Signal, a `terminal.write` or an MCP tool call from any Agent, whatever its text says; and an hour of an injected clock passing. A test reads the environment the fake `claude` and its Terminal receive and finds no `proof`. A Daemon started without an App (no proof on stdin) answers every `card.answer` with `FORBIDDEN`. The `rup mcp` server lists no tool that answers or lists Cards. The Daemon never calls `card.answer` itself and has no setting that does (the test greps `crates/` for a second caller). Contract change: the `proof` parameter and the `rupd` stdin handshake.

**H5 an open Card survives a webview reload.** Given an open Card and a client that disconnects (a reloaded webview) and a new client that connects and calls `card.list`, then it returns the same Card, with the same `id` and `opened_at`, and `card.answer` from the new client, which gets the `proof` back from the App, prints the reply on the still-waiting `rup permission`. The Daemon keeps Cards in memory only. Quitting the App ends the Daemon and every Agent with it (D1, S3), and with the Agent the hook that waits for the answer, so no Card can outlive the App and none is written to disk; a Daemon started by S5 holds no Card. The test replaces the client, not the Daemon, and a second test starts a new Daemon and finds `card.list` empty.

**H6 an Agent that ends clears its Cards.** Given an open Card, when its Agent's Terminal exits or `agent.stop` is called (A3, A7), then within the bound the test names the Card is cleared with outcome `agent-gone`, `card.cleared` is emitted once, `card.list` no longer has it, the Kind is the one A3 or A7 gives, and the waiting `rup permission` exits 1 with `the Agent ended` on stderr and nothing on stdout.

**H7 an answer given in the Terminal clears the Card.** Given an open Card, then each of these clears it with outcome `terminal`, emits `card.cleared` once, and makes a later `card.answer` for it `NOT_FOUND`: (a) the user answers the dialog with Yes or No, after which Claude Code sends `PostToolUse`, `PostToolUseFailure`, `Stop` or `UserPromptSubmit` for the Agent (H1: the hook is not signalled and keeps running; the Daemon then closes its connection and the late reply, if any, is dropped); the Kind is the one A1 gives for that Signal, `working` for the first, second and fourth; (b) the user presses Esc on the dialog, the hook gets SIGTERM and its connection closes with no later Signal (H1: no hook event fires): the Kind is `idle`, which corrects A2's "Esc on a dialog does not clear `needs-you`" for an Agent with an open Card. (c) the hook's `timeout` expires: Claude Code sends the hook SIGTERM at the timeout, the dialog stays open and shows nothing about it (H1b finding 10), so the connection closing at or after the `timeout` the settings name (H9) is not an Esc: the Card stays open with `answerable` false, `card.opened` is not repeated, one line goes to stderr, and the Kind stays `needs-you`; the test uses an injected clock and a settings `timeout` of 4 s. A Card never stays open after (a) or (b), and no Agent is `needs-you` without an open Card. The tests close the connection and feed the Signals from the fake `claude`.

**H8 the hook fails loud and never allows.** Given `rup permission <agent-id>`, when `RUPD_SOCKET` is unset or no Daemon listens, the payload on stdin is not JSON, or the Daemon answers `NOT_FOUND` for the id, then it prints one line on stderr naming the cause, prints nothing on stdout, and exits 1, whichever it was; Claude Code then shows its own dialog, which H1 records it does without telling the user why. When the Daemon is reachable but cannot build the reply (a payload it cannot read), it opens the Card with `answerable` false and `tool` and `args` as far as they could be read, so the Agent is `needs-you` with a Card that says to answer in the Terminal, and H7 clears it. When no Daemon answers at all, nothing can show it: the failure is the line on stderr that Claude Code prints, and the test asserts it. A Daemon that stops answering is not waited on past the hook's own `timeout`; the command exits 1 with `rupd did not answer` when the connection closes. It never exits 2 and never prints a decision it did not receive from the Daemon. The tests run the built `rup` against each case.

**H9 the Agent's settings route the request.** Given `agent.spawn` (A4), when the Daemon writes the per-Agent settings, then `PermissionRequest` runs `<rup> permission <agent-id>` with a `timeout` of 86400 seconds (H1 shows it is accepted; at expiry H7(c) holds), and every other event in `STATE_EVENTS` (`crates/agents/src/claude_code/launch.rs`) runs `rup signal <agent-id>` with the 5-second timeout. Amendments in the same PR: A4's "one command hook runs `rup signal <agent-id>`" becomes "one command hook per event in `STATE_EVENTS`: `rup signal <agent-id>` for every event except `PermissionRequest`, which runs `rup permission <agent-id>`"; ADR 0006's input design and its "one command hook" sentence say the same; `launch.rs` loses `PermissionRequest` from the `rup signal` list. A1, A2 and D2 are unchanged: `agent.permission` hands the payload to the adapter as the same Signal, so their replays of `spikes/hooks-state/` pass without edits, and in D2 the fake `claude` calls `rup permission` for that payload and the test calls `card.answer` as the user before `PostToolUse`. A `PermissionRequest` payload sent through `rup signal` or `agent.signal` still gives the Signal A1 reads and opens no Card.

**H10 permission Cards never climb the escalation chain.** Given an Agent that has a Meta-agent above it, when it raises a permission request, then the Card is in the user's Inbox at once (`card.opened`, no `Held` Message, no Route, no hop) and nothing sent to the Meta-agent says the Card exists; `card.answer` needs the `proof` of H4, so no Meta-agent can answer it however it is addressed. This differs from `ask_user` and Message questions, which follow the escalation chain of the mailbox series (child, Meta-agent, root, user's Inbox, with a bound per hop). The test opens a Card for a child Agent and asserts the Meta-agent's mailbox is unchanged and `card.list` has the Card.
