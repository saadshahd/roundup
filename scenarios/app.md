# App

Module: `crates/desktop` (the App: Tauri shell, App seam). Ids: every `S` heading in the file.

The App is the Tauri 2 shell in `crates/desktop` (ADR 0001). It starts a Daemon for each open Project and passes calls and events between the webview (`apps/desktop`, see `ui.md`) and that Daemon. It holds no state of its own beyond which Projects are open, their names (`project-tabs.md`, S10), the list of recently opened Projects (S6), and the selected Project for native menu dispatch (U3813). Tests use Tauri's mock runtime (`tauri::test`) and need no window. A fake `rupd` comes from `ROUNDUP_RUPD_BIN`; a real Daemon runs in-process on a temp socket (`rupd` as a dev-dependency).

## App seam

`crates/desktop` and `apps/desktop` meet only here. It is not a Daemon contract (`contracts/` is), so changing it means changing both sides in one PR.

| Webview calls (Tauri command) | Arguments | Result |
|---|---|---|
| `select_project_menu` | `{path: string or null}` | `null`; the webview synchronizes its selected Project whenever tabs change; native Project commands stay present and disabled for null (U3813). Starts no Daemon and sends no prompt. |
| `projects` | none | `[{name, path, running}]`, the open Projects in tab order (S8) |
| `open_project` | `{path}` (absolute) | `{name, path}`; the Project joins the end of `projects` (S8) |
| `close_project` | `{path}` | `null`; the Project's Daemon ends (S8) |
| `rename_project` | `{path, name}` | `{name, path}` (S10) |
| `rpc` | `{path, method, params}` | the method's JSON result, unchanged |
| `subscribe` | `{path, channel, after?}` (a Tauri `Channel`; `after` an Event number) | the Daemon's `head` (D11, I9); then, with `after`, every saved Event numbered above it, then every Event of that Project's Daemon, is sent on the channel, in the Daemon's order |
| `recent_projects` | none | the absolute paths of recently opened Projects, most recent first (S6) |
| `claude_binary` | none | `{path, version}` of the `claude` the App would run, or `null` (S6) |
| `open_in_editor` | `{path, line?}` (an absolute directory or file) | `null`; the directory, or the file at `line` when the editor takes one, opens in the user's code editor (`ui-rail-actions.md` U429, `ui-worktree-changes.md` U2539c) |

| App emits (Tauri event) | Payload | Result |
|---|---|---|
| `open-project-page` | `{path, command: "import-work" or "project-settings"}` | Native Project menu activation captures its synchronized selected Project; only that Project opens its center page (U3813/U3814). No selection emits nothing. |
| `open-app-settings` | none | The webview opens App Settings in the center (U3799); works without an open Project. |

Every command fails with `{code, message}`, using the codes in `rpc::code`; an error from the Daemon passes through unchanged. When the Daemon ends while the App runs, the App emits the Tauri event `daemon-exited` with `{path, code: number | null}`. `scenarios/project-tabs.md` (S8 to S10) holds the several-Project rules this table follows; where S1, S2, S3 and S5 say one Project or one Daemon, they now say it of each.

**S1 open a Project.** Given the App started as `roundup <project>`, or a webview call `open_project {path}`, then the App starts `rupd <path> --attached` (D1). It puts `RUPD_SOCKET` in that Daemon's environment, set to a socket path unique to this App run and under the 104-byte limit; Terminals inherit it, so hooks and MCP servers find this Daemon and no other. The App waits until `daemon.ping` answers, for at most a bound it names, then returns `{name: <basename>, path}`; afterwards `projects` lists it. The Daemon is `ROUNDUP_RUPD_BIN`, else the `rupd` beside the App's executable. A path that is not a directory is `INVALID_PARAMS` naming it. A Daemon that exits or stays silent past the bound is `INTERNAL`, and the message carries the last lines of its stderr. A second `open_project` for a path whose Daemon runs returns it and starts nothing (S8; S5 covers a Project whose Daemon has exited). The App grants the webview exactly these permissions and nothing else: `dialog:allow-open`, `dialog:allow-save`, `core:window:allow-set-badge-count`, `window-bar:allow-set-window-title`, `window-bar:allow-drag-window`, `window-bar:allow-zoom-window`, `core:event:allow-listen` and `core:event:allow-unlisten`. The last two are what let it hear `daemon-exited`. A release build (`just app-release`, W1) loads the webview's built files instead of the dev server; it is not bundled, signed or notarized.

**S2 calls and events.** Given an open Project, when the webview calls `rpc {method: "daemon.ping", params: null}`, then it gets `{pong: true}`. A call that fails in the Daemon (`todo.get {id: 99}`) fails with the same `{code, message}`. After `subscribe`, an event the Daemon emits (`todo.created`) arrives on the channel, and several arrive in order. Before any Project is open, `rpc` and `subscribe` fail at once with `CONFLICT` saying no Project is open; they never wait.

**S3 lifetime.** When the App exits, the Daemon's stdin closes, so the Daemon exits and its Agents and Terminals stop (D1). When the Daemon exits on its own, the webview gets `daemon-exited` with its exit code (`null` if a signal ended it), and later `rpc` calls fail with `INTERNAL`.

**S4 the window loads the webview.** Given `just app <project>`, then the App's window shows the webview served by the dev server on port 5173, and the dev server fails rather than take another port. Given a release build (`just app-release`, W1), then the window shows the webview's built files embedded from `apps/desktop/dist`. `just app` refuses to start, naming the port, when something already answers on 5173, so the window never opens on another server's webview; its wait also stops if the Vite it started exits. Neither needs an environment override: `crates/desktop/tauri.conf.json` names `devUrl` and `frontendDist`. Before starting Vite, `just app` installs the frozen lockfile noninteractively; a failed install stops before any build or window opens. HTML answering is not readiness: the dev server must successfully transform `/src/main.tsx` and every import reachable in Vite’s client module graph. A failed transform names the failing import and stops startup without opening the App; a cyclic import does not hang the check. Once HTML answers, module readiness has a 30-second bound and does not claim native rendering or execute App calls.

**S5 reopen after the Daemon exits.** Given a Project whose Daemon has exited (S3), when the webview calls `open_project {path}` with that Project's path, then the App starts a new `rupd <path> --attached` exactly as S1 does, on a socket path unique to this new run, and returns `{name, path}`. Afterwards `rpc` works against the new Daemon, a `subscribe` made after the reopen receives its events, and `daemon-exited` is emitted again if it ends. Until the reopen, `rpc` still fails with `INTERNAL` (S3). While a Daemon runs, a second `open_project` for its path starts nothing (S8), and after an exit a different path opens a second Daemon beside the exited one (S8). A reopen that fails is `INTERNAL`, as in S1, and leaves the App ready for another try. Narrowing: `s1_a_second_open_project_is_conflict` and `s3_after_the_daemon_exits_rpc_fails_with_internal` keep passing as written; S1's sentence "a second `open_project` while one is open is `CONFLICT`" now reads "while its Daemon runs".

**S6 first-run facts.** Given the App, then two new calls exist besides S1's, and both work before any Project is open, like `project`. `recent_projects` returns the paths of the Projects opened by a successful `open_project` or at launch as `roundup <project>` (S1), most recent first, at most five, each once, kept in the App's own data folder so they survive a restart; a path that is no longer a directory is left out. `claude_binary` returns `{path, version}` for the `claude` that `ROUNDUP_CLAUDE_BIN` names, else the first on `PATH`, with the version read from its `--version` output, and `null` when there is none or it does not answer within a bound the App names. Neither call starts a Daemon or changes the open Project, and a failed write of the recent list never fails `open_project`. The tests use a fake `claude`, a temporary data folder, and a fake `PATH`; nothing reads the user's real `claude` or data folder. This adds two rows to the App seam table above, which the review run's approve covers (the Contract recipe of `.agents/builder.md`). The webview's permissions stay exactly S1's list: the data folder and `claude --version` are reached from Rust only, so `s1_the_webview_is_granted_dialogs_the_dock_badge_and_hearing_events_and_nothing_else` passes as written. S6 ships in one PR with U52, which holds the webview side, because a seam change is made on both sides in one PR. No Daemon method changes.

**S7 the minimum window width.** Given the App's window configuration, then its minimum width is 1280 px and its initial width is at least 1280 px (U452). The window is declared maximized and sets no height, minimum height or maximum height. Observed by `u452_window_width_is_at_least_1280` and `u452_window_opens_maximized` in `crates/desktop/tests/`, reading the actual configuration without a display; the tests that read the dev URL and the built frontend keep passing.

**S2297a the webview renders at the display's rate.** Given the App's webview setup on macOS, when it runs on a `WKPreferences`, then that object reports `PreferPageRenderingUpdatesNear60FPSEnabled` off, read through `+[WKPreferences _features]` with no window; asserted by `s2297a_the_setup_turns_the_near_60_fps_feature_off`, a Rust test in `crates/desktop/tests/` that runs in the `mac` lane. The feature is off before the webview draws, for every App webview. Given a WebKit without `_features`, without `_setEnabled:forFeature:` or without the feature in its list, then the setup changes nothing, the App starts, and one stderr line names what is missing; asserted by `s2297a_a_webkit_without_the_feature_keeps_its_rate_and_says_so`, which runs the setup against a stand-in for each of the three gaps. Given `crates/desktop/tauri.conf.json` as committed, then the App builds under Tauri's mock runtime with the setup registered; asserted by `s2297a_the_app_builds_with_the_setup_registered`. Other platforms compile and behave as before (policy: the `mac-clippy` and Linux `check` lanes). The private calls are named in one place in `crates/desktop/src/`. S1's permission list and the App seam are unchanged, so `s1_the_webview_is_granted_dialogs_the_dock_badge_and_hearing_events_and_nothing_else` passes as written. `docs/perf.md`, "What can go wrong" under keystroke-to-render, gains: Low Power Mode halves the webview's frame rate, so a run in it measures the power setting, not the App; run on AC power with Low Power Mode off (policy). The Mac observation is the user's (R12): `ROUNDUP_ALLOW_WINDOW=1 just perf-keystroke` on AC power, Low Power Mode off, reports a mean frame time under 10 ms on the built-in 120 Hz display.

**S12 the app icon.** Given `just app <project>`, then the Dock shows roundup's icon: a matte ivory hand whose fingertips close to the thumb, its forearm rising from the tile's bottom edge, on a juniper teal tile. Soft upper-left lighting preserves warm ivory midtones; the hand has two tiny childhood marks and a short, flat, faded horizontal scar in its middle. `crates/desktop/icons/artwork.png` is the approved artwork and the icon's one source. `just icon` uses macOS's `sips` to render `crates/desktop/icons/icon.png` at 1024 px without applying another material or lighting effect; Tauri embeds that file and, in a development run, sets it as the Dock icon. A change to the mark edits `artwork.png` and runs `just icon` in the same PR. Asserted by `s12_the_app_carries_the_1024_px_rendered_icon` in `crates/desktop/tests/`: the App's embedded icon is 1024 px square and transparent outside its rounded corners. `README.md` shows the same `icon.png`. `crates/desktop/icons/social-preview.png` is a matching 1280 by 640 px image under 1 MB for the repository's social preview. A bundled App does not exist yet (S1); its packaging and macOS appearance variants remain outside S12. The Mac observation is the user's: the icon in their Dock beside their other apps.

## WebKit action audit

Module: `apps/desktop` and `crates/desktop`, limited to the three WebKit action classes.

Policy: S3806a–c specify the whole-App audit ordered by Issue #3806. This specification delivers no fixes or native pass. The implementation inventories all production callers on its exact head, repairs every instance of these three classes, and records each caller's source file/function, trigger, selected Project/object, result, guard coverage and any required Mac evidence on its work Issue. Include callers outside shared primitives and paths with no defect; an unexamined caller is incomplete, not a pass. Inventory pointers below are starting points, not a closed list. Preserve existing acceptance and tests; U3800a–c (`scenarios/ui-drag.md`) remain the drag-library migration's acceptance, not a prerequisite for this audit. Audit whichever library is present on the implementation head and recheck changed callers after a migration.

**S3806a an interrupted drag leaves one settled result.** Given each App drag or pointer-driven selection, begin the gesture and move to a different candidate destination. Include Rail nesting/order, Project and Workstream tabs, Todos, Pads/Agent Pads, Bubble move/resize/pull, pane/Shelf resizing, scrollbar dragging, editable text and Terminal output selection, and native file-drop routing. Inventory the dnd-kit providers and all pointer/mouse/native-drag handlers; follow their callers, not only matches for a library name.

When window blur, dragged-element blur, focus moving to another control, or `pointercancel` occurs before release (including blur before pointer capture), then the gesture settles: an interrupted reorder commits no mutation and restores its original order/parent; an interrupted resize or move follows its existing cancellation contract, retaining either its last completed position or its original position, never an outstanding preview. If no cancellation contract exists, restore the pre-gesture position. Selection keeps already selected text, sends no Terminal input, and stops extending after cancellation. File drops deliver no paths without an actual drop. A later release/move cannot commit that interrupted gesture, no frame/scroll/listener keeps it active, and a fresh gesture works. An incidental element blur during capture may continue the same gesture if the library retains ownership: its eventual release must commit exactly the chosen destination once; actual window blur or `pointercancel` must settle without a commit. Assert these alternatives by the library's observed active/cancelled state, never by assuming every blur cancels.

Observer: one parameterized, browser-free CI guard `s3806a_interruption_settles_the_gesture` in planned `apps/desktop/src/ui/s3806a_interruption.test.tsx`. Mount production gesture owners through their existing seams; exercise the event/phase matrix, assert original/settled state and mutation/delivery counts, then perform a fresh gesture. Parameterize distinct owner paths; a test only of a fake drag engine proves nothing. Browser-only input delivery and WKWebView's early blur/capture ordering use the native policy observer below. Normal release, keyboard reorder, Escape, nested moves, external path delivery and small-travel clicks keep their existing observers (policy). No new drag engine is prescribed.

**S3806b choosing an action outlives its surface.** Given every Ark menu, dialog, popover, picker and command-palette action that reaches `rpc` or a Tauri command, when the user activates it with pointer or keyboard and its surface closes and its owner unmounts, then dispatch begins before close/unmount can discard the action, with the Project, object and arguments captured by that activation, and reaches its RPC or Tauri command exactly once. For an asynchronous confirmation or native chooser, initiating that request precedes dismissal; cancellation dispatches no mutation, and an affirmative result dispatches the captured action once even if its originating owner has since unmounted. Closing a surface starts no call by itself. An acknowledged success updates the intended target through the existing App state; it cannot act on a subsequently selected target.

When that same dispatched call rejects after close/unmount, then its failure remains visible and actionable in a surviving App surface, names the failed action/cause and a recovery action, and does not report success or silently retry. Unsubmitted input and its original target remain recoverable under P11; an unknown external outcome does not authorize an automatic duplicate call. A console line or error owned only by removed content is not a surfaced failure.

Observer: one parameterized, browser-free CI guard `s3806b_action_survives_surface_close` in planned `apps/desktop/src/ui/s3806b_actions.test.tsx`. Activate real production items/submit handlers against the existing fake App; record dispatch/close/unmount order, call counts and captured arguments. Hold the reply, unmount the originating owner, switch selection, then resolve or reject; assert intended state or surviving accessible failure and recoverable draft. Include confirmation/chooser accept and cancel cases. An inventory row maps every action to an exercised production path; where many actions share dispatch ownership, cover that owner plus each caller's target/argument contract rather than duplicate its proof. Starting work solely in an exit animation, an untracked deferred callback or a component-owned effect fails. The guard checks behavior, roles, focus and contracts, never layout or exact copy. Existing confirmations and permissions still govern (policy).

**S3806c scale changes refit a sharp Terminal.** Given the App with a populated Agent Terminal, Door Terminal and a Terminal Bubble, including one hidden and later revealed, when the user double-clicks empty window-bar space to invoke `zoom_window`, changes macOS text size from its default to the largest available setting, or moves the window from its Retina display to an external display with a different `devicePixelRatio` and back, then visible Terminals redraw using the current pixel ratio and cell metrics and refit their cols/rows without reopening the Project or resizing by hand. The next revealed Terminal fits before accepting input at stale dimensions. The Daemon's `terminal.resize` agrees with the fitted cols/rows whenever dimensions change; a DPR-only change still refreshes rendering even when cols/rows stay equal. Output, selection and scrollback remain available; this operation neither recreates the PTY nor sends input. Assert dimension/delivery/content behavior with `s3806c_scale_change_refits_the_terminal` below; sharpness and panel fit are native policy observations.

Observer: one parameterized, browser-free CI guard `s3806c_scale_change_refits_the_terminal` in planned `apps/desktop/src/terminal/s3806c_scale.test.ts`. Drive the production emulator and screen/resize ownership with controllable DPR, host-size and text-metric notifications, including DPR 2→1→2 with unchanged CSS bounds and changed bounds, repeated notifications, hidden/reveal and disposal. Assert the renderer receives current scale/invalidation, fit yields the new cols/rows, only changed dimensions reach the original Terminal's resize call, preserved output and zero input/new-PTY calls. Observe production orchestration with the existing xterm/FitAddon seam; a double that implements scale handling itself is no proof. Read the installed xterm/WebGL addon's DPR support before adding an observer: if the library already owns a step, exercise that integration, rather than mandate a second atlas watcher. Native sharpness is not inferred from mock call counts.

Policy: `zoom_window` is native window zoom, not browser page zoom. Record which macOS setting actually changes text metrics; a setting WKWebView does not consume is recorded as no effect, never claimed as text-scaling coverage. Do not pin scale or disable accessibility to make panels fit. At each effective larger text size and display scale, all App panels and floating surfaces remain usable with no clipped actions, overlapping text or unreachable content; the design critic judges this, not CI geometry assertions.

### Audit observers and regression boundary

Policy: exactly one cheap CI guard per class above, parameterized as needed; no new browser launch when the event/call-count contract suffices. Each guard must fail when its production behavior is removed, not merely check source text or a test double. Do not weaken an existing test or duplicate its proof; rule 10's pruning names the surviving observer for any removal. No workflow, loop machinery, Daemon method, permission or App seam expansion is authorized here. If a repair requires an App seam change, use the Contract recipe with every caller and independent approval. Keep implementation PRs within rule 3, splitting native repairs into linked scoped prerequisite Issues if needed; the audit stays open until every inventory row is settled.

Policy, rendered observer: use U26's isolated headless harness, dark 1512×950, `tree-40`, `agents-10`, `tabs-8` and `bubbles`; inject a rejected action and keep its failure text visible on the densest seed. Inspect Enter (chooser/start), Understand (Rail/tabs), Intervene (Terminal/Bubble) and Review (Todo/Pad actions) through the journey in `.agents/data/journey.md`. Run `just capture S3806a S3806b S3806c`; leave PNGs/videos under `artifacts/ux/<id>/`, never commit them. Moves: D2, D5, D6, D10; no Check passing on the same main baseline regresses. Captures and the critic own appearance, hit areas, focus visibility, sharpness and overflow; CI owns calls, roles and contracts.

Policy, required native observer: implementation prepares one exact build commit and one combined `needs-mac` request per round for the owner's local agent. This specification needs no Mac request. On the owner's Mac, run `pnpm install` and `just app <disposable-project-path>` at that commit. Record macOS/WebKit versions, build SHA, text setting, both displays/scales, power state and actual DPR/cols/rows observations. Use two disposable Projects, populated Terminals and every audited gesture/surface; do not interact with unrelated user windows. Perform S3806a's pre-capture blur, mid-gesture focus change, cancellation, release and fresh-gesture checks with real native input; perform S3806b's immediate dismissal/owner removal and record call receipt and surviving failure; perform S3806c's window zoom, default/largest text setting and Retina→external→Retina sequence, including a hidden Terminal revealed after each change. Compare Terminal glyphs to freshly rendered text at each scale and check the panels with long names and visible failures. Restore changed system settings after recording results. Record each operation's pass/fail and evidence under its scenario id; missing hardware, unobservable native state or an unavailable setting is incomplete, never a pass. Existing `macos-latest` checks are read from CI history instead of requested again. Chromium establishes no WKWebView pass. Implementation completion needs all three class guards, the full caller inventory, rendered Checks and this native evidence; a specification merge alone completes none of the audit.
