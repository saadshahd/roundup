# Agents and the Rail

Read `spikes/hooks-state/REPORT.md` and ADR 0006 first: they define how hook Signals, the terminal title and the exit status become a Status.

**A1 signals to status.** Given an adapter replaying `spikes/hooks-state/log*.jsonl` payloads as Signals, then `UserPromptSubmit` gives `working`; `Stop` gives `idle`; `PermissionRequest` gives `needs-you` whose label quotes the question or tool; `StopFailure` gives `error` whose label is the `error` field; `PostToolUse` after a `needs-you` gives `working`; `SessionEnd` gives `done`. The mapping is a pure function `observe(Observation) -> Option<Status>` with `since` set by an injected clock.

**A2 title closes the silent gaps.** Given the title Observations in `spikes/hooks-state/screen.jsonl`, then a ◐/◑ title gives `working`; an ✳ title after an Esc interrupt gives `idle`; an ✳ title that follows a `PreToolUse` Signal is held for `STAR_HOLD` (a named constant, 200 ms, derived from the fixtures: across 9 dialogs the star lands 9–80 ms after `PreToolUse` and 18–79 ms before its `PermissionRequest`; the hold is measured from the star and leaves about 2.5 times the largest gap): if the `PermissionRequest` arrives within `STAR_HOLD` the Agent goes straight to `needs-you` with no `idle` between, and otherwise a `Tick` after `STAR_HOLD` resolves the held star to `idle` (so an Esc interrupt during an auto-allowed tool run reads `idle` after `STAR_HOLD`, never stuck at `working`); and a ◐/◑ title never clears `needs-you`. A denied dialog gives a spinner, not a star, in the fixtures, so `needs-you` holds until the next `UserPromptSubmit` or a `PostToolUse` after a Yes. Esc on a dialog fires no hook and no title in the fixtures, so it does not clear `needs-you`; a star never ends `needs-you`, `error` or `done`. A replay of the real deny in `screen3` with its own hooks must not read `working` while Claude waits at its prompt.

**A3 exit.** Given a Terminal behind an Agent, when it exits with code 0 the Status is `done`; with a non-zero code it is `error` with label `exited <code>`; killed by a signal it is `error` with label `exited by signal`. A Signal arriving after exit is ignored.

**A4 spawn.** Given `agent.spawn {cwd, prompt}` with `ROUNDUP_CLAUDE_BIN` pointing at a fake `claude` script (tests never run the real one), then a Terminal starts running it with a per-Agent `--settings` file whose one command hook runs `rup signal <agent-id>`, the hook command is the absolute path of the `rup` beside the running `rupd` with a 5-second timeout, the working directory is pre-trusted only when it lies inside the Project folder (any other is `INVALID_PARAMS`), `rup signal` never exits 2, the Agent appears in `rail.tree` with `kind: agent`, and the prompt is typed into the Terminal at the first idle. `rup signal <agent-id>` reads one hook payload from stdin, identifies as that Agent, and calls `agent.signal`.

**A5 signal path.** Given an Agent, when `agent.signal {id, payload}` arrives, then the adapter updates the Status and, only if it changed, emits `agent.status {id, status}`. A payload the adapter does not recognise is ignored and logged to stderr, never an error to the caller.

**A6 rail tree.** Given Groups and Agents, then `rail.createGroup`, `rail.rename` and `rail.move {id, parent, index}` keep sibling `order` values contiguous from 0, emit `rail.changed`, and fail with `CONFLICT` when a node would move into its own descendant or under a plain Agent or Terminal (nesting only under Groups and Meta-agents). `rail.tree` returns nodes ordered parent-first, then by `order`.

**A7 promote and stop.** Given a Group with two Agent children, when `rail.promote` is called, then it is a Meta-agent (`meta: true`) with a live Agent and a Status. When `agent.stop` is called on it, then it stays in the Rail with status `done`, its children move up one level (parent becomes the Meta-agent's parent, placed where it was) and keep running.

**A8 persistence.** Given a Rail, when `Agents::open` is called again on the same directory, then Groups, `parent` and `order`, names and `meta` flags are intact. Agents whose Terminal is gone come back with Status `done`; the module never claims a dead process is working.

**A9 name from the first prompt.** Given `agent.spawn` without a prompt, then the Agent's Rail name is `new-agent`. When its first `UserPromptSubmit` Signal arrives, then the node is renamed from the payload's `prompt` and `rail.changed` is emitted. The name is the prompt lower-cased, split on anything that is not a Unicode letter or digit (Rust's `char::is_alphanumeric`), with `a an the to of in on for and please` dropped, the first three remaining words joined by `-`, cut to 32 characters with no trailing `-`: "Fix the refresh race in token.ts" gives `fix-refresh-race`. A prompt with no words left keeps the current name. Later prompts never rename it, and a `rail.rename` made before the first prompt wins over it. An Agent spawned with a prompt is named by the same rule when that prompt is submitted. Meta-agents keep their Group's name.

**A10 a Terminal in the Rail.** Given `rail.spawnTerminal {cwd, parent}`, then a Terminal runs the user's login shell in `cwd`, and a node `{kind: terminal, name, terminal_id}` is placed last under `parent` with `rail.changed` emitted. `name` is the basename of `$SHELL`, else `shell`. `parent` follows A6: under a plain Agent or a Terminal it is `CONFLICT`, and an unknown id is `NOT_FOUND`. A `cwd` that is not a directory is `INVALID_PARAMS` and adds no node. When the program exits, the node stays in the Rail with `status: null`.

**A11 Todos and Pads over MCP.** Given `agent.spawn`, then Claude Code also gets `--mcp-config <file>`, where the file is `.roundup/agents/<id>.mcp.json` and declares one stdio server `roundup` whose command is the absolute `rup` path the hooks use, with args `mcp <id>`. The config adds to the user's own servers: `--strict-mcp-config` is never passed. The per-Agent settings file allows `mcp__roundup__*`, so these tools never raise a permission dialog. `RUPD_SOCKET` is not written into either file, because stdio servers and hooks inherit Claude Code's environment, which inherits the Daemon's. Tests read the argv and the two files; they never run `claude`. The flag and the allow rule follow code.claude.com/docs (cli-reference, permissions, mcp), read on 2026-10-01.

**A12 a reopened Rail never names another run's Terminal.** Given a Rail persisted by an earlier Daemon run, when `Agents::open` runs, then no node carries a `terminal_id` from that run. Terminal ids restart at 1 with every run, so an old id could name a new, unrelated Terminal. Agents come back `done` as in A8, and Terminal nodes come back with `terminal_id: null`. A12 replaces the two assertions in the agents stack that a reopened node keeps its old `terminal_id`: `a8_an_agent_whose_terminal_is_gone_comes_back_done` (`spawn.rs`) and `a8_a_meta_agent_keeps_its_flag_across_reopening_and_comes_back_done` (`promote.rs`). Both now expect `terminal_id: null`.
