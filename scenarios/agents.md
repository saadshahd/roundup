# Agents and the Rail

Read `spikes/hooks-state/REPORT.md` and ADR 0006 first: they define how hook Signals, the terminal title and the exit status become a Status.

**A1 signals to status.** Given an adapter replaying `spikes/hooks-state/log*.jsonl` payloads as Signals, then `UserPromptSubmit` gives `working`; `Stop` gives `idle`; `PermissionRequest` gives `needs-you` whose label quotes the question or tool; `StopFailure` gives `error` whose label is the `error` field; `PostToolUse` after a `needs-you` gives `working`; `SessionEnd` gives `done`. The mapping is a pure function `observe(Observation) -> Option<Status>` with `since` set by an injected clock.

**A2 title closes the silent gaps.** Given the title Observations in `spikes/hooks-state/screen.jsonl`, then a ◐/◑ title gives `working`; an ✳ title after an Esc interrupt gives `idle`; an ✳ title that follows a `PreToolUse` Signal is held for `STAR_HOLD` (a named constant, 200 ms, derived from the fixtures: across 9 dialogs the star lands 9–80 ms after `PreToolUse` and 18–79 ms before its `PermissionRequest`; the hold is measured from the star and leaves about 2.5 times the largest gap): if the `PermissionRequest` arrives within `STAR_HOLD` the Agent goes straight to `needs-you` with no `idle` between, and otherwise a `Tick` after `STAR_HOLD` resolves the held star to `idle` (so an Esc interrupt during an auto-allowed tool run reads `idle` after `STAR_HOLD`, never stuck at `working`); and a ◐/◑ title never clears `needs-you`. A denied dialog gives a spinner, not a star, in the fixtures, so `needs-you` holds until the next `UserPromptSubmit` or a `PostToolUse` after a Yes. Esc on a dialog fires no hook and no title in the fixtures, so it does not clear `needs-you`; a star never ends `needs-you`, `error` or `done`. A replay of the real deny in `screen3` with its own hooks must not read `working` while Claude waits at its prompt.

**A3 exit.** Given a Terminal behind an Agent, when it exits with code 0 the Status is `done`; with a non-zero code it is `error` with label `exited <code>`; killed by a signal it is `error` with label `exited by signal`. A Signal arriving after exit is ignored.

**A4 spawn.** Given `agent.spawn {cwd, prompt}` with `ROUNDUP_CLAUDE_BIN` pointing at a fake `claude` script (tests never run the real one), then a Terminal starts running it with a per-Agent `--settings` file whose one command hook runs `rup signal <agent-id>`, the hook command is the absolute path of the `rup` beside the running `rupd` with a 5-second timeout, the working directory is pre-trusted only when it lies inside the Project folder (any other is `INVALID_PARAMS`, and so is the user's home folder, which is never trusted), `rup signal` never exits 2, the Agent appears in `rail.tree` with `kind: agent`, and the prompt is typed into the Terminal at the first idle. `rup signal <agent-id>` reads one hook payload from stdin, identifies as that Agent, and calls `agent.signal`.

**A5 signal path.** Given an Agent, when `agent.signal {id, payload}` arrives, then the adapter updates the Status and, only if it changed, emits `agent.status {id, status}`. A payload the adapter does not recognise is ignored and logged to stderr, never an error to the caller.

**A6 rail tree.** Given Groups and Agents, then `rail.createGroup`, `rail.rename` and `rail.move {id, parent, index}` keep sibling `order` values contiguous from 0, emit `rail.changed`, and fail with `CONFLICT` when a node would move into its own descendant or under a plain Agent or Terminal (nesting only under Groups and Meta-agents). `rail.tree` returns nodes ordered parent-first, then by `order`.

**A7 promote and stop.** Given a Group with two Agent children, when `rail.promote` is called, then it is a Meta-agent (`meta: true`) with a live Agent and a Status. When `agent.stop` is called on it, then it stays in the Rail with status `done`, its children move up one level (parent becomes the Meta-agent's parent, placed where it was) and keep running.

**A8 persistence.** Given a Rail, when `Agents::open` is called again on the same directory, then Groups, `parent` and `order`, names and `meta` flags are intact. Agents whose Terminal is gone come back with Status `done`; the module never claims a dead process is working.

**A9 name from the first prompt.** Given `agent.spawn` without a prompt, then the Agent's Rail name is `new-agent`. When its first `UserPromptSubmit` Signal arrives, then the node is renamed from the payload's `prompt` and `rail.changed` is emitted. The name is the prompt lower-cased, split on anything that is not a Unicode letter or digit (Rust's `char::is_alphanumeric`), with `a an the to of in on for and please` dropped, the first three remaining words joined by `-`, cut to 32 characters with no trailing `-`: "Fix the refresh race in token.ts" gives `fix-refresh-race`. A prompt with no words left keeps the current name. Later prompts never rename it, and a `rail.rename` made before the first prompt wins over it. An Agent spawned with a prompt is named by the same rule when that prompt is submitted. Meta-agents keep their Group's name.

**A10 a Terminal in the Rail.** Given `rail.spawnTerminal {cwd, parent}`, then a Terminal runs the user's login shell in `cwd`, and a node `{kind: terminal, name, terminal_id}` is placed last under `parent` with `rail.changed` emitted. `name` is the basename of `$SHELL`, else `shell`. `parent` follows A6: under a plain Agent or a Terminal it is `CONFLICT`, and an unknown id is `NOT_FOUND`. A `cwd` that is not a directory is `INVALID_PARAMS` and adds no node. When the program exits, the node stays in the Rail with `status: null`.

**A11 Todos and Pads over MCP.** Given `agent.spawn`, then Claude Code also gets `--mcp-config <file>`, where the file is `.roundup/agents/<id>.mcp.json` and declares one stdio server `roundup` whose command is the absolute `rup` path the hooks use, with args `mcp <id>`. The config adds to the user's own servers: `--strict-mcp-config` is never passed. The per-Agent settings file allows `mcp__roundup__*`, so these tools never raise a permission dialog. `RUPD_SOCKET` is not written into either file, because stdio servers and hooks inherit Claude Code's environment, which inherits the Daemon's. Tests read the argv and the two files; they never run `claude`. The flag and the allow rule follow code.claude.com/docs (cli-reference, permissions, mcp), read on 2026-10-01.

**A12 a reopened Rail never names another run's Terminal.** Given a Rail persisted by an earlier Daemon run, when `Agents::open` runs, then no node carries a `terminal_id` from that run. Terminal ids restart at 1 with every run, so an old id could name a new, unrelated Terminal. Agents come back `done` as in A8, and Terminal nodes come back with `terminal_id: null`. A12 replaces the two assertions in the agents stack that a reopened node keeps its old `terminal_id`: `a8_an_agent_whose_terminal_is_gone_comes_back_done` (`spawn.rs`) and `a8_a_meta_agent_keeps_its_flag_across_reopening_and_comes_back_done` (`promote.rs`). Both now expect `terminal_id: null`.

Deferred past Phase 2: `blocked` for Agents (needs Todo ownership), Meta-agents receiving child events (needs the message bus), the Claude-trust-dialog screen scrape.

**A13 a symlinked agents directory is refused.** Given `.roundup/agents` under the Project is a symlink, when `agent.spawn` runs, then it fails with `INVALID_PARAMS` naming the path, and no per-Agent settings or MCP config file is written, neither through the link nor beside it. A real directory, and a missing one that the spawn creates, work as before. Narrowing: `a4_a_symlinked_config_is_written_through_and_stays_a_link` and `a4_a_symlink_planted_where_a_file_goes_is_replaced_not_written_through` are about a config file, not the directory, and keep passing as written.

**A14 a Signal that arrives early is held and applied.** Given an Agent whose Terminal has started but whose `agent.spawn` has not yet finished registering it, when `agent.signal {id, payload}` arrives for it, then the Signal is held and applied in arrival order as soon as the Agent is registered, exactly as A5 says (the Status updates and `agent.status {id, status}` is emitted if it changed), before any Signal that arrives later. The call returns success, so `rup signal` exits 0 and the Agent is never `error` because of it. At most 8 Signals are held for one Agent; the ninth and each later one drops the oldest held Signal, which is logged to stderr as A5 does for what it ignores, and the other eight are still applied in arrival order. If the spawn then fails (the Terminal cannot be attached to the Rail or cannot start), `agent.spawn` fails with its own error as today, no Agent exists, the held Signals are discarded and nothing is announced for it. An id that was never spawned still gets `NOT_FOUND`. The test holds the window open instead of racing it: a fake Terminal start that does not return until the test has sent the Signal (the seam is the Builder's choice, and it is a test seam, not a public function), so the test fails before the fix on every run, with no load and no timing. The same test, with the spawn then made to fail, covers the discard. `d4_ten_idle_agents_cost_the_daemon_less_than_150_mb` stays as the end-to-end proof.

**A15 a clean environment for every program the Daemon starts.** Given a Daemon whose own environment holds session markers, which are `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` (it was started from inside a Claude Code session), when `agent.spawn`, `rail.spawnTerminal` or `terminal.spawn` starts a program, then that program's environment holds none of them. Every other variable passes through, `PATH`, `HOME` and `SHELL` included, and so does the user's own Claude Code configuration (`CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_MAX_OUTPUT_TOKENS` and the like): that is a decision, because only the markers name a running session and a login or a setting is the user's. Found in the demo app: Claude Code in an Agent printed "Transcript saving is off, inherited CLAUDE_CODE_CHILD_SESSION marker". The test starts a real `rupd` with those markers, `CLAUDE_CODE_OAUTH_TOKEN` and `CLAUDE_CODE_USE_BEDROCK` in its environment (as `crates/rup/tests/signal.rs` starts one), spawns a Terminal through `terminal.spawn`, writes `env > <file>` to it, and checks that no marker is in the file and that the other three are, `PATH` included; one case does the same through `agent.spawn` with a fake `claude` that writes its environment. The fix is in the Terminal's spawn call; `SpawnParams` gains no field, since that would be a contract change. The Builder owns `crates/terminal/**`, `crates/agents/**` if its spawn needs it, and `crates/rup/tests/**`, and starts after #114 lands, since both edit `crates/agents/src/lib.rs`.

**A16 remove a node.** Given a Rail node, when `rail.remove {id}` arrives, then a running Agent is stopped as `agent.stop` does and a running Terminal is killed, and the node is deleted from the Rail; the siblings after it keep their order. For a Group, or for a Meta-agent (an Agent that has children, whose Agent runs under the node's own id), the children move to the node's parent at the node's place, in their order, and only the node goes: the Meta-agent's Agent is stopped as A7 says and then its node is deleted too, so no `meta` node and no `done` Agent is left, and the children end up where the node stood with no other change. The stop comes first, in the order `agent.stop` uses. If stopping fails (the test makes a fake Terminal's kill return an error), the call returns that error and deletes nothing: the node stays at its place under its parent, with its children, and its status is whatever `agent.stop` left, so a second `rail.remove` can retry. If the stop worked and the delete then fails, the node stays on the Rail with its exited Agent, and a second `rail.remove` removes it. For a Group, moving the children and deleting the node are one transaction: the test makes the delete fail and finds the children still under the Group. For a Meta-agent the stop itself lifts the children (A7), so a failed delete after the stop leaves them already lifted and the node on the Rail as `done`; the all-or-nothing clauses cover a Group and a plain Agent or Terminal only. Pads and Todos are never touched: after `rail.remove` of an Agent, `pad.list` still returns its Pads with the same `owner`, `todo.list` returns its Todos unchanged, and the user takes a Pad by `pad.setOwner` as U18 says. This is observed by an `a16_` test in `crates/rup/tests/**` against a real `rupd`, since `crates/agents` has no `pads` or `todos` dependency. An unknown id is `NOT_FOUND`. The call emits `rail.changed`. Contract change (the committee approves it; architect-c has): `rail.remove` takes `agent_NodeId` and returns `null`. Callers, all in one PR: the `METHODS` entry in `crates/contracts/src/methods.rs`, the regenerated `contracts/generated/methods.ts`, the `call` match and a delete in `crates/agents/src/lib.rs` and `rail.rs`, and the harness fake's handler in `apps/desktop/src/testing/seeds.ts`. `crates/desktop` and `rupd` need no change, because both pass any method of the `agent` and `rail` namespaces through. The kill-failure seam (a fake Terminal whose kill returns an error) lives inside `crates/agents/src/lib.rs`, since `Terminals` is a concrete type, so that test is an in-file test there. The Builder owns exactly those files plus the `a16_` tests in `crates/agents/tests/scenarios/**` and `crates/rup/tests/**`, and starts after #114 lands, since both edit `lib.rs`.

**A17 stopping an Agent leaves no program of its own behind.** Given an Agent whose fake `claude` starts a background child (`sleep 300`), writes the child's pid to a file and then waits, when `agent.stop {id}` returns, then the fake `claude` and the child are both gone within a bound the test names, and the Agent is `done` as in A7. The same holds when the fake `claude` exits by itself with the child still running: the child is gone within the bound once the Terminal's program has ended. The child was started by the Terminal's program and stays attached to it, as a shell's job or an MCP server of the real `claude` is; a child that detached on purpose (`setsid`) is out of scope. Owns `crates/agents/**` and, if the guarantee needs it, `crates/terminal/**`. Narrowing: `x6_kill_stops_the_program_and_keeps_it_listed`, `x6_kill_stops_a_program_that_ignores_hangup` and `x9_a_killed_program_is_gone_and_a_second_kill_is_not_found` keep passing as written, because X6 and X9 speak of the program and A17 adds its children. The test checks liveness by the pid in the file, never by a sleep that hopes.

**A18 a rejected Rail call changes nothing.** Given a Rail with a Group, an Agent and a Terminal, and a subscribed client, when each of these fails: `rail.move` into a descendant and under a plain Agent (`CONFLICT`), `rail.rename` of an unknown id (`NOT_FOUND`), `rail.spawnTerminal` with a `cwd` that is not a directory, `agent.spawn` with a `cwd` outside the Project folder, and `agent.spawn` whose `ROUNDUP_CLAUDE_BIN` cannot be run, then after every call `rail.tree` is byte-for-byte what it was before, `terminal.list` is unchanged, no `rail.changed` or `agent.status` event arrived, and `.roundup/agents` holds no file that was not there before. Owns `crates/agents/tests/scenarios/**`, and `crates/agents/src/**` only if a case fails today. Narrowing: A14's failed-spawn test (#114) keeps passing as written; the `agent.spawn` case with a `ROUNDUP_CLAUDE_BIN` that cannot be run is a new test, and `a4_a_rup_that_is_not_there_fails_loudly` (a missing `rup` at launch) is not narrowed. A failed `agent.spawn` may take an id it never gives back: the Rail never reuses an id, and A18 says nothing about which id the next node gets. Stacks after A14 (#114) because both assert that a failed spawn leaves no Agent.

**A30 an Agent takes a prompt.** Given an Agent whose Kind is `idle`, when the Daemon's own code calls `Agents::prompt(id, text)` (an in-process call; there is no RPC method), then `text` reaches its Terminal and is submitted as the prompt of `agent.spawn` is (A4), once, however many lines it has. An Agent of any other Kind is `CONFLICT` naming its Kind, with nothing typed; an id that names no Agent is `NOT_FOUND`; an Agent whose Kind is `done` or `error` is `CONFLICT`. The call changes no Status itself: the Agent's Kind changes only when an Observation says so (A1, A2). A call that cannot reach the Terminal returns the Terminal's error and types nothing. This is the Adapter's input seam of `PRINCIPLES.md` P4, made callable for B2 (`scenarios/messages.md`); it adds no fourth seam. The tests use the fake `claude` and the fake Terminal.
