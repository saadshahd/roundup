# Agents and the Rail

Module: `crates/agents` (+ the `rup signal` subcommand in `crates/rup`). Ids: every `A` heading in the file.

Read `spikes/hooks-state/REPORT.md` and ADR 0006 first: they define how hook Signals, the terminal title and the exit status become a Status.

**A1 signals to status.** Given an adapter replaying `spikes/hooks-state/log*.jsonl` payloads as Signals, then `UserPromptSubmit` gives `working`; `Stop` gives `idle`; `PermissionRequest` gives `needs-you` whose label quotes the question or tool; `StopFailure` gives `error` whose label is the `error` field; `PostToolUse` after a `needs-you` gives `working`; `SessionEnd` gives `done`. The mapping is a pure function `observe(Observation) -> Option<Status>` with `since` set by an injected clock.

**A2 title closes the silent gaps.** Given the title Observations in `spikes/hooks-state/screen.jsonl`, then a ◐/◑ title gives `working`; an ✳ title after an Esc interrupt gives `idle`; an ✳ title that follows a `PreToolUse` Signal is held for `STAR_HOLD` (a named constant, 200 ms, derived from the fixtures: across 9 dialogs the star lands 9–80 ms after `PreToolUse` and 18–79 ms before its `PermissionRequest`; the hold is measured from the star and leaves about 2.5 times the largest gap): if the `PermissionRequest` arrives within `STAR_HOLD` the Agent goes straight to `needs-you` with no `idle` between, and otherwise a `Tick` after `STAR_HOLD` resolves the held star to `idle` (so an Esc interrupt during an auto-allowed tool run reads `idle` after `STAR_HOLD`, never stuck at `working`); and a ◐/◑ title never clears `needs-you`. A denied dialog gives a spinner, not a star, in the fixtures, so `needs-you` holds until the next `UserPromptSubmit` or a `PostToolUse` after a Yes. Esc on a dialog fires no hook and no title in the fixtures, so for an Agent with no live `rup permission` hook it does not clear `needs-you` (with one, Esc or No gives `Dismissed` and so `idle`, H9); a star never ends `needs-you`, `error` or `done`. A replay of the real deny in `screen3` with its own hooks must not read `working` while Claude waits at its prompt.

**A3 exit.** Given a Terminal behind an Agent, when it exits with code 0 the Status is `done`; with a non-zero code it is `error` with label `exited <code>`; killed by a signal it is `error` with label `exited by signal`. A Signal arriving after exit is ignored.

**A4 spawn.** Given `agent.spawn {cwd, prompt}` with `ROUNDUP_CLAUDE_BIN` pointing at a fake `claude` script (tests never run the real one), then a Terminal starts running it with a per-Agent `--settings` file with one command hook per event in `STATE_EVENTS`: `rup signal <agent-id>` for every event except `PermissionRequest`, which runs `rup permission <agent-id>` (E3 adds a second command on `SessionStart`), the hook command is the absolute path of the `rup` beside the running `rupd` with a 5-second timeout, except `PermissionRequest`, whose hook has a 86400-second timeout (H9), the working directory is pre-trusted only when it lies inside the Project folder (any other is `INVALID_PARAMS`, and so is the user's home folder, which is never trusted), `rup signal` never exits 2, the Agent appears in `rail.tree` with `kind: agent`, and the prompt is sent as a Steer (H11) at the first `SessionStart`. `rup signal <agent-id>` reads one hook payload from stdin, identifies as that Agent, and calls `agent.signal`.

**A5 signal path.** Given an Agent, when `agent.signal {id, payload}` arrives, then the adapter updates the Status and, only if it changed, emits `agent.status {id, status}`. A payload the adapter does not recognise is ignored and logged to stderr, never an error to the caller.

**A6 rail tree.** Given Workstreams and Agents, then `rail.createWorkstream {name, parent}`, `rail.rename` and `rail.move {id, parent, index}` keep sibling `order` values contiguous from 0, emit `rail.changed`, and fail with `CONFLICT` when a node would move into its own descendant or under a Terminal, when a Terminal would move under an Agent (A26's Subagents come only from `agent.spawn`), or when a Workstream would be created or moved under any node (A26: Workstreams are flat, so `parent` of a Workstream is `null`). `rail.createWorkstream` persists one Workstream with a stopped Door; it does not start a program. `rail.tree` returns nodes ordered parent-first, then by `order`. A Workstream stored nested loads flat (A26). Narrowing (O3): `rail.createWorkstream` also takes an optional `order`, which its Door holds.

**A7 a Workstream survives its Door.** Given a Workstream with two running Agent children, when `rail.startDoor {id}` is called, then exactly one Door starts under that Workstream id and the Workstream reports its Status and `terminal_id`. A concurrent start, or a start while the Door's Terminal is actually live, fails with `CONFLICT` without another Terminal, even if a heuristic Status says `done`. `agent.stop {id}` stops the Door, leaves its Status `done`, and preserves the Workstream id, name, parent, order and every child's parent and running state. Natural exit has the same membership guarantee (A3 determines Status); neither path restarts automatically. Calling `rail.startDoor` after stop, exit or failed start starts the same Door id with a new Terminal. A failed start reports its error, leaves no live Door or partial launch files, and keeps the Workstream and its children so retry needs no replacement Workstream. After restart, an Exit, title, Tick or Signal from the previous Door incarnation cannot change the new Door's Status, Terminal, membership, files or pending work; deterministic observers hold each old observation across stop/retry, release it after the new run starts, and find the new Door still live and unchanged. Unknown or removed ids fail without creating a Workstream; late events cannot resurrect a removed Workstream. Observe success, concurrent rejection, stop, natural exit, failed start and retry with deterministic fake `claude` through the real Daemon; compare ids, parent/order, Terminal counts and child liveness, not a seeded tree.

**A8 persistence.** Given a Rail containing Workstreams with children and both running and stopped Doors, when `Agents::open` runs again on the same directory, then Workstream ids, names, order and membership are intact (a Workstream stored under another loads at the root, A26); each Door without a live Terminal reports `done`, with `terminal_id: null`. Reopening starts no program. `rail.startDoor` then works on the same Workstream id. Opening an existing database containing either kind of legacy Group preserves these same ids and memberships and exposes only Workstream nodes. The observer closes and reopens the real persisted Rail and starts the Door again; it does not recreate the fixture after reopening.

**A9 name from the first prompt.** Given `agent.spawn` without a prompt, then the Agent's Rail name is `new-agent`. When its first `UserPromptSubmit` Signal arrives, then the node is renamed from the payload's `prompt` and `rail.changed` is emitted. The name is the prompt lower-cased, split on anything that is not a Unicode letter or digit (Rust's `char::is_alphanumeric`), with `a an the to of in on for and please` dropped, the first three remaining words joined by `-`, cut to 32 characters with no trailing `-`: "Fix the refresh race in token.ts" gives `fix-refresh-race`. A prompt with no words left keeps the current name. Later prompts never rename it, and a `rail.rename` made before the first prompt wins over it. An Agent spawned with a prompt is named by the same rule when that prompt is submitted. A Door never renames its Workstream from a prompt. Narrowing (O2): an Agent spawned without a prompt now holds a Clarification order; its naming rule is unchanged.

**A10 a Terminal in the Rail.** Given `rail.spawnTerminal {cwd, parent}`, then a Terminal runs the user's login shell in `cwd`, and a node `{kind: terminal, name, terminal_id}` is placed last under `parent` with `rail.changed` emitted. `name` is the basename of `$SHELL`, else `shell`. `parent` follows A6: under a plain Agent or a Terminal it is `CONFLICT`, and an unknown id is `NOT_FOUND`. A `cwd` that is not a directory is `INVALID_PARAMS` and adds no node. When the program exits, the node stays in the Rail with `status: null`.

**A11 Todos and Pads over MCP.** Given `agent.spawn`, then Claude Code also gets `--mcp-config <file>`, where the file is `.roundup/agents/<id>.mcp.json` and declares one stdio server `roundup` whose command is the absolute `rup` path the hooks use, with args `mcp <id>`. The config adds to the user's own servers: `--strict-mcp-config` is never passed. The per-Agent settings file allows `mcp__roundup__*`, so these tools never raise a permission dialog. `RUPD_SOCKET` is not written into either file, because stdio servers and hooks inherit Claude Code's environment, which inherits the Daemon's. Tests read the argv and the two files; they never run `claude`. The flag and the allow rule follow code.claude.com/docs (cli-reference, permissions, mcp), read on 2026-10-01.

**A12 a reopened Rail never names another run's Terminal.** Given a Rail persisted by an earlier Daemon run, when `Agents::open` runs, then no node carries a `terminal_id` from that run. Terminal ids restart at 1 with every run, so an old id could name a new, unrelated Terminal. Agents come back `done` as in A8, and Terminal nodes come back with `terminal_id: null`. A12 replaces the two assertions in the agents stack that a reopened node keeps its old `terminal_id`: `a8_an_agent_whose_terminal_is_gone_comes_back_done` (`spawn.rs`) and `a8_a_meta_agent_keeps_its_flag_across_reopening_and_comes_back_done` (`promote.rs`). Both now expect `terminal_id: null`.

Deferred past Phase 2: `blocked` for Agents (needs Todo ownership), Doors receiving child events (needs the message bus), the Claude-trust-dialog screen scrape.

**A13 a symlinked agents directory is refused.** Given `.roundup/agents` under the Project is a symlink, when `agent.spawn` runs, then it fails with `INVALID_PARAMS` naming the path, and no per-Agent settings or MCP config file is written, neither through the link nor beside it. A real directory, and a missing one that the spawn creates, work as before. Narrowing: `a4_a_symlinked_config_is_written_through_and_stays_a_link` and `a4_a_symlink_planted_where_a_file_goes_is_replaced_not_written_through` are about a config file, not the directory, and keep passing as written.

**A14 a Signal that arrives early is held and applied.** Given an Agent whose Terminal has started but whose `agent.spawn` has not yet finished registering it, when `agent.signal {id, payload}` arrives for it, then the Signal is held and applied in arrival order as soon as the Agent is registered, exactly as A5 says (the Status updates and `agent.status {id, status}` is emitted if it changed), before any Signal that arrives later. The call returns success, so `rup signal` exits 0 and the Agent is never `error` because of it. At most 8 Signals are held for one Agent; the ninth and each later one drops the oldest held Signal, which is logged to stderr as A5 does for what it ignores, and the other eight are still applied in arrival order. If the spawn then fails (the Terminal cannot be attached to the Rail or cannot start), `agent.spawn` fails with its own error as today, no Agent exists, the held Signals are discarded and nothing is announced for it. An id that was never spawned still gets `NOT_FOUND`. The test holds the window open instead of racing it: a fake Terminal start that does not return until the test has sent the Signal (the seam is the Builder's choice, and it is a test seam, not a public function), so the test fails before the fix on every run, with no load and no timing. The same test, with the spawn then made to fail, covers the discard. `d4_ten_idle_agents_cost_the_daemon_less_than_150_mb` stays as the end-to-end proof.

**A15 a clean environment for every program the Daemon starts.** Given a Daemon whose own environment holds session markers, which are `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` (it was started from inside a Claude Code session), when `agent.spawn`, `rail.spawnTerminal` or `terminal.spawn` starts a program, then that program's environment holds none of them. Every other variable passes through, `PATH`, `HOME` and `SHELL` included, and so does the user's own Claude Code configuration (`CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_MAX_OUTPUT_TOKENS` and the like): that is a decision, because only the markers name a running session and a login or a setting is the user's. Found in the demo app: Claude Code in an Agent printed "Transcript saving is off, inherited CLAUDE_CODE_CHILD_SESSION marker". The test starts a real `rupd` with those markers, `CLAUDE_CODE_OAUTH_TOKEN` and `CLAUDE_CODE_USE_BEDROCK` in its environment (as `crates/rup/tests/signal.rs` starts one), spawns a Terminal through `terminal.spawn`, writes `env > <file>` to it, and checks that no marker is in the file and that the other three are, `PATH` included; one case does the same through `agent.spawn` with a fake `claude` that writes its environment. The removal is in the Terminal's spawn call, but the Terminal names no vendor (P4): `crates/agents/src/claude_code/` owns the list of markers, and the Daemon hands it to `Terminals::open`, which removes those names from every program it starts. `SpawnParams` gains no field, since that would be a contract change. The Builder owns `crates/terminal/**`, `crates/agents/src/claude_code/**`, `crates/rupd/src/lib.rs` and `crates/rup/tests/**`, and starts after #114 lands, since both edit `crates/agents/src/lib.rs`.

**A16 remove a node.** Given a Rail node, when `rail.remove {id}` arrives, then a running Agent is stopped as `agent.stop` does and a running Terminal is killed, and the node is deleted from the Rail; the siblings after it keep their order. For a Workstream, its Door is stopped and the Workstream is deleted; only this explicit removal lifts its children to its parent at its place, in their order. Stopping the Door alone never lifts children (A7). The stop comes first, in the order `agent.stop` uses. If stopping fails (the test makes a fake Terminal's kill return an error), the call returns that error and deletes nothing: the node stays at its place under its parent, with its children, and its status is whatever `agent.stop` left, so a second `rail.remove` can retry. If the stop worked and the delete then fails, the node stays on the Rail with its exited Agent, and a second `rail.remove` removes it. For a Workstream, lifting children and deleting the Workstream are one transaction: a failed delete leaves all children in the Workstream even after its Door stopped. Pads are never touched, and Todos are touched only by T13's Home reset for a removed Workstream (`crates/rupd` owns that step: it intercepts `rail.remove` after `crates/agents` returns, since `crates/agents` has no `todos` dependency, so `rupd` no longer passes `rail.remove` through unchanged): after `rail.remove` of an Agent, `pad.list` still returns its Pads with the same `owner`, `todo.list` returns its Todos unchanged, and the user takes a Pad by `pad.setOwner` as U18 says. This is observed by an `a16_` test in `crates/rup/tests/**` against a real `rupd`, since `crates/agents` has no `pads` or `todos` dependency. An unknown id is `NOT_FOUND`. The call emits `rail.changed`. Contract change (the committee approves it; architect-c has): `rail.remove` takes `agent_NodeId` and returns `null`. Callers, all in one PR: the `METHODS` entry in `crates/contracts/src/methods.rs`, the regenerated `contracts/generated/methods.ts`, the `call` match and a delete in `crates/agents/src/lib.rs` and `rail.rs`, and the harness fake's handler in `apps/desktop/src/testing/seeds.ts`. `crates/desktop` needs no change, because it passes any method of the `agent` and `rail` namespaces through; `rupd` passes them through too, except for T13's step on `rail.remove`. The kill-failure seam (a fake Terminal whose kill returns an error) lives inside `crates/agents/src/lib.rs`, since `Terminals` is a concrete type, so that test is an in-file test there. The Builder owns exactly those files plus the `a16_` tests in `crates/agents/tests/scenarios/**` and `crates/rup/tests/**`, and starts after #114 lands, since both edit `lib.rs`.

**A17 stopping an Agent leaves no program of its own behind.** Given an Agent whose fake `claude` starts a background child (`sleep 300`), writes the child's pid to a file and then waits, when `agent.stop {id}` returns, then the fake `claude` and the child are both gone within a bound the test names, and the Agent is `done` as in A7. The same holds when the fake `claude` exits by itself with the child still running: the child is gone within the bound once the Terminal's program has ended. The child was started by the Terminal's program and stays attached to it, as a shell's job or an MCP server of the real `claude` is; a child that detached on purpose (`setsid`) is out of scope. Owns `crates/agents/**` and, if the guarantee needs it, `crates/terminal/**`. Narrowing: `x6_kill_stops_the_program_and_keeps_it_listed`, `x6_kill_stops_a_program_that_ignores_hangup` and `x9_a_killed_program_is_gone_and_a_second_kill_is_not_found` keep passing as written, because X6 and X9 speak of the program and A17 adds its children. The test checks liveness by the pid in the file, never by a sleep that hopes.

**A18 a rejected Rail call changes nothing.** Given a Rail with a Workstream, an Agent and a Terminal, and a subscribed client, when each of these fails: `rail.move` into a descendant and under a plain Agent (`CONFLICT`), `rail.rename` of an unknown id (`NOT_FOUND`), `rail.spawnTerminal` with a `cwd` that is not a directory, `agent.spawn` with a `cwd` outside the Project folder, and `agent.spawn` whose `ROUNDUP_CLAUDE_BIN` cannot be run, then after every call `rail.tree` is byte-for-byte what it was before, `terminal.list` is unchanged, no `rail.changed` or `agent.status` event arrived, and `.roundup/agents` holds no file that was not there before. Owns `crates/agents/tests/scenarios/**`, and `crates/agents/src/**` only if a case fails today. Narrowing: A14's failed-spawn test (#114) keeps passing as written; the `agent.spawn` case with a `ROUNDUP_CLAUDE_BIN` that cannot be run is a new test, and `a4_a_rup_that_is_not_there_fails_loudly` (a missing `rup` at launch) is not narrowed. A failed `agent.spawn` may take an id it never gives back: the Rail never reuses an id, and A18 says nothing about which id the next node gets. Stacks after A14 (#114) because both assert that a failed spawn leaves no Agent.

**A20 each launch is one Attempt.** Given an Agent or a Door, when the Daemon launches its program (A4's spawn, A7's `rail.startDoor`, A22's resume), then that launch gets the Agent's next Attempt: a per-Agent ordinal from `1`, so two of one Agent compare by launch order, and nothing else is read from it. A4's settings file is rewritten for each launch, and its hook command, not the program, carries the Attempt in its environment; `rup signal <agent-id>` forwards it as `agent.signal {id, attempt, payload}`, with its positional arguments unchanged. The Terminal watcher tags that launch's title and exit Observations with the same Attempt. Only an Observation carrying the current Attempt changes Status, acknowledges a start (A22) or saves continuation data (A21). One from an earlier Attempt is ignored and logged to stderr by event name, never an error to the caller, even when it names the same vendor conversation as the current run. A missing `attempt` is `INVALID_PARAMS`. A14 holds Signals only for the pending launch's Attempt and ignores an older one instead of holding it. A20 is the mechanism behind A7's "previous Door incarnation" clause. Narrowing: A4, A5 and A14's `agent.signal {id, payload}` becomes `{id, attempt, payload}`; The hook command becomes `ROUNDUP_ATTEMPT='<attempt>' '<rup>' signal '<id>'`: `a4_the_settings_hold_exactly_one_signal_command_per_state_event` (`crates/agents/tests/launch.rs`) and `a4_spawn_runs_claude_with_the_agents_settings_and_lists_an_agent` (`crates/agents/tests/scenarios/spawn.rs`) assert that form with the launch's Attempt, and a second launch's settings name a different one; `a4_signal_signals_the_agent_as_that_agent` also asserts the Attempt is forwarded, and the `a5_` and `a14_` tests take the Attempt from the current launch. Contract change (rule 4): `SignalParams` gains `attempt: string`, with the hook caller in the same PR; `GLOSSARY.md` gains **Attempt** ("one launch of an Agent's program; internal to the Daemon and its hook, never a Rail identity or a vendor conversation id") in that PR. Observers: `a20_` cases hold an old Signal, title and exit, start a new Attempt, release them, and find the new run's Status and Terminal unchanged.

**A21 an Agent keeps its conversation.** Given a launched Agent or Door, when a Signal of the current Attempt names its conversation, then the Adapter saves that conversation id and the effective working directory (after Worktree mapping, any subdirectory kept) in `agents.db` before it applies the Signal. For Claude Code this is `SessionStart`'s `session_id`, accepted only as a UUID. Only `crates/agents/src/claude_code/` reads vendor fields; no vendor id or history path enters a public name or reaches the webview. The saved id is the one the latest such Signal named; clearing and compacting the conversation are the Agent's own, and roundup does nothing for them. A Signal from an earlier Attempt never replaces it (A20). If the save fails after `agent.spawn` returned, `agent.signal` fails with the storage cause, the Agent's Status becomes `error` with label `cannot save conversation: <cause>` (emitted as `agent.status`, and kept when the Terminal's exit follows, unlike A7's `done` after a stop), and its Terminal is stopped; in A14's window the held Signal is saved before `agent.spawn` returns, and a failed save fails the spawn as A14's failed spawn does. The saved data survives `Agents::open` while A8/A12 still clear old Terminal links. An Agent saved before A21 has no data, and none is guessed from its name, Terminal or files. Observers: `a21_` cases for capture, a non-UUID id, a later Signal naming another id, a failed save before and after `agent.spawn` returns, a nested cwd with Worktrees on and off, and reopen.

**A22 resume an exited Agent.** Given an Agent that is not a Door, whose Terminal has exited and which has A21 data, when `agent.resume {id}` is called, then it returns the same `RailNode` with a new `terminal_id` and emits `rail.changed`. Id, name, parent, order, Worktree, Pads, Todos and Routes are unchanged; A9 never renames it again. The program runs in the saved directory with the saved Worktree path, branch and Base (checked against Git first), even if the Project's `worktrees` setting changed since. It never provisions a new Worktree, falls back to the Project root, starts a fresh conversation, forks one, picks the most recent one, or types the original prompt again. For Claude Code the argv adds `--resume <saved id>`. The call succeeds only after the new Attempt's `SessionStart` arrives with source `resume` and the saved id; without one in 10 seconds of the injected clock it fails with `CONFLICT`. While it is pending, the Agent's `can_resume` is false (one `rail.changed`, still naming the old `terminal_id`); the new `terminal_id`, its Status and any `agent.status` for it are announced only after acknowledgement. On failure, the new Terminal is stopped, and once it has exited `can_resume` returns to true with one `rail.changed`; the old node, its old `terminal_id` and its last Snapshot stay, the Worktree and its files are never removed, and the cause is the error. The Daemon serializes resume with `agent.stop` and `rail.remove` on the Agent id: whichever claims it first wins, and the other returns `CONFLICT` (or `NOT_FOUND` after a removal); there is never a second running Terminal for one Agent, including when a rollback kill fails. Errors: an unknown id is `NOT_FOUND`; a Workstream, a Terminal, a running Agent (whatever its Kind), missing data, a concurrent resume, or a missing, detached or mismatched directory is `CONFLICT` with that reason. A Snapshot of the old Terminal is never fed into the new one. Contract change (rule 4): `agent.resume` takes `agent_NodeId` and returns `agent_RailNode`; `RailNode` gains `can_resume: boolean`, true only for an exited Agent or Door with A21 data and no start in flight. Every change to it emits `rail.changed`, including the watcher's after an exit, so a client that fetched the tree while the Agent ran sees `true` without reloading. `GLOSSARY.md`'s **Agent** becomes "one supervised identity on the Rail, with a Status; each launch of its program is an Attempt, and at most one runs at a time", and gains **Resume** ("starting an exited Agent's next Attempt in its saved conversation"), in that PR. Observers: failing `a22_` cases first, through the real `rupd` with a fake `claude` that records argv and cwd and replays `SessionStart` with source `resume`; plus timeout, wrong source, wrong id, failed launch and rollback, both orders against stop and remove, refresh of `can_resume` after exit, and A12 after reopen. A separate authenticated smoke records `claude --version`, says a unique phrase, exits, resumes through roundup, recalls the phrase, then repeats after a Daemon reopen; `claude --help`'s `--resume [value]` (2.1.283, 2026-10-03) is not that proof.

**A23 a restarted Door keeps its conversation.** Given a Workstream whose Door has exited and has A21 data, when `rail.startDoor {id}` is called, then the Door resumes its conversation through A22's launch, acknowledgement, rollback, serialization and Worktree rules, and A7's guarantees for the Workstream and its children hold unchanged. A Door with no A21 data, its first start included, starts fresh as A7 says. A saved conversation that cannot be resumed fails with A22's error and never starts fresh in its place. An explicit "start fresh" for such a Door is deferred; until it exists, the user removes the Workstream and creates another. Observers: `a23_` cases through the real `rupd`: start, exit, restart with the saved id in argv; restart after reopen; restart with missing history failing without a fresh start; and A7's old-incarnation cases with A20 Attempts.

**A24 starting a closed Workstream's Door returns or fails, never hangs.** Narrows A7 and A23. Given a Workstream whose Door was stopped or exited in this Daemon run, or whose Daemon was restarted since (A8, A12), with or without A21 data, with children running and with the saved conversation present, missing or unresumable, when `rail.startDoor {id}` is called, then the call settles within 10 000 ms with either the Workstream's node holding a live Door (A7, A23) or an error whose message tells the user what to do (A22's code for an unresumable conversation); it never waits on an acknowledgement that cannot arrive, and a failure leaves no `Starting` or `Resuming` slot, so an immediate second `rail.startDoor` is answered by A7's rules and not `CONFLICT` from a stuck start. While the call is pending the Daemon still answers `rail.tree` and `agent.stop` for other ids. In the App, `start Door` (U9) shows the pending state, then the Door's Terminal (success) or `✕ <message>` with `retry Door` (failure) within the same bound; the Rail stays clickable and the pane's width and height do not change. Tests (`a24_`) through the real `rupd` with deterministic fake `claude`: close in this run then start (`a24_start_after_close_in_this_run_settles_within_the_bound`); reopen the Daemon then start (`a24_start_after_reopen_settles_within_the_bound`); a fake that never sends `SessionStart` (`a24_a_start_never_acknowledged_fails_within_the_bound`); a saved conversation the fake rejects (`a24_an_unresumable_conversation_fails_with_a22s_code`); each asserts the 10 000 ms bound and the node or error, and, while pending, a concurrent `rail.tree` and an `agent.stop` for another id are answered. `a24_a_failed_start_leaves_no_slot` asserts that after each failure an immediate second `rail.startDoor` gets A7's answer and not `CONFLICT`. App tests (`u9_`-suite on the fake App seam, `a24_` prefix): `a24_a_pending_start_keeps_the_rail_interactive_and_the_pane_size` leaves a `rail.startDoor` pending, clicks other rows, shows the pending state and measures the pane unchanged; `a24_a_late_failure_shows_the_error_and_retry_door`; `a24_a_start_that_succeeds_shows_the_doors_terminal`.

## Workstream/Door structural slice (A6–A9, A12, A16; U6/U8/U9/U62; G2/G6)

Approved product direction is `docs/wireframes.md`'s Workstream/Door section. This slice replaces public Group/Meta-agent vocabulary atomically: `NodeKind::Group` becomes `Workstream`, `CreateGroupParams`/`rail.createGroup` become `CreateWorkstreamParams`/`rail.createWorkstream`, `rail.promote` becomes `rail.startDoor`, and `RailNode.meta` disappears. ### Attempt transport (A20 in this slice)

This slice builds A20's Attempt for Doors and plain Agents. Every launch allocates the Agent's next Attempt before it runs, including a launch that fails; the Daemon numbers them from `1`, so a caller may compare two of one Agent but reads nothing else from one. `RailNode.attempt` is the last allocated, or `null` before the first; it is not liveness. `SignalParams` and `StatusEvent` carry the required `attempt` string: a canonical positive decimal within SQLite's signed 64-bit range. The settings file is rewritten for each launch and its hook command, `ROUNDUP_ATTEMPT='<attempt>' '<rup>' signal '<id>'`, carries the Attempt; the program's own environment does not. `rup signal <agent-id>` forwards it and rejects a missing or malformed value before connecting. No Actor field or credential is added.

A missing or malformed `attempt` is `INVALID_PARAMS`. A Signal, title, Tick or Exit from an earlier Attempt while a later one is starting or running is ignored and logged to stderr by event name, never an error to the caller, and has no state or bus effect (A20). An unknown or removed id, or an Agent with no starting or running launch, is `NOT_FOUND`; a launch that is stopping is `CONFLICT`. Signals of the pending Attempt keep A14's bounded ordering. The same (Agent id, Attempt) pair privately binds Agent-addressed Message acceptance and Takeovers; delayed earlier status events and receiver lookups cannot affect a later Attempt. Reopen keeps the numbering and starts no program. This changes neither Message/Route/Takeover wire contracts nor M3/M5/M7 finality laws and claims no automatic Terminal delivery. A21 to A23 build on this Attempt unchanged.

Status transitions within an Attempt also carry a canonical positive `status_revision`: `1` at Starting, increasing only when Status changes, independent of wall-clock ties. `RailNode.status_revision` is absent after reopening without a live attempt. The Rail snapshot and emitted Status use the same revision. Messages and Takeovers privately bind both ordinals: delayed Error/Done at revision E closes only bindings through E; a genuinely later recovery can accept new work without reviving older final Messages. Idle E consumes only Messages accepted before E. Stale receiver reads and delivery refusals cannot reopen closed bindings. The App ignores older or duplicate revisions. This ordering amendment adds no Signal field and no Message/Takeover wire field.
