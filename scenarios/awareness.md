# Agent awareness

Module: `crates/agents` (the Brief file and the Claude Code flag and hook, under `claude_code/`, P4) and `crates/rupd` (`agent.context` and `agent.brief`, which read Todos and the Rail; `crates/agents` has no Todos dependency), `crates/rup` (the `rup context` subcommand and the MCP tool), with end-to-end tests in `crates/rup/tests`. Term: Brief (`CONTEXT.md`). Principles served: P1, P3 and P4 (`PRINCIPLES.md`). Design: `docs/awareness.md`. An Agent is an unmodified Claude Code: it is told who it is by the vendor's own injection points, never by editing the user's files and never by reading its screen. Tests run a fake `claude` (`ROUNDUP_CLAUDE_BIN`, A4) and read argv and files; E7 is the one scenario that runs the real `claude`. Contract change (the committee approves it with the first Builder PR, as B's did): `agent.context` and the MCP tool named below are new.

**E7 the spike comes first.** Given the installed `claude` and a throwaway directory, when `spikes/context-injection/run.sh` starts it interactively with `--append-system-prompt-file` naming a file that holds a fixed word, with a `SessionStart` command hook that prints `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "<another fixed word>"}}`, and with `--mcp-config` naming a stdio server that records when it is started, then `spikes/context-injection/REPORT.md`, written by the Builder on the laptop (a VM only if it holds the `CLAUDE_CODE_OAUTH_TOKEN` secret as `AGENTS.md` describes), after the prompt "state the two words you were given" and a second prompt that asks the model to call the server's tool, records, for each of the three, whether the model could state its word and whether the server started before the first prompt, and the version of `claude` it ran on. E1, E3 and E6 follow the report: a clause the report contradicts is rewritten in the same PR as the Builder's code. The three claims are in the vendor's docs (cli-reference, hooks, mcp, read on 2026-10-02) and not yet observed here.

**E1 the Brief's file.** Given `agent.spawn` (A4), then Claude Code also gets `--append-system-prompt-file <Project folder>/.roundup/agents/<id>.brief.md`, and the file holds the first part of the Brief: the Agent's id (ids never change and are never reused, A19), that roundup started it and supervises it, and the tool names `agent_context` (E4), `message_send` (B12) and each of M1's tools, each with one line on when to use it. It holds no name, no Terminal, no parent, no peer and no Todo, because those change (`rail.rename` changes a name, A9; Terminal ids restart, A12); the second part, which holds them, is E3's start text. The flag is added to the argv the user's own settings already produce and replaces none of it. The spawn writes nothing beyond the files A4 and A11 already write and this one: `CLAUDE.md`, `.claude/` and the user's settings are the same bytes after it. Spawning twice for the same id writes the same text. A test reads the argv and the file, and checks that each tool name appears in it; the wording is not tested.

**E2 the context.** Served by `crates/rupd`, which holds both the Rail and the Todos. Given a Rail with a Meta-agent `m` and Agents `a` and `b` under it, and a plain Group `g` holding Agent `c`, when `agent.context {id}` arrives from Agent `a` for its own id, then it returns `{self: {id, name, status}, parent: {id, name, node} | null, ask: {to}, peers: [{id, name, status}], todos: [{id, title, blocked}]}`. `status` is the Agent's Status (`{kind, label, since}`), so no field here means a node kind except `parent.node`, which is `"group"` or `"meta-agent"`. `parent` is the node `a` sits under, and `null` when `a` sits at the Project root. `peers` are the other Agents under the same parent, in Rail order, never `a` itself and never a Terminal or a Group; a sibling Meta-agent's Agent is a peer. `ask.to` is the id of the Agent at the parent when the parent is a Meta-agent (here `m`), and `"you"`, the user's Actor id (`Actor::user()`), when the parent is a plain Group or `null` (a Message to `"you"` is B10's; B1 and B10 name the user by that id). `todos` are the Todos whose `creator` is `a` (T8) that are not complete, `blocked` true when one has an incomplete blocker. For `c` the result has `ask: {to: "you"}` and `peers: []`. A call from an Agent for another Agent's id is `FORBIDDEN`; from the user, any Agent's id works; an id that names no Agent is `NOT_FOUND`. The call changes nothing and logs no Touch.

**E3 told at start.** Given `agent.spawn`, then the per-Agent settings file (A4) has a second `SessionStart` command hook besides `rup signal`, `<absolute rup path> context <agent-id>` with a 5-second timeout (A4's settings test changes to expect two commands on that event). When `rup context` runs, it identifies as that Agent, calls `agent.brief {id}` and prints the `stdout` string of the result verbatim and nothing else, exiting 0. `agent.brief {id}` returns `{stdout: string}`; the Agent itself or the user may call it, another Agent is `FORBIDDEN`, an id that names no Agent is `NOT_FOUND`; it changes nothing and logs no Touch. The Daemon builds that string, and the vendor's own JSON shape for it (for Claude Code, `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": <text>}}`) lives in `claude_code/` as `agent.signal`'s payload parsing does, so `rup` holds no vendor string (P4). `<text>` is E2's result in glossary words: the parent, who to ask, the peers (id, name, Kind) and the open Todos, each on its own line. When the Daemon does not answer, or accepts the connection and does not answer within 4 seconds, `rup context` prints one line on stderr naming the socket, prints nothing on stdout and exits 0, so it never blocks the Agent's start (the model test is `a4_signal_to_a_daemon_that_never_answers_exits_1_in_time`, with exit 0). The fake `claude` in the test runs the command from the settings file and the test reads its stdout and exit code.

**E4 asking again.** Given `rup mcp <agent-id>` on stdio (M1), when an MCP client lists tools, then `agent_context` is offered besides M1's and B12's, named after `agent.context` with the dot replaced by `_`, taking no input. A call returns E2's result for that Agent as the tool's text. After `rail.move` puts the Agent under another parent, the next call returns the new parent, `ask` and peers, so the Agent can refresh what E3 told it at start.

**E5 asking the Meta-agent.** Given a Meta-agent `m` and its child `a`, when `a` calls `agent_context` and then `message_send {to: <ask.to>, kind: "question", body}` (B12), then the Message is delivered to `m` as B2 says. Given `c` under a plain Group, the same two calls store the Message to the user and type nothing anywhere (B10). An Agent that sends to a peer's id from `peers` gets B2's delivery too. No new method is involved: this scenario fixes that E2's `ask.to` is a valid `to` for B1.

**E6 no channel is loud.** Given an Agent just spawned, then its node in `rail.tree` has `channel: "pending"`; every other node (a Group, a Terminal, an Agent with no live Terminal) has `channel: null`. The Channel is the connection `rup mcp <id>` holds to the Daemon (`CONTEXT.md`). At start, before it serves any tool call, `rup mcp <id>` calls `agent.channelUp {id}` once (it returns `null`; only that Agent may call it, so the user or another Agent is `FORBIDDEN`; an id that names no Agent is `NOT_FOUND`; a second call while `channel` is already `up` succeeds and emits nothing; this narrows M3, which had it connect only per call); a hook such as `rup signal` or `rup context` never calls it, and `daemon.identify` is not the signal. When `agent.channelUp` has not arrived 15 seconds after `agent.spawn`, then the node's `channel` is `"missing"`, one `agent.channel {id, channel}` event is emitted, the Agent's Kind and Status are unchanged, and nothing interrupts the user (P3). When it arrives at any time, `channel` becomes `"up"` and `agent.channel` is emitted once. Three cases with a fake `claude`: one that starts the shim at once goes `pending` to `up` and never to `missing`, with the default deadline; one that runs the `SessionStart` hooks (`rup signal` and `rup context`) but never starts the shim still reaches `missing`; one that starts the shim only after the deadline goes `missing` then `up`. The 15 seconds is a Daemon constant a test shortens through `ROUNDUP_CHANNEL_DEADLINE_MS`. Contract change: `RailNode` gains `channel`, `agent.channel` is a new event, and `agent.channelUp` and `agent.brief` are new methods, specified below. The Rail's `no channel` Chip is a webview scenario, E8, reserved. If E7's report shows that Claude Code starts MCP servers only on the first tool call, this clause is rewritten there, not guessed here.
