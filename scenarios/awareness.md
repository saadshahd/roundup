# Agent awareness

Module: `crates/agents` (the `agent.context` method; the Claude Code flag and hook live under `claude_code/`, P4), `crates/rup` (the `rup context` subcommand and the MCP tool), with end-to-end tests in `crates/rup/tests`. Term: Brief (`CONTEXT.md`). Principles served: P1, P3 and P4 (`PRINCIPLES.md`). Design: `docs/awareness.md`. An Agent is an unmodified Claude Code: it is told who it is by the vendor's own injection points, never by editing the user's files and never by reading its screen. Tests run a fake `claude` (`ROUNDUP_CLAUDE_BIN`, A4) and read argv and files; E7 is the one scenario that runs the real `claude`. Contract change (the committee approves it with the first Builder PR, as B's did): `agent.context` and the MCP tool named below are new.

**E7 the spike comes first.** Given the installed `claude` and a throwaway directory, when `spikes/context-injection/run.sh` starts it interactively with `--append-system-prompt-file` naming a file that holds a fixed word, with a `SessionStart` command hook that prints `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "<another fixed word>"}}`, and with `--mcp-config` naming a stdio server that records when it is started, then `spikes/context-injection/REPORT.md` records, for each of the three, whether the model could state its word and whether the server started before the first prompt, and the version of `claude` it ran on. E1, E3 and E6 follow the report: a clause the report contradicts is rewritten in the same PR as the Builder's code. The three claims are in the vendor's docs (cli-reference, hooks, mcp, read on 2026-10-02) and not yet observed here.

**E1 the Brief.** Given `agent.spawn` (A4), then Claude Code also gets `--append-system-prompt-file <Project folder>/.roundup/agents/<id>.brief.md`, and the file holds the Brief: the Agent's id and name, that roundup started it and supervises it, the Terminal it runs in, and one line each for the tools `agent_context` (E4), `message_send` (B12), `todo_*` and `pad_*` (M1) saying when to use them. It names no peer, parent or Todo, because those change. The flag is added to the argv the user's own settings already produce and replaces none of it. No file outside `.roundup/agents/` is written or edited (`CLAUDE.md`, `.claude/` and the user's settings are the same bytes after the spawn), and spawning twice writes the same text for the same id and name. Tests read the argv and the file.

**E2 the context.** Given a Rail with a Meta-agent `m` and Agents `a` and `b` under it, and a plain Group `g` holding Agent `c`, when `agent.context {id}` arrives from Agent `a` for its own id, then it returns `{self: {id, name, kind}, parent: {id, name, nodeKind}, ask: {to}, peers: [{id, name, kind}], todos: [{id, title, blocked}]}`. `parent` is the node `a` sits under. `peers` are the other Agents under the same parent, in Rail order, never `a` itself and never a Terminal or a Group. `ask.to` is the id of the Agent at the parent when the parent is a Meta-agent (here `m`), and `"user"` when it is a plain Group or the Project root (Messages to the user are B10's). `todos` are the Todos whose `creator` is `a` (T8) that are not complete, `blocked` true when one has an incomplete blocker. For `c` the result has `ask: {to: "user"}` and `peers: []`. A call from an Agent for another Agent's id is `FORBIDDEN`; from the user, any Agent's id works; an id that names no Agent is `NOT_FOUND`. The call changes nothing, and logs no Touch (it reads no Todo's body).

**E3 told at start.** Given `agent.spawn`, then the per-Agent settings file (A4) also has a `SessionStart` command hook, `rup context <agent-id>`, with a 5-second timeout. When `rup context` runs, it identifies as that Agent, calls `agent.context` for itself and prints on stdout one JSON object `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": <text>}}` where `<text>` names the parent, who to ask, the peers (id, name, Kind) and the open Todos, each on its own line, in glossary words. It exits 0 whatever happens: when the Daemon does not answer it prints an `additionalContext` that says the Daemon could not be reached and exits 0, so it never blocks the Agent's start. The fake `claude` in the test runs the command from the settings file and the test reads its stdout.

**E4 asking again.** Given `rup mcp <agent-id>` on stdio (M1), when an MCP client lists tools, then `agent_context` is offered besides M1's and B12's, named after `agent.context` with the dot replaced by `_`, taking no input. A call returns E2's result for that Agent as the tool's text. After `rail.move` puts the Agent under another parent, the next call returns the new parent, `ask` and peers, so the Agent can refresh what E3 told it at start.

**E5 asking the lead.** Given a Meta-agent `m` and its child `a`, when `a` calls `agent_context` and then `message_send {to: <ask.to>, kind: "question", body}` (B12), then the Message is delivered to `m` as B2 says. Given `c` under a plain Group, the same two calls store the Message to the user and type nothing anywhere (B10). An Agent that sends to a peer's id from `peers` gets B2's delivery too. No new method is involved: this scenario fixes that E2's `ask.to` is a valid `to` for B1.

**E6 no channel is loud.** Given an Agent whose `rup mcp <id>` has not connected to the Daemon 15 seconds after `agent.spawn` (the fake `claude` never starts it), then the Agent's Status gains the Chip `no channel`, `agent.status` is emitted once, its Kind is unchanged, and the Live line says `no channel` (`CONTEXT.md`: a Chip never changes the glyph). Nothing interrupts the user (P3). When the shim connects later, the Chip goes and `agent.status` is emitted once more. A fake `claude` that starts the shim at once never gets the Chip. The 15 seconds is a Daemon constant a test shortens through `ROUNDUP_CHANNEL_DEADLINE_MS`. The rule is restated by E7's report: if Claude Code starts its MCP servers only on the first tool call, this clause is rewritten there, not guessed here.
