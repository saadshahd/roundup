# UI: daily use of the Terminal pane (U101, U102, U162, U174)

Module: `apps/desktop` (the webview). Ids: U101, U102, U162, U174.

U101 and U102 are webview only: no App command, no Daemon method, nothing under `contracts/` (U162 below is the exception: it adds one App seam command). Those two clauses are read on the injected emulator and the fake App (U11). U102 keeps its size as U100 keeps the Rail's layout (`ui-persist.md`). Nothing animates (`docs/motion.md` has no row for any of the three).

**U101 copy and paste.** Given the selected Terminal runs and its emulator holds a selection, when the user presses `⌘C`, then the selected text is written to the system clipboard and the Terminal receives nothing: no `terminal.write`. With no selection `⌘C` does nothing at all. `⌃C` is not `⌘C`: it still goes to the Terminal as the byte `0x03` (U12). When the user presses `⌘V` with text on the clipboard, then the pane hands that text to the emulator's paste exactly once, and the bytes the emulator emits for it reach `terminal.write` in order, as U12 says; a multi-line paste is one paste, never one write per line typed by the webview. `⌘V` with an empty clipboard does nothing. Both chords follow U32's rules: the webview handles them, calls `preventDefault`, Caps Lock does not change them, `⇧⌘C`, `⌥⌘C`, `⇧⌘V` and `⌥⌘V` do nothing, and they do nothing while another place holds focus (a Drawer, U33's prompt field, any text field), where the field's own copy and paste work as the browser gives them. An exited Terminal takes no paste (U12) but still copies. After `daemon-exited` paste does nothing (U25) and copy still works. A failed clipboard read or write shows `✕ <message>` in Ink where a failed `terminal.write` shows its message (`u12_a_failed_write_shows_its_message`) and changes nothing else.

U101 QA compares the same selected Terminal before and after at a 1280×800 window; after a clipboard failure, the Ink error line appears in the pane's fixed slot.

**U102 text size.** Given the selected Terminal, when the user presses `⌘` with the key `=` or `+` (on a US layout `⇧⌘=` is the same press as `⌘+`, so Shift is allowed for this one key only), with `-` or with `0`, then the emulator's font size grows by 1 px, shrinks by 1 px or returns to 13 px, the size the emulator has on main, which is also the Rail's size. The size stays between 9 px and 21 px; at either end the chord changes nothing. Any of those keys does nothing with Ctrl or Alt held, without `⌘`, or with Shift on `-` or `0`, as U32 says of other modifier sets. The size is one value for every Terminal in the window, so selecting another Terminal shows it at the same size. When the new size changes the fitted `cols` or `rows`, `terminal.resize {id, cols, rows}` is called once for them (U13's at-most-once-per-frame rule holds); when both stay the same it is not called. The Terminal's content, its scrollback (U34) and its scroll position are kept. The size is kept as U100 keeps the Rail's layout, so it survives a restart, and a value outside the range or not a number in the saved state is treated as the default. The chords follow U32's rules (handled by the webview, `preventDefault`, Caps Lock neutral), and do nothing while focus is outside the pane or after `daemon-exited`. This narrows U59: the Rail's size is the emulator's default size, and U102's chords change it.

U102 QA compares the same selected Terminal before and after at 1280×800 and 700×800, using the real emulator and actual size chords; long wrapped output, including an unterminated last line, keeps its content and logical scroll position.

Tests (`u101_`, `u102_`) use the injected emulator, a stubbed clipboard and the fake App: selection and no selection, `⌃C` against `⌘C`, a multi-line paste, an exited Terminal, `daemon-exited`, each chord's modifier cases, a throwing clipboard, each end of the size range, a second Terminal at the same size, one `terminal.resize` per change, and a mount with a saved size in range and out of range, `⇧⌘=` and `⌘+` growing the size, `⇧⌘-`, `⌥⌘0`, `⌃⌘=`, `⌥⌘=` and `⌃⌘+` doing nothing, and a size change that leaves `cols` and `rows` as they were calling nothing.

**U162 drop files on a pane.** Found by the user's report #356: files dropped on a Terminal pane, shell or Agent, do nothing. The cause is the window's native file drop, which Tauri handles before the webview sees a DOM `drop`, so one route is standard: the App seam reports the drop and the pane inserts the paths. Adds one App seam command and no Daemon method, nothing under `contracts/`, and no Token; it follows the Contract recipe of `.agents/builder.md` (rule 4), and its PR needs an architect's approval other than its author's. The seam gains `onFileDrop(listener): Promise<Unsubscribe>`, where `listener` receives `{phase: "over" | "drop" | "leave", paths: string[], x: number, y: number}` with `x` and `y` in CSS pixels of the webview, `paths` absolute and empty unless `phase` is `drop`; the Tauri adapter builds it from the webview's drag-drop event and divides the physical position by the device pixel ratio, and `GLOSSARY.md` gains **File drop** for it in the same PR. Given the selected Terminal runs (an Agent's Terminal, a shell Terminal or the Door's), when a `drop` lands inside the pane's rectangle, then the pane hands the paths to the emulator's paste exactly once, as U101 hands text, so `terminal.write` receives them in order with the bracketed-paste markers when the program asked for them. Each path is single-quoted for a POSIX shell (a `'` in it becomes `'\''`), paths are joined by one space, one trailing space follows the last, and no newline is added: the user chooses what the line does. A drop outside the pane's rectangle, on the Rail, the Shelf or a Drawer, does nothing here; the Thread's input keeps U109's image drop. While `over` is inside the pane of a Terminal that takes input, the pane shows a `--accent` ring inside its edge, 2 px, read from `--accent` with no new Token, and `leave`, a `drop` or a pane switch clears it; no row or the pane's size moves (U5, U46). An exited Terminal, the state after `daemon-exited` (U25) and a drop with no paths take nothing, show no ring and call nothing. A directory is a path like a file. Two drops are two pastes. Focus returns to the pane after a drop. Tests (`u162_`, in `apps/desktop/src/terminal/`, on the injected emulator and the fake App, whose `onFileDrop` the test drives): one file and a path with a space and a `'`; three paths in one line; the ring on `over` inside the pane and not outside; `leave` and a pane switch clear it; a drop outside; an exited Terminal and `daemon-exited`; an empty drop; a failed `terminal.write` shows its message as `u12_a_failed_write_shows_its_message` does; `u162_the_ring_moves_no_row_and_no_size` compares the pane's and its rows' rectangles before, during and after `over`; `u162_a_directory_is_quoted_like_a_file` drops a path the fake App reports as a directory and expects the same quoting; `u162_two_drops_are_two_pastes` drives two drops and expects two pastes in order; `u162_focus_returns_to_the_pane_after_a_drop` moves focus to another place, drops, and expects the emulator focused. `u162_the_tauri_adapter_converts_a_physical_drop_to_css_pixels` calls the adapter with a stubbed webview at a device pixel ratio of 2. Observer: `agent-browser` in the U26 harness captures the ring at 1280 by 800 and 700 by 800 to `artifacts/ux/U162/`, and the PR body asks the user for a `macOS:` line, since WKWebView's drop is the one thing the harness cannot show.

**U174 a File drop adds no wait of roundup's.** Found by the user's report #603 after U162: an image dropped on an Agent's pane takes a few seconds to become an attached image, a little longer than in a native terminal with the same Claude Code, and the share that is roundup's is not measured. Narrows U162; changes no contract, App seam command or Token. Rule: from the `drop` that `onFileDrop` reports to the bytes at the program's pty, roundup holds nothing: the paste is one synchronous hand-off to the emulator, one `terminal.write` and one pty write, with no timer, debounce or `await` before the write, none per path and none that grows with the file's size or format (roundup never reads the file). The budget is one frame, 16 ms at p95, the keystroke bound of `AGENTS.md` rule 7 (L29). Given the selected Terminal runs, then:

- The webview leg: a `drop` of one path and of 50 paths on the injected emulator and the fake App reaches the fake `terminal.write` in the same task as the listener's call, with no timer advanced and no microtask awaited, and the written bytes are those of U162 (`u174_a_drop_reaches_terminal_write_in_the_same_task`).
- The Daemon leg: `terminal.write` of the quoted bytes to a Terminal running `cat` echoes back within 16 ms at p95 over 100 writes, with bracketed-paste markers and without (`u174_a_write_reaches_the_pty_within_a_frame`, in `crates/terminal/tests/scenarios`).
- Observer: the native comparison, which only the user's Mac can make: with one image, one `claude --version` and a stopwatch from the drop to the attached image, the median of five drops in `just app` is within 500 ms of the median of five in Terminal.app or iTerm; the PR body asks the user for a `macOS:` line with both medians, as U162 does. The 500 ms is policy chosen by this spec: about 30 frames, above stopwatch error and below a wait the user notices as longer. A larger gap is a defect to reduce on the Issue, not a pass.
- Policy: the bytes. Whether the bytes roundup writes for one dropped image differ from a native terminal's, and whether Claude Code waits on a difference (it may treat a bracketed paste and typed text differently), is investigated in #609, not here; U174's acceptance is the three clauses above.

U174 changes nothing for a shell Terminal, whose insertion is already immediate.

The Daemon leg's test is in `crates/terminal`; U174 is the exception to rule 3 only as a scenario, and its tests land in one PR per module directory.
