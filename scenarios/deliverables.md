## Chosen mechanism and boundaries

Policy: implementation introduces the code term **Deliverable**, a deliberately published Project-scoped result, in `GLOSSARY.md` with its new contracts. Output continues to mean Terminal bytes. App label: “Made”. A Deliverable records an opaque never-reused id, Project identity, authenticated maker identity and retained display name, Home, title, publication time, target kind and target identity. Titles and paths are not identities. A publication request carries an idempotency key scoped to its authenticated maker and Project; equal replay returns the same record, conflicting replay is refused.

Policy: extend the existing Project storage owner and SQLite transaction facilities. Local regular files and Pad text are published as retained immutable bytes in Project data, separate from mutable authoring sources. No second editor or Pad store is introduced. Store bytes with the record in one transaction, bounded at 32 MiB per publication, 1 GiB retained bytes per Project; refuse excess without evicting another publication. Pad publication requires its expected Revision and retains exactly that Revision's UTF-8 text. File publication captures one open file's bytes and records length and SHA-256; refuse non-regular files, traversal, symlink escape and a source changed during capture. File access stays within the maker's authorized Project/Worktree roots; publication grants no new filesystem read authority. The user can publish an existing Pad or choose a file; an Agent deliberately invokes the declared publication capability. Neither filesystem scans nor Terminal parsing publish anything.

Policy: external http/https links, including PRs, record the exact URL as a **current external target**, never as immutable remote contents. No network crawler, credential copy or URL rewriting is added. Unknown remote availability is shown as “not checked”; an opener acknowledgement is not proof that a remote page exists. A known refusal or missing target reports its actual cause. Published local bytes open through an integrity-checked read-only materialization and existing `open_target`; a Pad revision uses the existing Pad reader in read-only mode or native Markdown opening, without changing the live Pad. Do not pass `roundup://` to the OS opener.

Policy: use a single `deliverable` public Daemon namespace for publish/list/get/move/remove/resolve; CLI and MCP derive from these contracts. List/get carry metadata; resolve returns the exact retained revision/target or a typed unavailability cause and never searches by title/path. Implementations choose concrete parameter types in the Contract recipe and update every caller together. Authenticated Agents publish only as themselves, read within existing Project/object access, and cannot spoof another maker, move a user-placed item or resurrect a removal. User operations retain existing App authentication. No Message or Route semantics change; M1–M10 remain unchanged.

## Acceptance

Each named observer below is a planned behavioral test, not an existing test claim. Extend a test already proving a clause instead of adding a second proof. Use real temporary Projects through public Daemon RPC and derived CLI/MCP; App probes use the real Daemon and fake vendor only when delivery needs one.

**DV1 deliberate publication.** Given Projects A/B and makers a/b with equal display names, each publishes a file, Pad revision and current external PR URL with equal titles. Then each record has a distinct identity, correct Project/maker/Home/title and target discriminator; A never lists or resolves B's identity (`dv1_publication_identity`, real-Daemon test in `crates/rup/tests`). Creating scratch files, editing source, emitting Terminal output, updating Todos and writing an unpublished Pad adds no record; explicit publication does (`dv1_only_explicit_publication`, same seam). Spoofed maker, unauthorized source/Pad, traversal and symlink escape fail without reading or publishing protected bytes (`dv1_publication_authority`, same seam).

**DV2 retained revision and bounded commit.** Given file bytes F1 and Pad Revision 1, publish, edit both sources to F2/Revision 2, stop/remove the makers and clean their Worktrees, then restart the Daemon. Resolving the original identities returns F1/Revision 1 and the original maker, never current source bytes; the live Pad still reads Revision 2 (`dv2_retained_revision`, real-Daemon test in `crates/rup/tests`). A stale Pad Revision, changed file capture, denied read, 32 MiB plus one byte and Project quota excess each refuse without a visible partial publication or eviction; exactly 32 MiB and quota equality succeed (`dv2_publish_failures`, same seam). Crash before commit leaves no record; crash after commit before reply plus replay creates one record and one byte allocation; conflicting replay refuses (`dv2_publish_replay`, same seam, injected commit boundaries). Metadata/listing never loads every retained payload (`dv2_metadata_only`, instrumented storage test through public calls).

Cost observer (TC1): `dv2_publish_failures` retains the real Project Daemon publication boundary and on-disk payloads: the stale-revision, file-size and aggregate-quota refusals must leave the public listing intact after actual publication transactions, not merely pass a size predicate.

**DV3 unavailable is not replacement.** Given a retained publication, corrupt or remove its retained bytes and create another file/Pad with the same name/title. Resolve reports respectively integrity failure or missing retained revision and opens nothing; the record remains discoverable after restart (`dv3_no_substitution`, real-Daemon test in `crates/rup/tests`). Source disappearance through Worktree cleanup alone is not access revocation. Explicit user deletion of the published source object or a recorded access revocation makes resolve/send unavailable with the access cause even if retained bytes exist; recreating the same source name grants no authority (`dv3_revoked_access`, same seam). Current external targets remain labelled current and return their exact URL; unsafe schemes refuse, unknown remote availability remains unknown, and resolution adds no fallback (`dv3_external_target`, real-Daemon test in `crates/rup/tests`). No HTTP success or remote revision retention is claimed.

**DV4 user placement and removal.** Given Home A, the user moves a publication to B; delayed maker placement, publication replay and refresh cannot move it back or duplicate it. List by Home shows it only in B and Provenance records the user move (`dv4_user_home_wins`, real-Daemon test in `crates/rup/tests`). Removing a Workstream rehomes surviving publication records to Project root without changing maker/target; stopping/removing a maker does not remove them (`dv4_home_lifecycle`, same seam). Explicit user removal tombstones that publication identity, releases its retained bytes/materializations and makes get/resolve/send refuse; reopen, replay and background refresh never resurrect it. A fresh deliberate publication requires a fresh key/id (`dv4_removal_replay`, same seam). An already opened OS document cannot be recalled; removal/revocation forbids every later resolve and invalidates cached materializations (`dv4_cached_access`, same seam).

**DV5 one discovery surface and native opening.** Given a reopened Project with ten makers, stopped makers, duplicate titles, all target kinds and unavailable records, the Project overview's “Made” section lists all publications; selecting a Workstream filters by Home and selecting an Agent filters by maker. Each row exposes title, maker, Home and published revision/current-target status; equal titles remain independently actionable. Keyboard and pointer selection open only the selected identity via existing Pad/native paths; the App never starts an Agent or Model to list/read/open (`dv5_discover_open`, real-Daemon App test in `apps/desktop/src`). An unsafe external scheme or removed/revoked cached materialization invokes no opener; an external/native opener refusal has no fallback. A rejected open leaves selection and catalogue intact and shows the cause (`dv5_open_failure`, same seam). Policy: retain Project overview/Ask, real Agent/Workstream Terminals, per-Agent diff ownership and existing Shelf authoring; no conversation renderer, embedded browser, splits or dictation. Critic observes D2/D5/D6 and every Check passing on main at 1512×950 with the densest seed, including failure text, using `.agents/data/harness.md`; UI tests assert roles/actions/data/focus, never geometry or exact copy.

**DV6 share the recorded identity.** Given two same-titled publications, Copy Link and Send to Agent for the selected row carry that publication's Project/id and resolve command, never only its title, mutable source path or copied description. The receiving Project's public reader resolves the exact retained revision or explicit current external target; another Project, wrong/stale id, removed or revoked publication refuses without substitution (`dv6_bound_share`, real-Daemon App/CLI test in `apps/desktop/src`). Send uses existing `message.send` and Send to Agent composition: Reach, Attempt and existing inbox delivery rules remain effective; retry does not change target identity, and opening the menu sends nothing (`dv6_guarded_send`, same seam with deterministic fake Claude). No new send channel or permission grant is introduced.

Policy: the specification PR closes #2774 only after independent specification acceptance. Dependent implementation work owns DV1–DV4 (publication/storage/authority), DV5 (discovery/native opening), and DV6 (bound sharing). Discovery requires the publication implementation; sharing requires both discovery and the actual link-reader/Send to Agent owners #2692/#2694. Those Issues retain current-content link semantics; publication links are a distinct target kind, not a changed meaning. Native blocked-by links, progress and engineering questions live on Issues, never a scenario scheduling table. A merged specification is not feature delivery.
