# UI surfaces

Module: `apps/desktop` (the webview); the window half is S7 in `app.md`. Ids: U80–U86.

What the webview shows when something fails, takes a moment, has ended or has no workstream. Ids U80 to U86; the window's smallest size is S7 in `app.md`. These scenarios are new and edit no earlier text; where one narrows an earlier scenario or test it says so, and a scenario that says "after X" may be built from X's branch and merges after X. The scenarios they build on (U47, U52, U56, U57, U59 and U4's 4.5:1) are on main. The empty states (U38), first run (U2), Daemon gone and reopen (U25, U37) and an exited Terminal that takes no input (U12) are specified elsewhere and are not repeated. Tests run in Vitest with jsdom against the fake App seam, with the injected clock and emulator (`ui.md` header), except U85, which needs real layout and is a check run in a browser (below). Every rule here is a value a test can read: a string, a token, a duration, a call that is or is not made. Ink stays what `GLOSSARY.md` says: bold plus colour for `error` and `needs-you` only, and text keeps U4's 4.5:1.

**U80 one failure line.** Given any `✕ <message>` the webview shows for a failed call (U2, U9, U14, U16, U19, U21, U32, U35, U56) or a failed write (U12), then it is one line: the mark `✕` and the message up to its first line break, cut with `…` when it is wider than its place, and the whole message, line breaks kept, is the line's `title`, so the last lines of a Daemon's stderr (S1) never grow the Rail or the centre. Every place shows it the same way: in Ink, with `role="alert"` so a screen reader announces it once, with class `ink` and no other class, in the same frame as the failure, with no fade, slide or shake (`docs/motion.md` has no row for it); under `prefers-reduced-motion` nothing differs. It never clears on a timer; each place's own rule clears it (U9 and U35: the next click). Two failures in one place show the newer one only. It narrows the tests that assert the message text of these lines, which must now also pass with a message of three lines: `u2_a_failed_open_project_shows_the_message_in_ink_in_place_of_the_prompt`, `u2_a_failed_open_project_is_the_only_ink_in_the_window`, `u2_a_failed_chooser_shows_the_message_in_ink`, `u3_a_failed_rail_refetch_shows_the_message_in_ink_in_the_centre`, `u9_a_failed_call_shows_one_ink_line_until_the_next_click`, `u9_the_failure_line_sits_above_the_actions`, `u32_a_failed_chord_spawn_shows_the_error_line`, `u12_a_failed_write_shows_its_message`, `u16_a_failed_create_shows_the_message_in_place_of_the_field`, `u21_an_export_error_shows_the_message_in_the_drawer`, `u35_a_failed_complete_shows_its_message_in_place_of_the_second_line`, `u13_a_failed_rail_refetch_line_sits_in_the_panes_fixed_slot`, `u14_a_failed_stop_shows_its_message` and `u14_an_error_line_never_changes_the_height_of_the_slot_that_holds_it`; their assertions on text and class stay as written. After U52 if both are merging, since U52 adds a second `✕` line to the first-run centre.

**U81 a spawn that takes a moment.** Given an open Project, when `agent.spawn` or `rail.spawnTerminal` has been in flight for 500 ms of the injected clock, then a light line (`--grey`, never Ink) takes the place above `+ agent  + terminal  + group` where U9's failure line sits, reading `starting agent…` or `starting terminal…`. A call that settles in under 500 ms shows nothing, so a fast spawn never flashes. While the call is in flight the pressed word has `aria-busy="true"`, and the three words keep their place and width; no spinner, no pulse and no movement is added (`docs/motion.md`: no spinner). The line goes in the same frame the call settles. On success the selection follows U9 and U47 (the new row is selected once the tree has it); on failure the line is replaced by U9's `✕ <message>`; never both. `rail.createGroup` is not covered: it is not a spawn. The same line serves the prompt field (U33) when Enter has called `agent.spawn`, and the field keeps its text as U33 says. After U33 and U56. These keep passing as written: `u32_a_second_chord_while_a_spawn_is_in_flight_calls_nothing`, `u9_plus_terminal_and_plus_group_are_disabled_while_a_spawn_is_pending`, `u9_a_double_click_on_plus_agent_spawns_one_agent`, `u9_the_new_agents_row_becomes_selected_once_the_tree_has_it` and the `u9_` failure-line tests.

**U82 the last screen outlives the program.** Given a selected Agent or Terminal whose program exits (`terminal.exited`, so Kind `error` or `done` by A3, or an exited Terminal), then its pane keeps the screen it had: the injected emulator for that Terminal is not disposed, cleared or reset, its scrollback (U34) stays scrollable and selectable, and `terminal.output` that arrived before the exit is still all there after selecting another row and back. The injected emulator records the cursor as hidden once the program has exited. Nothing is added to the pane: no `✕` and no message, because how it ended already reads in the Rail (U7: `exited <code>`, `exited by signal`, with Ink for `error`). The pane sends no `terminal.write` and no `terminal.resize` for it from then on (U12, U13). After U57, which removes the pane header; until it merges, U14's exited header stays and `u14_a_terminal_that_exits_while_selected_changes_its_header` and the `exited 3` and `exited by signal` cases in `u14_header.test.tsx` are U57's to replace, not this scenario's. These keep passing as written: `u12_an_exited_terminal_takes_no_input`, `u12_a_terminal_that_exits_while_shown_stops_taking_input`, `u13_an_exited_terminal_is_not_resized` and `u13_a_terminal_that_exits_is_no_longer_resized`.

**U83 a node from an earlier run has no output to show.** Given a Rail node of kind Agent or Terminal whose `terminal_id` is `null` (A8, A12: an earlier Daemon run's Agent comes back `done`, its Terminal gone; an earlier run's Meta-agent has no Terminal either), when the user selects it, then the pane reads `no output kept from an earlier run`, centred, in `--grey`, never in Ink, since nothing failed. The pane makes no `terminal.write`, no `terminal.resize` and no emulator for it, and the Rail row reads as U6 and U7 say. A node with a `terminal_id` never shows this line, even before any output has arrived. This narrows U57's "the pane shows only the terminal" for a node that has no Terminal, as U38 narrows it for no selection, and it replaces what `u14_a_terminal_row_with_no_terminal_id_reads_exited_alone` asserts for the pane once U57 has removed that header. After U57 and U38. `u14_with_nothing_selected_the_pane_is_empty` and its U38 successor are unchanged.

**U84 the cursor and the selection stay calm.** Given any selected Terminal (U59), then the emulator is built with a cursor that does not blink, and with the cursor drawn as an outline, not a block, whenever the pane does not hold keyboard focus, as when a Drawer holds it (U40) or the Rail does (U41). The selection's background is `--lightest` and its foreground `--text`, so selected text keeps at least 4.5:1 (U4) whatever ANSI colour it was printed in; the test computes the ratio from the two tokens. No token is added or changed. The options are asserted on what the injected emulator was built with, as U34 asserts its scrollback bound. After U59, which sets the cursor's colour and the palette; every one of its clauses stays.

**U85 the layout holds at the smallest window.** Given the window's smallest size, 640 by 400 px (S7), when the fake-Daemon harness (U26) loads the webview at that size with an Agent selected and a Drawer open, then the Rail is 252 px wide, the Shelf sits under it (U24), the terminal pane is the rest of the width, the Drawer is no wider than that rest, and no region's box overlaps another's. Jsdom computes no layout, so this is not a Vitest test: QA or the Reviewer opens `just harness` in `agent-browser` at a 640 by 400 viewport (`AGENTS.md`), reads each region's box, and reports the five boxes; the check fails when one is missing or two overlap. The CSS values U23's test reads do not change. Nothing else is narrowed.

**U86 the App draws icons as vectors.** Given the `tree-40`, `agents-10`, `conflict` and first-run harness screens at 1280 by 800 and 700 by 800, when the Rail, Shelf, Drawer or an error line shows a Kind, a Group disclosure, Pad ownership or an add/close action, then the mark is an SVG from one maintained SolidJS-compatible icon library, never a font character standing alone as an icon. Kind still has one stable shape and the tone in `docs/design-system.md`; hue alone never conveys it. Icons align on one 16 px scan line without changing row height or selection alignment, while buttons keep their 24 px hit area, visible focus and accessible name. Adjacent text is not announced twice; a standalone icon action has its own accessible name. The migration changes each existing text-glyph assertion to inspect the SVG and accessible name in the same PR, with no compatibility copy of the font mark. QA compares before and after at both window sizes, light and dark, and checks D2, D4, D5 and D6 on the real rendering. The `u86_` cases verify each Kind, disclosure, ownership and action; U6, U9, U15, U20 and U80 outcomes stay green. Owns `apps/desktop/src/ink/**` and the icon call sites across `rail`, `todos`, `pads`, `drawer` and `app`; the Builder coordinates with U67's Pad Editor before touching `pads`.
