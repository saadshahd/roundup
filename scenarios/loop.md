# Loop tooling

**L1 size.** Given a PR, when `loop/rules.sh size` runs, then it prints an advisory on stderr, and still exits 0, when the changed files span more than one module directory or exceed about 2000 changed lines (lockfiles and files under `generated/` excluded); otherwise it prints nothing. Neither guide ever makes it fail. A binary file and a rename into another module each count toward the module list. An unknown base ref fails loudly.

**L2 approval.** Given commits that each carry `Author-Agent`, and an empty newest commit carrying only `Reviewed-by-Agent`, when `loop/rules.sh trailers` runs, then it passes. It fails when the reviewer id is also an author id, when a commit that changes files carries the reviewer trailer, when a commit follows the approval, and when a commit has neither trailer.

**L3 vocabulary.** Given a public Rust item or field, TS export or `contracts/` name containing an `_Avoid:_` word from `CONTEXT.md` (also as a plural), when `loop/rules.sh vocab` runs, then it fails and names the word. `crates/agents/claude_code/` is exempt. A missing `CONTEXT.md` fails loudly.

**L4 pause.** Given Builder output with `api_error_status` 429 or "usage limit" / "rate limit" text, when `loop/boxd.sh build` runs, then it exits 75, writes `loop/out/PAUSED` and keeps its first timestamp on later runs. While the file exists no VM is created.

**L5 cleanup.** Given any exit path of `loop/boxd.sh build`, then the VM it created is destroyed, the original exit code is kept, and a failed removal is reported as a leaked VM. A failed create removes nothing. A successful run leaves a patch in `loop/out/patches/`.

**L6 secret.** Given the boxd secret `CLAUDE_CODE_OAUTH_TOKEN` is missing, when `loop/boxd.sh build` or `review` runs, then no VM is created and it exits 1. A VM only ever sees the secret's placeholder, so no token is scanned for or handled.

**L7 isolation.** Given a Builder run, then its VM is created from the `ru-toolchain` snapshot with `--isolated`.

**L8 cap.** Given `BOXD_MAX_VMS` `ru-` VMs (default 12), or a held `loop/out/lock`, when `loop/boxd.sh build` runs, then no VM is created and it exits 1. A non-numeric `BOXD_MAX_VMS` exits 2. The count includes every `ru-` VM, a suffixed one from L9 too, and `loop/boxd.sh review` is held to the same cap and lock: a review's fallback create is inside the same locked count-then-create as its first.

**L9 review.** Given a ref, when `loop/boxd.sh review <name> <prompt-file> [ref]` runs, then an isolated VM holds a git checkout whose tag `base` is the merge-base with `origin/main` and whose HEAD is the ref: the ref's own commits are replayed on `base` with their authors, messages and trailers, including a commit with no changes, and no synthetic commit is added; when the range from the merge-base to the ref contains a merge commit, the VM instead gets one commit named `head` holding the ref's tree, because a series cannot carry merges, the Reviewer's answer is written to `loop/out/verdicts/<name>.md`, and the VM is destroyed. The VM is named `ru-<name>`. When that create fails for any reason, the run creates `ru-<name>-r<pid>` (the run's pid) instead; only a failed second create exits 1, so a name freed or taken between the two never decides the outcome. The `-r<digits>` ending cannot be mistaken for a swarm VM (`ru-builder-<n>`, `ru-reviewer-<n>`) or an L15 check VM (`ru-chk-<slug>-<pid>`). A run removes only a VM its own successful create made (L5), on every exit path: one whose plain create failed never removes `ru-<name>`, and an L19 retry makes a new create under the same rule, plain name first, so a retry may own `ru-<name>` although its first attempt had the suffixed name, and then removes that one. A swarm child is suffixed like any other review. Both runs go on, each on its own VM; each writes `<name>.md` when it ends, so the file holds the answer of the run that ended last. The tests use the `boxd` stub, which refuses a name that exists, and give it a different result text per run: two parallel `review x` runs get two different VM names and both exit 0; `review x` with no clash uses exactly `ru-x`; with `ru-x` alive, `review x` exits 0 and `ru-x` is still alive with no `machine remove ru-x ` in the log; `x.md` holds the text of the run that ended last; with `ru-x` alive and the reboot failing once, removing `alive-ru-x` before the retry leaves no VM of the run alive.

**L10 input.** Given a name outside `^[a-z0-9][a-z0-9-]*$`, a prompt file starting with `-`, or a ref starting with `-`, when `build` or `review` runs, then it exits 2 before creating a VM or a file. So does a name ending in `-r<digits>`, which L9's suffixed VM names use; the test runs `review x-r5`.

**L11 reboot.** Given a VM created from the snapshot, then it is rebooted and answers `exec` before any agent or check runs on it.

**L12 swarm.** Given N prompt files, when `loop/boxd.sh swarm <build|review> <prompt-file>...` runs, then every prompt file is validated before any VM is made, each agent gets its own isolated VM named `ru-builder-<n>` or `ru-reviewer-<n>` (a review child whose create fell back, L9, is `ru-reviewer-<n>-r<pid>`), no more than `BOXD_MAX_VMS` VMs exist at once, one `ok` or `failed rc=<n> (see <log>)` line is printed per VM, naming the VM that run actually used, and it exits 1 if any failed. On SIGINT or SIGTERM it removes its VMs, stops its agents and exits 130.

**L13 status.** Given `ru-` VMs, when `loop/boxd.sh status` runs, then it prints one line per VM with `agent-running`, `idle` or `unreachable`.

**L14 kill.** Given `loop/boxd.sh kill <name>`, then `ru-<name>` and every `ru-<name>-r<digits>` (L9's suffixed VM) are removed and no other; given `kill all`, then every VM named exactly `ru-builder-<n>` or `ru-reviewer-<n>` (what `swarm` creates, including another swarm's), each with or without a `-r<digits>` ending, is removed and no other; a hand-run review named `reviewer` is `ru-reviewer` or `ru-reviewer-r<pid>` and `kill all` leaves it. A failed removal prints `FAILED <vm>` and exits 1. The test lists `ru-x`, `ru-x-r123`, `ru-x-2`, `ru-xy`, `ru-reviewer`, `ru-reviewer-r9`, `ru-reviewer-2` and `ru-reviewer-2-r8`: `kill x` removes the first two and no other; `kill all` removes only the last one and `ru-reviewer-2`.

**L15 check.** Given a PR number or a branch name, when `loop/boxd.sh check` runs, then it fetches `origin/main` and that ref, merges them in the object store on this machine, uploads that merged tree (tag `base` is `origin/main`) to a fresh `--isolated` VM with an auto-destroy timer (no GitHub login; nothing is cloned or fetched on the VM; no Claude secret is needed), runs `just check` there from the lockfile, shows the last 25 lines with GitHub token shapes masked, destroys the VM and exits with the check's exit code. A ref with shell syntax or a leading dash fails with exit 2, and a ref that conflicts with `origin/main` fails with exit 1 naming the ref and the conflicting file, both before any VM exists. The VM's auto-destroy timer is 4200 s, longer than the reboot wait (at most 60 attempts of 5 s plus 1 s, 360 s), the upload, an agent run of at most 1800 s, `just check` at most 1800 s and the patch step. At `BOXD_MAX_VMS` `ru-` VMs it creates none. `loop/boxd.sh bake` runs on an isolated VM, warms the dependency build from the lockfile, cleans every workspace member from that warm target (no artifact may name the bake checkout or be reused by mtime), and refuses to save a snapshot when that holds or when its scan finds a GitHub or Anthropic token.

**L16 empty approval.** Given a ref whose series contains an empty commit (such as the empty `review: approve` commit), when `loop/boxd.sh review <name> <prompt-file> <ref>` runs, then the VM's checkout contains that commit too (a commit with the same subject is HEAD, tag `base` is still the merge-base) and the review does not fail on that commit.

**L17 run logs.** Given two runs of `loop/boxd.sh build` or `review` with the same `<name>`, then each keeps its own log files under `loop/out/runs`, named `<name>-<UTC yyyymmddThhmmssZ>-<pid>` plus an extension, so a relaunch never overwrites a failed run's log; the patch and verdict keep their stable names `<name>.patch` and `<name>.md`; `check <ref>` names its VM `ru-chk-<slug>-<pid>` (the L15 name plus the run's pid, the one part of the log suffix a VM name can carry, since VM names are lowercase), so two parallel checks of the same ref never collide on a VM name.

**L18 slot wait.** Given `BOXD_SLOT_WAIT=<s>` (default 0, so a single run does not wait; a non-numeric value exits 2 like `BOXD_MAX_VMS` in L8), when `BOXD_MAX_VMS` `ru-` VMs exist, including VMs that are not this run's, then the run re-checks every second for up to `<s>` seconds and creates its VM as soon as a slot frees; if none frees it exits 1 with a message naming `BOXD_MAX_VMS` and creates nothing. `swarm` gives its children a wait of `BOXD_SLOT_WAIT` seconds (default 900), so an outside VM cannot make the last child fail at create.

**L19 retry and events.** Given a run whose VM never answers after its reboot (at most `BOXD_REBOOT_ATTEMPTS` of 5 s plus 1 s, default 60), or whose upload fails within `BOXD_RETRY_WITHIN` seconds (default 30) of the VM answering after its reboot, then the VM is destroyed and the run is retried once on a fresh VM before any agent has started, printing `retrying once`; a second failure exits 1 with `giving up after one retry`; a later upload failure is not retried; nothing is retried once the agent has run. Each retry, an agent run with no output, and an agent or check run whose boxd exec error reports `DeadlineExceeded` (boxd's no-output deadline) are appended to `loop/out/events.log` as `<UTC time> <VM> <phase> <event>`; an agent run with no output and a `DeadlineExceeded` run are recorded and never retried.

**L20 swarm ref per prompt.** Given `loop/boxd.sh swarm review <prompt-file>[@<ref>]...`, then each prompt is reviewed at its own ref, a prompt without `@<ref>` uses `BOXD_REF` (default HEAD) so existing invocations stay valid, an existing file whose name contains `@` is a plain prompt file, and a ref that is not a commit is refused with exit 2 before any VM exists.

**L25 design critic run.** Needs L21 (the event stream) on main. Given a PR whose newest commit is a `Reviewed-by-Agent` approval (L2) and a `design-critic` prompt, when `loop/boxd.sh critic <pr> <prompt-file>` runs, then it follows L4, L6, L8, L10 (`<pr>` is digits) and L11 and keeps L17's run log as `review` does, `<pr>` is resolved to its head with `gh` on the laptop, and one isolated VM named `ru-critic-<pr>`, made from the `ru-toolchain` snapshot as L7 says, holds the PR's own commits replayed on `base` as L9 does for a ref; the prompt runs there as the agent. A `<pr>` that is not digits, or a prompt file starting with `-`, exits 2 before any VM or file exists. A PR with no approval exits 2 with `not approved` and makes no VM; that is checked first, so a PR with no approval and no id prints only `not approved`. An approved PR whose title, body and commit subjects name no `U<digits>` exits 2 with `no scenario id`. Those ids are the scenarios the run covers. The run succeeds when `artifacts/ux/<id>/report.md` exists for each id and its first line is `CRITIC: pass` or `CRITIC: fail`, and when every image the report embeds, as `![...](<name>)`, is a `.png` file name with no `/` in it that exists beside it. Other text, including a cited path such as `docs/motion.md` or a link that is not an image, is not checked. A report that embeds any other file, a first line that is neither verdict, a missing image, or no report exits 1 naming the id. Only each `report.md` and its named images come back, to `loop/out/critic/<pr>/<id>/`; any other file stays on the VM, and nothing is written under `loop/out/patches/` or `loop/out/verdicts/`. The command never changes the PR and never posts a review: the VM is isolated, so it holds no GitHub credential and `github-app` is not available there (`docs/boxd.md`). The VM is destroyed as in L5. That the critic's exit code gates nothing, and the Merger does not wait for it, is policy of the loop, not something these tests observe. The checks the prompt makes are measured, not judged: contrast from computed colours (U4), durations from sampled frames against `docs/motion.md` within its 25% tolerance, and fonts and spacing against the Rail's computed values. The prompt, not this command, files a Todo for each failure, as `docs/development-loop.md` says; the command only collects `report.md`. The tests use the `boxd` stub and fake `claude`: a report with an image, which also cites `docs/motion.md` in prose, with exit 0 and the files in `loop/out/critic/<pr>/<id>/` and nothing else; the stub log shows the reboot and an `exec` answered before the agent runs, a run log under `loop/out/runs`, the PR's head resolved by a fake `gh` call, and the PR's commits replayed on `base` (a fake `git` shows the replay); two ids give two folders; a report naming a missing image, one embedding `../x.patch`, one embedding `a/b.png`, one whose first line is `hello`, and one run that writes nothing each exit 1 naming the id; extra files the agent wrote do not come back; a PR with no approval, an approved PR naming no id, a `<pr>` of `x1` and a prompt file `-p` each exit 2 with no VM and no file under `loop/out/`, the first printing only `not approved`; the stub log shows `--isolated`, the `ru-toolchain` snapshot and the name `ru-critic-<pr>`, and one removal; `BOXD_MAX_VMS` VMs or a missing secret stop it as for `review`, and a rate or usage limit pauses it as L4 says; a fake `gh` and `git` record no post and no push, and the PR's head is unchanged.
