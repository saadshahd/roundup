# Loop tooling

Module: `loop/`. Ids: every `L` heading in the file.

**L1 size.** Given a PR, when `loop/rules.sh size` runs, then it prints an advisory on stderr, and still exits 0, when the changed files span more than one module directory or exceed about 2000 changed lines (lockfiles and files under `generated/` excluded); otherwise it prints nothing. Neither guide ever makes it fail. A binary file and a rename into another module each count toward the module list. An unknown base ref fails loudly.

**L2 approval.** Given commits that each carry `Author-Agent`, and an empty newest commit carrying only `Reviewed-by-Agent`, when `loop/rules.sh trailers` runs, then it passes. It fails when the reviewer id is also an author id, when a commit that changes files carries the reviewer trailer, when a commit follows the approval, and when a commit has neither trailer.

**L3 vocabulary.** Given a public Rust item or field, TS export or `contracts/` name containing an `_Avoid:_` word from `CONTEXT.md` (also as a plural), when `loop/rules.sh vocab` runs, then it fails and names the word. `crates/agents/claude_code/` is exempt. A missing `CONTEXT.md` fails loudly.

**L4 pause.** Given a run whose final `result` event reports `api_error_status` 429 or an error whose text says "usage limit" or "rate limit", when `loop/boxd.sh build` or `review` runs, then it exits 75, writes `loop/out/PAUSED` and keeps its first timestamp on later runs. While the file exists no VM is created. Only that final event is read, so the words "usage limit" or "rate limit" quoted in an Agent's or a Reviewer's text never pause anything; a stream that ends with no `result` event is not a pause: with no event at all it is L19's no-output case, and with events it is L21's ended-without-result case.

**L5 cleanup.** Given any exit path of `loop/boxd.sh build`, then the VM it created is destroyed, the original exit code is kept, and a failed removal is reported as a leaked VM. A failed create removes nothing. A successful run leaves a patch in `loop/out/patches/`.

**L6 secret.** Given the boxd secret `CLAUDE_CODE_OAUTH_TOKEN` is missing, when `loop/boxd.sh build` or `review` runs, then no VM is created and it exits 1. A VM only ever sees the secret's placeholder, so the secret's token is never scanned for or handled (L23 scans a VM tool's files, which is a different thing).

**L7 isolation.** Given a Builder run, then its VM is created from the `ru-toolchain` snapshot with `--isolated`.

**L8 cap.** Given `BOXD_MAX_VMS` `ru-` VMs (default 12), or a held `loop/out/lock`, when `loop/boxd.sh build` runs, then no VM is created and it exits 1. A non-numeric `BOXD_MAX_VMS` exits 2. The count includes every `ru-` VM, a suffixed one from L9 too, and `loop/boxd.sh review` is held to the same cap and lock: a review's fallback create is inside the same locked count-then-create as its first.

**L9 review.** Given a ref, when `loop/boxd.sh review <name> <prompt-file> [ref]` runs, then an isolated VM holds a git checkout whose tag `base` is the merge-base with `origin/main` and whose HEAD is the ref: the ref's own history reaches the VM as a git bundle and is checked out, not replayed: every commit keeps its real author, message and trailers exactly as the branch has them, including a commit with no changes and a merge commit in the range, with no commit folded or invented (a merge's trailers still come from the range, see L22); the Reviewer's answer is written to `loop/out/verdicts/<name>.md`, and the VM is destroyed. The VM is named `ru-<name>`. When that create fails for any reason, the run creates `ru-<name>-r<pid>` (the run's pid) instead; only a failed second create exits 1, so a name freed or taken between the two never decides the outcome. The `-r<digits>` ending cannot be mistaken for a swarm VM (`ru-builder-<n>`, `ru-reviewer-<n>`) or an L15 check VM (`ru-chk-<slug>-<pid>`). A run removes only a VM its own successful create made (L5), on every exit path: one whose plain create failed never removes `ru-<name>`, and an L19 retry makes a new create under the same rule, plain name first, so a retry may own `ru-<name>` although its first attempt had the suffixed name, and then removes that one. A swarm child is suffixed like any other review. Both runs go on, each on its own VM; each writes `<name>.md` when it ends, so the file holds the answer of the run that ended last. The tests use the `boxd` stub, which refuses a name that exists, and give it a different result text per run: two parallel `review x` runs get two different VM names and both exit 0; `review x` with no clash uses exactly `ru-x`; with `ru-x` alive, `review x` exits 0 and `ru-x` is still alive with no `machine remove ru-x ` in the log; `x.md` holds the text of the run that ended last; with `ru-x` alive and the reboot failing once, removing `alive-ru-x` before the retry leaves no VM of the run alive.

**L10 input.** Given a name outside `^[a-z0-9][a-z0-9-]*$`, a prompt file starting with `-`, or a ref starting with `-`, when `build` or `review` runs, then it exits 2 before creating a VM or a file. So does a name ending in `-r<digits>`, which L9's suffixed VM names use; the test runs `review x-r5`.

**L11 reboot.** Given a VM created from the snapshot, then it is rebooted and answers `exec` before any agent or check runs on it.

**L12 swarm.** Given N prompt files, when `loop/boxd.sh swarm <build|review> <prompt-file>...` runs, then every prompt file is validated before any VM is made, each agent gets its own isolated VM named `ru-builder-<n>` or `ru-reviewer-<n>` (a review child whose create fell back, L9, is `ru-reviewer-<n>-r<pid>`), no more than `BOXD_MAX_VMS` VMs exist at once, one `ok` or `failed rc=<n> (see <log>)` line is printed per VM, naming the VM that run actually used, and it exits 1 if any failed. On SIGINT or SIGTERM it removes its VMs, stops its agents and exits 130.

**L13 status.** Given `ru-` VMs, when `loop/boxd.sh status` runs, then it prints one line per VM with `agent-running`, `idle` or `unreachable`.

**L14 kill.** Given `loop/boxd.sh kill <name>`, then `ru-<name>` and every `ru-<name>-r<digits>` (L9's suffixed VM) are removed and no other; given `kill all`, then every VM named exactly `ru-builder-<n>` or `ru-reviewer-<n>` (what `swarm` creates, including another swarm's), each with or without a `-r<digits>` ending, is removed and no other; a hand-run review named `reviewer` is `ru-reviewer` or `ru-reviewer-r<pid>` and `kill all` leaves it. A failed removal prints `FAILED <vm>` and exits 1. The test lists `ru-x`, `ru-x-r123`, `ru-x-2`, `ru-xy`, `ru-reviewer`, `ru-reviewer-r9`, `ru-reviewer-2` and `ru-reviewer-2-r8`: `kill x` removes the first two and no other; `kill all` removes only the last one and `ru-reviewer-2`.

**L15 check.** Given a PR number or a branch name, when `loop/boxd.sh check` runs, then it fetches `origin/main` and that ref, merges them in the object store on this machine, uploads that merged tree (tag `base` is `origin/main`) to a fresh `--isolated` VM with an auto-destroy timer (no GitHub login; nothing is cloned or fetched on the VM; no Claude secret is needed), runs `just check` there from the lockfile, shows the last 25 lines with GitHub token shapes masked, destroys the VM and exits with the check's exit code. A ref with shell syntax or a leading dash fails with exit 2, and a ref that conflicts with `origin/main` fails with exit 1 naming the ref and the conflicting file, both before any VM exists. The VM's auto-destroy timer is 4200 s, longer than the reboot wait (at most 60 attempts of 5 s plus 1 s, 360 s), the upload, an agent run of at most 1800 s, `just check` at most 1800 s and the patch step. At `BOXD_MAX_VMS` `ru-` VMs it creates none. `loop/boxd.sh bake` runs on an isolated VM, warms the dependency build from the lockfile, cleans every workspace member from that warm target (no artifact may name the bake checkout or be reused by mtime), and refuses to save a snapshot when that holds or when its scan finds a GitHub or Anthropic token.

**L16 empty approval.** Given a ref whose series contains an empty commit (such as the empty `review: approve` commit), when `loop/boxd.sh review <name> <prompt-file> <ref>` runs, then the VM's checkout contains that commit too (a commit with the same subject is HEAD, tag `base` is still the merge-base) and the review does not fail on that commit.

**L17 run logs.** Given two runs of `loop/boxd.sh build` or `review` with the same `<name>`, then each keeps its own log files under `loop/out/runs`, named `<name>-<UTC yyyymmddThhmmssZ>-<pid>` plus an extension, so a relaunch never overwrites a failed run's log; the patch and verdict keep their stable names `<name>.patch` and `<name>.md`; `check <ref>` names its VM `ru-chk-<slug>-<pid>` (the L15 name plus the run's pid, the one part of the log suffix a VM name can carry, since VM names are lowercase), so two parallel checks of the same ref never collide on a VM name.

**L18 slot wait.** Given `BOXD_SLOT_WAIT=<s>` (default 0, so a single run does not wait; a non-numeric value exits 2 like `BOXD_MAX_VMS` in L8), when `BOXD_MAX_VMS` `ru-` VMs exist, including VMs that are not this run's, then the run re-checks every second for up to `<s>` seconds and creates its VM as soon as a slot frees; if none frees it exits 1 with a message naming `BOXD_MAX_VMS` and creates nothing. `swarm` gives its children a wait of `BOXD_SLOT_WAIT` seconds (default 900), so an outside VM cannot make the last child fail at create.

**L19 retry and events.** Given a run whose VM never answers after its reboot (at most `BOXD_REBOOT_ATTEMPTS` of 5 s plus 1 s, default 60), or whose upload fails within `BOXD_RETRY_WITHIN` seconds (default 30) of the VM answering after its reboot, then the VM is destroyed and the run is retried once on a fresh VM before any agent has started, printing `retrying once`; a second failure exits 1 with `giving up after one retry`; a later upload failure is not retried; nothing is retried once the agent has run. Each retry, an agent run with no output (no event in the event stream, L21, for the whole run), and an agent or check run whose boxd exec error reports `DeadlineExceeded` (boxd's no-output deadline) are appended to `loop/out/events.log` as `<UTC time> <VM> <phase> <event>`; an agent run with no output and a `DeadlineExceeded` run are recorded and never retried.

**L20 swarm ref per prompt.** Given `loop/boxd.sh swarm review <prompt-file>[@<ref>]...`, then each prompt is reviewed at its own ref, a prompt without `@<ref>` uses `BOXD_REF` (default HEAD) so existing invocations stay valid, an existing file whose name contains `@` is a plain prompt file, and a ref that is not a commit is refused with exit 2 before any VM exists.

**L21 streamed agent run.** Given `loop/boxd.sh build` or `review`, or a `swarm` child, then each event the agent produces is written to the run's event stream, `loop/out/runs/<run>.jsonl` (L17's run name), as it happens, so a run that is producing events is never silent. The verdict, the cost line and L4's pause come from the last event of the stream, which must be a `result` event; an event after a `result` event means the run ended without a result, as below. A run that has produced no event at all is L19's no-output case, and L21 adds nothing to it; in the tests it ends when the `boxd` stub reports `DeadlineExceeded` after 5 s. A run that has produced at least one event and ends before `BOXD_AGENT_TIMEOUT` with no final `result` event exits 1 with `agent ended without a result` naming its event stream; it is treated as a timed-out run is below (no check, a build's diff so far as `.partial.patch`, no verdict, an earlier result file removed), and L4 reads no pause from it. A run that has produced at least one event and is still running at `BOXD_AGENT_TIMEOUT` (default 1800 s) exits 1 with `agent timed out after <s> s` naming its event stream; it does not run the check; a build saves the VM's diff so far as `loop/out/patches/<name>.partial.patch`; a review writes no verdict. A timed-out run removes the `<name>.patch` or `verdicts/<name>.md` an earlier run left, and a later successful build removes `<name>.partial.patch`, so a result file is always from the latest run. The tests use a fake `claude` inside the `boxd` stub and `BOXD_AGENT_TIMEOUT=3`: one that emits an event every second (the first event is in the event stream while the stub still runs, and the run ends with the timeout message and a `.partial.patch`); one whose successful `result` text quotes "usage limit" and "rate limit" (exit 0, no pause, the verdict saved); one whose `result` reports `api_error_status` 429 (exit 75 and `PAUSED`); one whose `result` event reports 429 and is followed by one more event (exit 1 with `agent ended without a result`, no pause); one whose error `result` quotes "usage limit" without a 429 status (exit 75 and `PAUSED`, as L4 says); two runs of the same build name, a timed-out one after a successful one (the `<name>.patch` is removed) and a successful one after a timed-out one (the `.partial.patch` is removed), and the same for a review's `verdicts/<name>.md`; one that emits events and exits with no `result` event (exit 1 with `agent ended without a result`, no pause, a `.partial.patch`); and one that hangs with no event and a stub that reports `DeadlineExceeded` after 5 s (L19's no-output outcome, and no timeout message).

**L22 review keeps the branch's trailers.** Given a ref whose range from the merge-base contains a merge commit, when `loop/boxd.sh review` builds the VM's checkout, then `loop/rules.sh trailers base` run on the VM gives the same exit code and the same findings as it does on the real branch. No trailer is invented: every `Author-Agent` and `Reviewed-by-Agent` on the VM's commits is copied from a real commit of the range, and the newest commit is still the approval commit when the real branch ends in one.

**L23 VM tools.** Given `loop/boxd.sh build`, `review` or a `swarm` child, when the agent starts on a VM, then the VM tools uploaded for it are exactly the entries that `loop/vm-tools.json` (the tool list) names for its role, `builder` for `build` and `reviewer` for `review`, and no file from the laptop's home directory is uploaded for it except what L9 and L15 already upload (the repository archive and the prompt file). Each entry names its source and a pinned commit or version. An entry without a pin, a role other than those two, or a tool list that cannot be read exits 2 before any VM exists, and when that and L6's missing secret both apply the tool list's exit 2 wins, because a usage error is reported before an environment one (as L8 does), and `swarm` checks the tool list before it creates its first VM. An entry's files are placed outside the checkout, so they never appear in a build's patch, or in a review's checkout tree or its `git status` (L9). Every entry's files are scanned for a token shape, meaning a string that matches `TOKEN_PATTERN` in `loop/boxd.sh` (`gho_`, `ghp_`, `github_pat_` or `sk-ant-` followed by 20 or more token characters), and a hit refuses the upload with exit 1 naming the entry; log masking is L15's and is not changed here. The scan covers an entry's files only: it does not scan the repository archive, and the Claude secret is L6's. No byte of a credential used to obtain an entry is uploaded. The run appends `<UTC time> <VM> tools <name>@<pin>` to `loop/out/events.log` for each entry, and when a Claude Code hook (a command Claude Code runs on an event) exits non-zero or cannot run (its file is missing or not executable), `<UTC time> <VM> hook <name> failed: <reason>`; a failed hook is recorded and never skipped silently; in the tests the `boxd` stub runs the fixture hook when the fake `claude` starts. What the `ru-toolchain` snapshot already carries is not claimed here: the Builder's report states it from a real VM. The tests use the `boxd` stub and local fixtures: the uploaded entries for each role and none outside them; a `HOME` that holds a planted skill uploads none of it; an unpinned entry, an unknown role and an unreadable tool list exit 2 with no VM, and for `swarm` before its first VM; a source that needs a planted fake credential is obtained and the credential's bytes appear in no uploaded file; an entry file holding a token shape is refused; no entry file appears in the patch or in `git status`; each entry has its `tools` line; and a fixture hook that exits non-zero, one whose file is missing and one that is not executable each have their `hook … failed` line. Which entries each role lists is recorded in the tool list, not in this scenario.

**L24 agent search servers.** Needs L23 (the tool list and its transport) on main. Given `loop/boxd.sh build`, `review` or a `swarm` child, when the agent starts on a VM, then it has the MCP servers that the `mcp` list of `loop/vm-tools.json` names for its role and no others. Each entry names its source and a pin, is uploaded as files with the repository archive but placed outside the checkout (L23), and needs no credential and no fetch on the VM (L23's transport and token refusal apply, and `loop/vm-tools.json` is L23's tool list). A pin is a version, or for a binary a tag plus a sha256 checksum that the upload is checked against, and a binary is the build for the VM's platform (Linux x86_64), never the laptop's. An unpinned entry, a checksum that does not match, or a binary for the wrong platform fails with exit 2 before any VM exists, and wins over L6's missing secret as L23 says. An entry that reports usage to its maker, or checks for updates over the network, is configured by the tool list not to, so nothing leaves the VM through it and nothing is fetched. A server that serves an index of the code (such as `codegraph`) answers only from an index built on the VM, never from one uploaded from this machine. The first index is built last, after the series replay has been applied to the tree, so at the agent's start it describes that checkout and no other commit; refreshing it as the agent edits files is the server's own work on the VM. If the first index cannot be built within `BOXD_INDEX_WAIT` seconds (default 120; a value that is not a whole number from 1 to 120 exits 2 as in L8, before any VM exists), the server is not configured and the run records it. The wait is at most 120 s and L15's timer of 4200 s stays: the worst case there, 3960 s, plus 120 s leaves 120 s for upload and patch. The index never appears in a build's patch or in `git status` of the checkout. The run appends one line per server to `loop/out/events.log`, `<UTC time> <VM> mcp <name>@<pin> ready` or `<UTC time> <VM> mcp <name>@<pin> unavailable: <reason>`. The tests use fake MCP servers and a tool list of local fixtures: exactly the listed servers are configured for the role and none outside it, an unpinned entry, a wrong checksum and a wrong-platform binary each exit 2 with no VM, a fake server that would report usage runs with the tool list's off setting, a fake index builder that exceeds `BOXD_INDEX_WAIT=1` leaves the server unconfigured with its `unavailable` line, a `BOXD_INDEX_WAIT` that is non-numeric or above 120 exits 2 with no VM, a fake server that would check for updates runs with that off, the index files are absent from the build's patch and from `git status` in a build's and in a review's checkout, the index records the commit id that `HEAD` has when the agent starts, the uploaded archive holds no index file, the prompt a review sends names the servers and no way to use them, and each configured server has its `ready` line. Which servers each role lists is recorded in the tool list, not in this scenario; a Reviewer's prompt says only that the servers exist and does not tell it how to use them to judge.

**L25 design critic run.** Needs L21 (the event stream) on main. Given a PR whose newest commit is a `Reviewed-by-Agent` approval (L2) and a `design-critic` prompt, when `loop/boxd.sh critic <pr> <prompt-file>` runs, then it follows L4, L6, L8, L10 (`<pr>` is digits) and L11 and keeps L17's run log as `review` does, `<pr>` is resolved to its head with `gh` on the laptop, and one isolated VM named `ru-critic-<pr>`, made from the `ru-toolchain` snapshot as L7 says, holds the PR's own commits replayed on `base` as L9 does for a ref; the prompt runs there as the agent. A `<pr>` that is not digits, or a prompt file starting with `-`, exits 2 before any VM or file exists. A PR with no approval exits 2 with `not approved` and makes no VM; that is checked first, so a PR with no approval and no id prints only `not approved`. An approved PR whose title, body and commit subjects name no `U<digits>` exits 2 with `no scenario id`. Those ids are the scenarios the run covers. The run succeeds when `artifacts/ux/<id>/report.md` exists for each id and its first line is `CRITIC: pass` or `CRITIC: fail`, and when every image the report embeds, as `![...](<name>)`, is a `.png` file name with no `/` in it that is a regular file beside it (a symlink or a directory is not). Other text, including a cited path such as `docs/motion.md` or a link that is not an image, is not checked. A report that embeds any other file, a first line that is neither verdict, a missing image, or no report exits 1 naming the id. Only each `report.md` and its named images come back, to `loop/out/critic/<pr>/<id>/`; any other file stays on the VM, and nothing is written under `loop/out/patches/` or `loop/out/verdicts/`. The command never changes the PR and never posts a review: the VM is isolated, so it holds no GitHub credential and `github-app` is not available there (`docs/boxd.md`). The VM is destroyed as in L5. That the critic's exit code gates nothing, and the Merger does not wait for it, is policy of the loop, not something these tests observe. What the prompt checks, and the Todos it files from failures, belong to `.agents/design-critic.md`, not to this scenario; the tests below observe only what the command does with the prompt's output. The tests use the `boxd` stub and fake `claude`: a report with an image, which also cites `docs/motion.md` in prose, with exit 0 and the files in `loop/out/critic/<pr>/<id>/` and nothing else; the stub log shows the reboot and an `exec` answered before the agent runs, a run log under `loop/out/runs`, the PR's head resolved by a fake `gh` call, and the PR's commits replayed on `base` (a fake `git` shows the replay); two ids give two folders; a report naming a missing image, one embedding `../x.patch`, one embedding `a/b.png`, one embedding a symlink `a.png`, one whose first line is `hello`, and one run that writes nothing each exit 1 naming the id; extra files the agent wrote do not come back; a PR with no approval, an approved PR naming no id, a `<pr>` of `x1` and a prompt file `-p` each exit 2 with no VM and no file under `loop/out/`, the first printing only `not approved`; the stub log shows `--isolated`, the `ru-toolchain` snapshot and the name `ru-critic-<pr>`, and one removal; `BOXD_MAX_VMS` VMs or a missing secret stop it as for `review`, and a rate or usage limit pauses it as L4 says; a fake `gh` and `git` record no post and no push, and the PR's head is unchanged.

**L26 watch.** Given an agent that has open work, meaning at least one open PR whose commits carry its `Author-Agent` id (for the agent whose id is `driver`, any open PR), when it runs `loop/wake.sh watch <id> <seconds> [<vm>...]`, then the call returns as soon as something it watches differs from the state `loop/out/wake/<id>` recorded at its last return, and prints one line per difference: `<pr> head <7-character sha>` when a PR's head moved, `<pr> verdict` when a comment whose first line starts `Reviewer:` or `VERDICT:` appeared, `<pr> closed` when it merged or closed, `<file> new` (`<file>` is the path relative to `loop/out/`, such as `verdicts/<name>.md`) for a file that appeared in `loop/out/verdicts/` or `loop/out/patches/`, `<file> changed` for one whose content differs from the recorded state (L17 rewrites a name's result in place), and `<vm> gone` when a `<vm>` named on the command line left `boxd machine list`. A change that landed between two calls returns at once, because the recorded state is the baseline; the first call for an `<id>` has an empty baseline, so it prints everything it watches once and exits 0. A named `<vm>` need not exist; one that is absent from `boxd machine list` on the first call that names it is reported `<vm> gone` at once, even when that call is not the agent's first. The presence or absence of each named `<vm>` is recorded in `loop/out/wake/<id>` by every call that names it, whatever that call's exit code (exit 0 and exit 3 alike), but a call whose `boxd` answer is unknown (exit 4, or cut off by the time left) leaves every VM entry unchanged, so a `gone` is never lost to a failed call; otherwise the entry is replaced, never kept, when the call sees the VM differently: after `<vm> gone` is reported, a later call that names the same `<vm>` and finds it present records it present again and watches it afresh, so a VM that leaves after a call that timed out is still reported `<vm> gone`; the rest of the state is written only when the call exits 0. It exits 0 for a change and 3 with `<id> no change in <seconds> s` when none came. A call to `gh` or `boxd` that gets no answer at all within `<seconds>` exits 4 naming the tool, and appends no `timeout` line; exit 3 is only for a call where at least one poll got an answer. `BOXD_GH_TIMEOUT` must be a whole number from 1 up and `BOXD_WORK_WINDOW` a whole number from 1 up; anything else exits 2 naming the variable, as L18 does for its own variables. Every agent sees every file under those two folders, so a result for another agent can wake it; that is accepted. `<seconds>` is a whole number from 1 to 3600, and any other value exits 2 with `seconds must be 1 to 3600`; an `<id>` or `<vm>` that is empty, starts with `-` or has a character outside letters, digits and `-` exits 2 with `bad name <value>`; an unknown command, or nothing to watch (no PR, no named VM and not `driver`) exits 2 and writes nothing. Each `gh` or `boxd` call is limited to the smaller of `BOXD_GH_TIMEOUT` seconds (default 20) and the time left of `<seconds>`; a failure, a hang or no network exits 4 naming the tool and appends `<UTC time> <id> wake error <tool>` to `loop/out/events.log`, never an empty result. `watch` appends `<UTC time> <id> wake waiting <seconds>` to `loop/out/events.log` when it starts and `<UTC time> <id> wake <what>` when it returns, where `<what>` is the first printed line or `timeout`, with `<UTC time>` in the `%FT%TZ` form `loop/boxd.sh` uses. Tests use a fake `gh` and `boxd` that return fixed PRs, heads, comments and VMs, and every test but the hang test sets `BOXD_GH_TIMEOUT=1` and a `watch` of 3 s or less; the hang test sets `BOXD_GH_TIMEOUT=20`, a `gh` that never answers and `watch x 2`, and exits 4 naming `gh` with no `timeout` line: a head that changes after 1 s returns exit 0 with `<pr> head <7-character sha>`; a head that changed before the call returns at once; a new `Reviewer:` comment returns `<pr> verdict`; a merged PR returns `<pr> closed`; a new file under `loop/out/verdicts/` returns `<file> new` and the same file rewritten with other content returns `<file> changed`; a named VM that leaves the list returns `<vm> gone`, and so does a VM named for the first time on a later call when it is already gone, a VM that was present on a call that timed out and left before the next, and a call whose `boxd` fails leaves the recorded entries as they were and the next good call reports the `gone`, and so does one that `boxd` cuts off; a name reused after `gone` (a call reports `<vm> gone`, a later call finds the same name present, a third call finds it gone and reports it); `driver` sees a PR it did not author change, and a PR opened since its recorded state prints `<pr> head <7-character sha>`; the first call for an id prints the current state and exits 0; no change in 3 s returns exit 3 and both lines appear in `events.log`; a failing `gh`, a failing `boxd` and a `gh` that hangs return exit 4 within the 3 s with the `error` line; `watch 0 x`, `watch ../x 5`, `watch -x 5`, `watch x 99999`, `watch x 5 -v` and `watch` for an agent with nothing to watch exit 2 and leave `events.log` and `loop/out/wake/` unchanged.

**L27 stall check.** Given `loop/out/events.log` and an agent with open work (an open PR by the L26 rule, opened more than `BOXD_WORK_WINDOW` seconds ago, default 3600), when `loop/wake.sh check` runs, then it lists the agent as `<id> no wake` if its last `wake` line is a `waiting <seconds>` line older than `<seconds>` plus 120 s, a return line or `error` line older than `BOXD_WORK_WINDOW`, or missing, and exits 1 if it lists any. So an agent inside a running `watch`, and one working on a result it was woken with for less than `BOXD_WORK_WINDOW`, is never listed; a turn of work longer than that without another `watch` counts as a stall. It exits 0 and prints nothing otherwise, exits 4 naming `gh` on a `gh` failure or hang as L26 does, and writes nothing. **L53 a PR shows its proof.** Given a PR number, when `loop/rules.sh proof <pr>` runs (the Driver or Merger runs it with `gh`; a boxd Reviewer has no network, so the Driver puts its output in the Reviewer's brief), then it exits 0 only when the PR body has the two sections below, otherwise it exits 1 naming each missing part, and a `gh` failure exits 4 naming the tool, never a green. A PR is *visible* when any changed path is under `apps/desktop/src/`, `crates/desktop/`, `docs/motion.md` or `docs/design-system.md`, or when its scenarios have a screenshot or motion clause; any other PR is *not visible*. The body has `## Shape`: one fenced block, at most 40 lines, in the shortest view that makes the change clear (a call tree, a component tree, a file tree, a mermaid sequence, or a diff of the shape). It has `## Proof`. For a not-visible PR, `## Proof` holds a fenced block of the test output, with one line per test named after the PR's scenario ids and the word `ok` or `passed` on it, from a run on the PR's head. For a visible PR, `## Proof` holds, for each scenario id the PR names, a `before` and an `after` image or video, each as a link into the branch `proof/pr-<n>` of this repository, each followed by its window size `W×H` (the size the scenario names; the real Tauri window is preferred for layout, a `just harness` capture is allowed and says `harness <seed>`), and a line `Shows:` that says what to look at. Each linked file exists on `proof/pr-<n>` at that path (checked with `gh api`), is a `.png`, `.webp`, `.mp4` or `.webm`, at most 5 MiB, with at most 20 MiB on the branch. How the files get there: the capture of a PR's head runs unreviewed code, so it runs in an `--isolated` VM, which has no GitHub access and must not be given any; its files are copied out with `boxd machine cp` and pushed to `proof/pr-<n>` by a separate normal boxd VM that holds only the files and none of the PR's code, or by the Driver from the laptop. **L55 green means merged.** Today (2026-10-03, read with `gh api`): `allow_auto_merge` is false, the repository has no ruleset, and the classic protection of `main` requires the checks `check` and `rules`. Given a PR, when `check`, `rules` and `merge-ready` are all green on its head, then GitHub merges it on its own (`gh pr merge --auto --merge`, set by the Driver only when all three hold: `loop/rules.sh settings` exits 0 (so `merge-ready` is already a required context and arming cannot merge on `check` and `rules` alone), `merge-ready` has printed `ready <head>` for the PR's current head, and no changed path is under `.github/`), with no agent between the green and the merge. `merge-ready` is a commit status that the workflow `.github/workflows/merge-ready.yml` sets on the PR's head SHA by running `loop/rules.sh merge-ready <pr>` (L46). The workflow's triggers are `pull_request_target` (it runs from `main`'s copy of the workflow file, so the PR cannot change it), `issue_comment`, `pull_request_review` and `workflow_run` on the completion of `check` and `loop`, because the `ARCHITECT: approve <sha>` and `VERDICT:` comments and the other checks finishing all change the answer; the job holds `pull-requests: write` only to disarm auto-merge, checks out `main` only (its checkout pins `ref: ${{ github.event.repository.default_branch }}` for every trigger, because the default ref of `pull_request_review` is the PR's merge ref, which would run the PR's own `loop/rules.sh` with the right to set the status), runs `main`'s script, and reads the PR as data (`gh` for its commits and comments, `git fetch origin pull/<n>/head` for its objects) and never executes a file from the PR. Only comments whose `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR` count as a `VERDICT:`, an `ARCHITECT: approve` or a `TRIAGE:` line (L56); a comment by anyone else counts for nothing. The status is per head SHA, so a push after the auto-merge was set leaves the new head with no `merge-ready` and nothing merges until the gate has run on it: the same pin as `--match-head-commit`. The status description is the first line `merge-ready` printed, `ready <sha>` or each failing condition, and a script that is missing or does not know `merge-ready` sets `failure` with the description `merge-ready not built`, never a pass. Rollback: `gh pr merge --disable-auto <pr>` for one PR; for all, `gh api -X PATCH repos/<owner>/<repo> -f allow_auto_merge=false`, which stops auto-merge and leaves the checks and the Merger's manual `gh pr merge --match-head-commit` (L46); the Builder PR records one live run of both commands on a throwaway PR the day the user enables the setting, and until then the rollback is stated and not proven. **L56 Copilot findings are answered before the review.** Given a PR, when it opens, then the Driver requests Copilot (`gh pr edit <pr> --add-reviewer @copilot`) and waits at most 3 minutes before sending the head to a VM review (advice, never a verdict). A thread is a *Copilot thread* when its first comment's author is the Copilot reviewer (`copilot-pull-request-reviewer`), read with the GraphQL `reviewThreads` of the PR. Within 10 minutes of a Copilot comment the Triage role replies in that thread with one line starting `TRIAGE: fix`, `TRIAGE: reject` or `TRIAGE: na` and a reason of at least one sentence: `fix` for a real defect against a rule or a scenario, `reject` for a finding that is wrong (the reason names the rule or line that shows it), `na` for a style note no rule asks for. A `fix` is handed to the PR's Builder (or its Architect for a docs PR), who pushes the fix and replies `FIXED <sha>`; the thread is resolved by the triager for `reject` and `na` and by the author for `fix` once its reply names the pushed head. The Driver does not send a head to review while a Copilot thread on it has no `TRIAGE:` reply or a `fix` with no `FIXED`, because a push after an approval voids it; a Copilot comment that arrives after an approval is triaged too, and a `fix` there is a new head that needs a fresh review (L54's carry does not apply to it). `loop/rules.sh copilot <pr>` is the observer: it exits 0 only when every Copilot thread on the PR has a `TRIAGE:` reply, every `fix` has a `FIXED` reply, and every thread is resolved, otherwise exits 1 naming each thread by its path and line, and 4 when `gh` fails; `merge-ready` (L46) runs it, so an unanswered thread blocks the merge; with no Copilot threads it exits 0, and a Copilot that has not answered is not a failure (it is advice). A Copilot comment with no `TRIAGE:` reply 10 minutes after it was posted is a stall of kind `k`, `loop/stalls.sh check` writing `loop/out/stalls/k-<pr>` as L28 does, owner `Triage`, deadline 30 minutes. The tests use a fake `gh` with threads: none, one unanswered at 9 and at 11 minutes, `TRIAGE: reject` unresolved, `TRIAGE: fix` with and without `FIXED`, `TRIAGE: na` resolved, a thread by a human (ignored), a comment arriving after an approval, and `gh` failing.
