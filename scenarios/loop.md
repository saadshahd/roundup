# Loop tooling

**L1 size.** Given a PR, when `loop/rules.sh size` runs, then it prints an advisory on stderr, and still exits 0, when the changed files span more than one module directory or exceed about 2000 changed lines (lockfiles and files under `generated/` excluded); otherwise it prints nothing. Neither guide ever makes it fail. A binary file and a rename into another module each count toward the module list. An unknown base ref fails loudly.

**L2 approval.** Given commits that each carry `Author-Agent`, and an empty newest commit carrying only `Reviewed-by-Agent`, when `loop/rules.sh trailers` runs, then it passes. It fails when the reviewer id is also an author id, when a commit that changes files carries the reviewer trailer, when a commit follows the approval, and when a commit has neither trailer.

**L3 vocabulary.** Given a public Rust item or field, TS export or `contracts/` name containing an `_Avoid:_` word from `CONTEXT.md` (also as a plural), when `loop/rules.sh vocab` runs, then it fails and names the word. `crates/agents/claude_code/` is exempt. A missing `CONTEXT.md` fails loudly.

**L4 pause.** Given Builder output with `api_error_status` 429 or "usage limit" / "rate limit" text, when `loop/boxd.sh build` runs, then it exits 75, writes `loop/out/PAUSED` and keeps its first timestamp on later runs. While the file exists no VM is created.

**L5 cleanup.** Given any exit path of `loop/boxd.sh build`, then the VM it created is destroyed, the original exit code is kept, and a failed removal is reported as a leaked VM. A failed create removes nothing. A successful run leaves a patch in `loop/out/patches/`.

**L6 secret.** Given the boxd secret `CLAUDE_CODE_OAUTH_TOKEN` is missing, when `loop/boxd.sh build` or `review` runs, then no VM is created and it exits 1. A VM only ever sees the secret's placeholder, so no token is scanned for or handled.

**L7 isolation.** Given a Builder run, then its VM is created from the `ru-toolchain` snapshot with `--isolated`.

**L8 cap.** Given `BOXD_MAX_VMS` `ru-` VMs (default 12), or a held `loop/out/lock`, when `loop/boxd.sh build` runs, then no VM is created and it exits 1. A non-numeric `BOXD_MAX_VMS` exits 2. The count includes every `ru-` VM, a suffixed one from L9 too, and `loop/boxd.sh review` is held to the same cap and lock: a review's fallback create is inside the same locked count-then-create as its first.

**L9 review.** Given a ref, when `loop/boxd.sh review <name> <prompt-file> [ref]` runs, then an isolated VM holds a git checkout whose tag `base` is the merge-base with `origin/main` and whose HEAD is the ref: the ref's own commits are replayed on `base` with their authors, messages and trailers, including a commit with no changes, and no synthetic commit is added; when the range from the merge-base to the ref contains a merge commit, a series cannot carry it, so the VM instead replays the range's non-merge commits and stands in one further commit for the merge's resolution (its trailers come from the range, see L22); the Reviewer's answer is written to `loop/out/verdicts/<name>.md`, and the VM is destroyed. The VM is named `ru-<name>`. When that create fails for any reason, the run creates `ru-<name>-r<pid>` (the run's pid) instead; only a failed second create exits 1, so a name freed or taken between the two never decides the outcome. The `-r<digits>` ending cannot be mistaken for a swarm VM (`ru-builder-<n>`, `ru-reviewer-<n>`) or an L15 check VM (`ru-chk-<slug>-<pid>`). A run removes only a VM its own successful create made (L5), on every exit path: one whose plain create failed never removes `ru-<name>`, and an L19 retry makes a new create under the same rule, plain name first, so a retry may own `ru-<name>` although its first attempt had the suffixed name, and then removes that one. A swarm child is suffixed like any other review. Both runs go on, each on its own VM; each writes `<name>.md` when it ends, so the file holds the answer of the run that ended last. The tests use the `boxd` stub, which refuses a name that exists, and give it a different result text per run: two parallel `review x` runs get two different VM names and both exit 0; `review x` with no clash uses exactly `ru-x`; with `ru-x` alive, `review x` exits 0 and `ru-x` is still alive with no `machine remove ru-x ` in the log; `x.md` holds the text of the run that ended last; with `ru-x` alive and the reboot failing once, removing `alive-ru-x` before the retry leaves no VM of the run alive.

**L10 input.** Given a name outside `^[a-z0-9][a-z0-9-]*$`, a prompt file starting with `-`, or a ref starting with `-`, when `build` or `review` runs, then it exits 2 before creating a VM or a file. So does a name ending in `-r<digits>`, which L9's suffixed VM names use; the test runs `review x-r5`.

**L11 reboot.** Given a VM created from the snapshot, then it is rebooted and answers `exec` before any agent or check runs on it.

**L12 swarm.** Given N prompt files, when `loop/boxd.sh swarm <build|review> <prompt-file>...` runs, then every prompt file is validated before any VM is made, each agent gets its own isolated VM named `ru-builder-<n>` or `ru-reviewer-<n>` (a review child whose create fell back, L9, is `ru-reviewer-<n>-r<pid>`), no more than `BOXD_MAX_VMS` VMs exist at once, one `ok` or `failed rc=<n> (see <log>)` line is printed per VM, naming the VM that run actually used, and it exits 1 if any failed. On SIGINT or SIGTERM it removes its VMs, stops its agents and exits 130.

**L13 status.** Given `ru-` VMs, when `loop/boxd.sh status` runs, then it prints one line per VM with `agent-running`, `idle` or `unreachable`.

**L14 kill.** Given `loop/boxd.sh kill <name>`, then `ru-<name>` and every `ru-<name>-r<digits>` (L9's suffixed VM) are removed and no other; given `kill all`, then every VM named exactly `ru-builder-<n>` or `ru-reviewer-<n>` (what `swarm` creates, including another swarm's), each with or without a `-r<digits>` ending, is removed and no other; a hand-run review named `reviewer` is `ru-reviewer` or `ru-reviewer-r<pid>` and `kill all` leaves it. A failed removal prints `FAILED <vm>` and exits 1. The test lists `ru-x`, `ru-x-r123`, `ru-x-2`, `ru-xy`, `ru-reviewer`, `ru-reviewer-r9`, `ru-reviewer-2` and `ru-reviewer-2-r8`: `kill x` removes the first two and no other; `kill all` removes only the last one and `ru-reviewer-2`.

**L15 check.** Given a PR number or a branch name, when `loop/boxd.sh check` runs, then it fetches `origin/main` and that ref, merges them in the object store on this machine, uploads that merged tree (tag `base` is `origin/main`) to a fresh `--isolated` VM with an auto-destroy timer (no GitHub login; nothing is cloned or fetched on the VM; no Claude secret is needed), runs `just check` there from the lockfile, shows the last 25 lines with GitHub token shapes masked, destroys the VM and exits with the check's exit code. A ref with shell syntax or a leading dash fails with exit 2, and a ref that conflicts with `origin/main` fails with exit 1 naming the ref and the conflicting file, both before any VM exists. The VM's auto-destroy timer is 4200 s, longer than the reboot wait (at most 60 attempts of 5 s plus 1 s, 360 s), the upload, an agent run of at most 1800 s, `just check` at most 1800 s and the patch step. At `BOXD_MAX_VMS` `ru-` VMs it creates none. `loop/boxd.sh bake` runs on an isolated VM, warms the dependency build from the lockfile, cleans every workspace member from that warm target (no artifact may name the bake checkout or be reused by mtime), and refuses to save a snapshot when that holds or when its scan finds a GitHub or Anthropic token.

**L16 empty approval.** Given a ref whose series contains an empty commit (such as the empty `review: approve` commit), when `loop/boxd.sh review <name> <prompt-file> <ref>` runs, then the VM's checkout contains that commit too (a commit with the same subject is HEAD, tag `base` is still the merge-base) and the review does not fail on that commit.

**L17 run logs.** Given two runs of `loop/boxd.sh build` or `review` with the same `<name>`, then each keeps its own log files under `loop/out/runs`, named `<name>-<UTC yyyymmddThhmmssZ>-<pid>` plus an extension, so a relaunch never overwrites a failed run's log; the patch and verdict keep their stable names `<name>.patch` and `<name>.md`; `check <ref>` names its VM `ru-chk-<slug>-<pid>` (the L15 name plus the run's pid, the one part of the log suffix a VM name can carry, since VM names are lowercase), so two parallel checks of the same ref never collide on a VM name.

**L18 slot wait.** Given `BOXD_SLOT_WAIT=<s>` (default 0, so a single run does not wait; a non-numeric value exits 2 like `BOXD_MAX_VMS` in L8), when `BOXD_MAX_VMS` `ru-` VMs exist, including VMs that are not this run's, then the run re-checks every second for up to `<s>` seconds and creates its VM as soon as a slot frees; if none frees it exits 1 with a message naming `BOXD_MAX_VMS` and creates nothing. `swarm` gives its children a wait of `BOXD_SLOT_WAIT` seconds (default 900), so an outside VM cannot make the last child fail at create.

**L19 retry and events.** Given a run whose VM never answers after its reboot (at most `BOXD_REBOOT_ATTEMPTS` of 5 s plus 1 s, default 60), or whose upload fails within `BOXD_RETRY_WITHIN` seconds (default 30) of the VM answering after its reboot, then the VM is destroyed and the run is retried once on a fresh VM before any agent has started, printing `retrying once`; a second failure exits 1 with `giving up after one retry`; a later upload failure is not retried; nothing is retried once the agent has run. Each retry, an agent run with no output, and an agent or check run whose boxd exec error reports `DeadlineExceeded` (boxd's no-output deadline) are appended to `loop/out/events.log` as `<UTC time> <VM> <phase> <event>`; an agent run with no output and a `DeadlineExceeded` run are recorded and never retried.

**L20 swarm ref per prompt.** Given `loop/boxd.sh swarm review <prompt-file>[@<ref>]...`, then each prompt is reviewed at its own ref, a prompt without `@<ref>` uses `BOXD_REF` (default HEAD) so existing invocations stay valid, an existing file whose name contains `@` is a plain prompt file, and a ref that is not a commit is refused with exit 2 before any VM exists.

**L22 review keeps the branch's trailers.** Given a ref whose range from the merge-base contains a merge commit, when `loop/boxd.sh review` builds the VM's checkout, then `loop/rules.sh trailers base` run on the VM gives the same exit code and the same findings as it does on the real branch. No trailer is invented: every `Author-Agent` and `Reviewed-by-Agent` on the VM's commits is copied from a real commit of the range, and the newest commit is still the approval commit when the real branch ends in one.

**L40 the boxd check does not depend on files outside the checkout.** Given a workspace package whose sources use Node types (`process`, `node:fs`) and whose own dependencies do not include `@types/node`, and a directory above the checkout that holds `node_modules/@types/node`, when `loop/boxd.sh check` runs on that tree, then it fails: its exit code is non-zero and the saved log holds the `tsc` error naming the package's file. The same tree with `@types/node` declared in that package passes. The case is real: on 2026-10-02 the `ru-tsc-gate` Builder ran `tsc --listFiles` on a boxd VM and it listed `/node_modules/@types/node` (v26.2.0), outside the checkout (fix PR #142). The tests use the `boxd` stub, which runs the VM's command in a copy of a two-package fixture workspace placed below a directory holding a planted `node_modules/@types/node`: the undeclared package fails with exit non-zero and the error in the saved log, and the declared one passes; the assertions read the saved log, never the shown last 25 lines (L15).

**L28 a stall is detected and owned.** Given any of: (a) the newest run of a required check on `main` has failed, or one required check has failed on every open PR; (b) an approved PR has been open for 20 minutes with no merge; (c) a PR has had three rejects; (d) a file in `loop/out/verdicts/` that holds the full head SHA of an open PR was written 5 minutes ago or more and that PR has no comment holding that SHA and a line starting `VERDICT:`; (e) fewer than the smaller of 8 and `BOXD_MAX_VMS` `ru-` VMs exist while an open PR has no verdict, when `loop/stalls.sh check` runs, then for each condition that holds it writes `loop/out/stalls/<kind>-<subject>` (`<kind>` is `a` to `e`, `<subject>` the PR number, `main`, or `all-prs` for a required check that has failed on every open PR, which needs at least one open PR) holding `since`, `owner` and `deadline`, and exits 1 listing them. The owner is one named role per kind: `Triage` for (a), `Merger` for (b), `Architect` for (c), where the file also holds `except`, the PR author's id, and an Architect with that id is not the owner, `Driver` for (d) and (e). The deadline is `since` plus 30 minutes. A second run leaves an existing file's `since` unchanged; a file whose condition no longer holds is deleted; with no condition holding it prints nothing and exits 0. `gh` or `boxd` failing, or not answering within `BOXD_GH_TIMEOUT` seconds (default 20), exits 4 naming the tool and writes nothing, never a false green. The tests use a fake `gh` and `boxd` with fixed runs, PRs, comments and VM lists, one case per kind and one with every condition false.

**L29 a stall is reported once.** Given stall files written by L28, when `loop/stalls.sh report` runs, then it prints one line per file that it has not printed before, `<kind> <subject> owner <owner> due <UTC time>`, and a second run prints nothing; a stall whose file was removed and then written again is printed again. The tests run `report` twice on the same files, then remove one file, write it again and run it a third time.

**L30 a stall's resolution records its tradeoff.** Given a stall file written by L28, when `loop/stalls.sh resolve <kind>-<subject> --fast <text> --proper <text> --cost <text> --pick fast|proper [--bypass <gate> --user-word <text>]` runs, then the file holds `fast`, `proper`, `cost` (what the fast option costs) and `picked`, and the file is moved to `loop/out/stalls/resolved/<kind>-<subject>-<since>` with those fields added, so L28 no longer lists it; if the condition still holds at the next `check`, a new file with a new `since` is written, and L29 reports it. Each of `--fast`, `--proper`, `--cost` and `--pick` is required, and a missing one, or a `--pick` other than `fast` or `proper`, exits 2 and leaves the file unchanged. A `--bypass` names a gate that is skipped (an admin merge, a skipped check) and needs `--user-word`, the user's own words authorising it, which the file then holds; `--bypass` without it exits 2 and changes nothing. The tests run `resolve` with a complete set of options, with each option missing in turn, with a bad `--pick`, with `--bypass` once without and once with `--user-word`, and with the condition still true afterwards.

**L31 an agent worktree commits with its Author-Agent trailer.** Given `loop/worktree.sh add <agent-id> <path> <branch> [<ref>]`, then it creates the worktree on `<branch>` (from `<ref>`, default `origin/main`) and every commit made in it carries `Author-Agent: <agent-id>`, whatever the commit message says, except as stated below for `Reviewed-by-Agent`: a message with no trailer gets it, a message that already has `Author-Agent: <agent-id>` keeps exactly one, a message with another id keeps that one and gains this id, and `--amend`, `-F`, `--no-verify` and `git cherry-pick` do the same. A message that carries `Reviewed-by-Agent` is left unchanged, because L2's approval commit carries only that trailer. A commit made in the main checkout or in another worktree is untouched. The setup writes `extensions.worktreeConfig` to the repository's shared config, and that changes nothing for the main checkout or for another worktree. An `<agent-id>` outside `^[a-z0-9][a-z0-9-]*$`, a `<path>` that exists, a `<branch>` that exists, or a `<ref>` that is not a commit exits 2 before anything is created. The tests create two worktrees with different ids in a temporary repository and commit in each with `-m` and no trailer, with the trailer already there, with another id, with `--amend`, `-F`, `--no-verify` and a cherry-pick, and with a `Reviewed-by-Agent` message (unchanged), then in the main checkout, and read `git log --format='%(trailers:key=Author-Agent,valueonly)'`.

**L33 a merge targets main.** Given a PR number, when `loop/rules.sh base <pr>` runs, then it exits 0 when the PR's base ref is `main`, and exits 1 printing `base is <ref>, not main` on stderr when it is any other ref, so a PR stacked on another PR's branch is never merged into that branch by mistake. A `<pr>` that is missing or not all digits exits 2 printing usage, before `gh` runs, so it never falls back to the current branch's PR. If `gh` fails, or runs longer than `BOXD_GH_TIMEOUT` seconds (default 20), it exits 4 naming `gh`, never 0. The tests put a fake `gh` first on `PATH` that reports base `main`, base `architect/x`, a failure and a hang (with `BOXD_GH_TIMEOUT=1`), and assert the exit code and the stderr line for each, plus a call with no `<pr>` and with `12a`.
