# Loop tooling

**L1 size.** Given a PR, when `loop/rules.sh size` runs, then it prints an advisory on stderr, and still exits 0, when the changed files span more than one module directory or exceed about 2000 changed lines (lockfiles and files under `generated/` excluded); otherwise it prints nothing. Neither guide ever makes it fail. A binary file and a rename into another module each count toward the module list. An unknown base ref fails loudly.

**L2 approval.** Given commits that each carry `Author-Agent`, and an empty newest commit carrying only `Reviewed-by-Agent`, when `loop/rules.sh trailers` runs, then it passes. It fails when the reviewer id is also an author id, when a commit that changes files carries the reviewer trailer, when a commit follows the approval, and when a commit has neither trailer.

**L3 vocabulary.** Given a public Rust item or field, TS export or `contracts/` name containing an `_Avoid:_` word from `CONTEXT.md` (also as a plural), when `loop/rules.sh vocab` runs, then it fails and names the word. `crates/agents/claude_code/` is exempt. A missing `CONTEXT.md` fails loudly.

**L4 pause.** Given a run whose final `result` event reports `api_error_status` 429 or an error whose text says "usage limit" or "rate limit", when `loop/boxd.sh build` or `review` runs, then it exits 75, writes `loop/out/PAUSED` and keeps its first timestamp on later runs. While the file exists no VM is created. Only that final event is read, so the words "usage limit" or "rate limit" quoted in an Agent's or a Reviewer's text never pause anything; a stream that ends with no `result` event is not a pause: with no event at all it is L19's no-output case, and with events it is L21's ended-without-result case.

**L5 cleanup.** Given any exit path of `loop/boxd.sh build`, then the VM it created is destroyed, the original exit code is kept, and a failed removal is reported as a leaked VM. A failed create removes nothing. A successful run leaves a patch in `loop/out/patches/`.

**L6 secret.** Given the boxd secret `CLAUDE_CODE_OAUTH_TOKEN` is missing, when `loop/boxd.sh build` or `review` runs, then no VM is created and it exits 1. A VM only ever sees the secret's placeholder, so the secret's token is never scanned for or handled (L23 scans a VM tool's files, which is a different thing).

**L7 isolation.** Given a Builder run, then its VM is created from the `ru-toolchain` snapshot with `--isolated`.

**L8 cap.** Given `BOXD_MAX_VMS` `ru-` VMs (default 12), or a held `loop/out/lock`, when `loop/boxd.sh build` runs, then no VM is created and it exits 1. A non-numeric `BOXD_MAX_VMS` exits 2. The count includes every `ru-` VM, a suffixed one from L9 too, and `loop/boxd.sh review` is held to the same cap and lock: a review's fallback create is inside the same locked count-then-create as its first.

**L9 review.** Given a ref, when `loop/boxd.sh review <name> <prompt-file> [ref]` runs, then an isolated VM holds a git checkout whose tag `base` is the merge-base with `origin/main` and whose HEAD is the ref: the ref's own commits are replayed on `base` with their authors, messages and trailers, including a commit with no changes, and no synthetic commit is added; when the range from the merge-base to the ref contains a merge commit, a series cannot carry it, so the VM instead replays the range's non-merge commits and stands in one further commit for the merge's resolution (its trailers come from the range, see L22); the Reviewer's answer is written to `loop/out/verdicts/<name>.md`, and the VM is destroyed. The VM is named `ru-<name>`. When that create fails for any reason, the run creates `ru-<name>-r<pid>` (the run's pid) instead; only a failed second create exits 1, so a name freed or taken between the two never decides the outcome. The `-r<digits>` ending cannot be mistaken for a swarm VM (`ru-builder-<n>`, `ru-reviewer-<n>`) or an L15 check VM (`ru-chk-<slug>-<pid>`). A run removes only a VM its own successful create made (L5), on every exit path: one whose plain create failed never removes `ru-<name>`, and an L19 retry makes a new create under the same rule, plain name first, so a retry may own `ru-<name>` although its first attempt had the suffixed name, and then removes that one. A swarm child is suffixed like any other review. Both runs go on, each on its own VM; each writes `<name>.md` when it ends, so the file holds the answer of the run that ended last. The tests use the `boxd` stub, which refuses a name that exists, and give it a different result text per run: two parallel `review x` runs get two different VM names and both exit 0; `review x` with no clash uses exactly `ru-x`; with `ru-x` alive, `review x` exits 0 and `ru-x` is still alive with no `machine remove ru-x ` in the log; `x.md` holds the text of the run that ended last; with `ru-x` alive and the reboot failing once, removing `alive-ru-x` before the retry leaves no VM of the run alive.

**L10 input.** Given a name outside `^[a-z0-9][a-z0-9-]*$`, a prompt file starting with `-`, or a ref starting with `-`, when `build` or `review` runs, then it exits 2 before creating a VM or a file. So does a name ending in `-r<digits>`, which L9's suffixed VM names use; the test runs `review x-r5`.

**L11 reboot.** Given a VM created from the snapshot, then it is rebooted and answers `exec` before any agent or check runs on it.

**L12 swarm.** Given N prompt files, when `loop/boxd.sh swarm <build|review> <prompt-file>...` runs, then every prompt file is validated before any VM is made, each agent gets its own isolated VM named `ru-builder-<n>` or `ru-reviewer-<n>` (a review child whose create fell back, L9, is `ru-reviewer-<n>-r<pid>`), no more than `BOXD_MAX_VMS` VMs exist at once, one `ok` or `failed rc=<n> (see <log>)` line is printed per VM, naming the VM that run actually used, and it exits 1 if any failed. On SIGINT or SIGTERM it removes its VMs, stops its agents and exits 130.

**L13 status.** Given `ru-` VMs, when `loop/boxd.sh status` runs, then it prints one line per VM with `agent-running`, `idle` or `unreachable`.

**L14 kill.** Given `loop/boxd.sh kill <name>`, then `ru-<name>` and every `ru-<name>-r<digits>` (L9's suffixed VM) are removed and no other; given `kill all`, then every VM named exactly `ru-builder-<n>` or `ru-reviewer-<n>` (what `swarm` creates, including another swarm's), each with or without a `-r<digits>` ending, is removed and no other; a hand-run review named `reviewer` is `ru-reviewer` or `ru-reviewer-r<pid>` and `kill all` leaves it. A failed removal prints `FAILED <vm>` and exits 1. The test lists `ru-x`, `ru-x-r123`, `ru-x-2`, `ru-xy`, `ru-reviewer`, `ru-reviewer-r9`, `ru-reviewer-2` and `ru-reviewer-2-r8`: `kill x` removes the first two and no other; `kill all` removes only the last one and `ru-reviewer-2`.

**L15 check.** Given a PR number or a branch name, when `loop/boxd.sh check` runs, then it fetches `origin/main` and that ref, merges them in the object store on this machine, uploads that merged tree (tag `base` is `origin/main`) to a fresh `--isolated` VM with an auto-destroy timer (no GitHub login; nothing is cloned or fetched on the VM; no Claude secret is needed), runs `just check` there from the lockfile, shows the last 25 lines with GitHub token shapes masked, destroys the VM and exits with the check's exit code. A ref with shell syntax or a leading dash fails with exit 2, and a ref that conflicts with `origin/main` fails with exit 1 naming the ref and the conflicting file, both before any VM exists. The VM's auto-destroy timer is 4200 s, longer than the reboot wait (at most 60 attempts of 5 s plus 1 s, 360 s), the upload, an agent run of at most 1800 s, `just check` at most 1800 s and the patch step. At `BOXD_MAX_VMS` `ru-` VMs it creates none. `loop/boxd.sh bake` runs on an isolated VM, warms the dependency build from the lockfile, cleans every workspace member from that warm target (no artifact may name the bake checkout or be reused by mtime), and refuses to save a snapshot when that holds or when its scan finds a GitHub or Anthropic token.

**L16 empty approval.** Given a ref whose series contains an empty commit (such as the empty `review: approve` commit), when `loop/boxd.sh review <name> <prompt-file> <ref>` runs, then the VM's checkout contains that commit too (a commit with the same subject is HEAD, tag `base` is still the merge-base) and the review does not fail on that commit.

**L17 run logs.** Given two runs of `loop/boxd.sh build` or `review` with the same `<name>`, then each keeps its own log files under `loop/out/runs`, named `<name>-<UTC yyyymmddThhmmssZ>-<pid>` plus an extension, so a relaunch never overwrites a failed run's log; the patch and verdict keep their stable names `<name>.patch` and `<name>.md`; `check <ref>` names its VM `ru-chk-<slug>-<pid>` (the L15 name plus the run's pid, the one part of the log suffix a VM name can carry, since VM names are lowercase), so two parallel checks of the same ref never collide on a VM name.

**L18 slot wait.** Given `BOXD_SLOT_WAIT=<s>` (default 0, so a single run does not wait; a non-numeric value exits 2 like `BOXD_MAX_VMS` in L8), when `BOXD_MAX_VMS` `ru-` VMs exist, including VMs that are not this run's, then the run re-checks every second for up to `<s>` seconds and creates its VM as soon as a slot frees; if none frees it exits 1 with a message naming `BOXD_MAX_VMS` and creates nothing. `swarm` gives its children a wait of `BOXD_SLOT_WAIT` seconds (default 900), so an outside VM cannot make the last child fail at create.

**L19 retry and events.** Given a run whose VM never answers after its reboot (at most `BOXD_REBOOT_ATTEMPTS` of 5 s plus 1 s, default 60), or whose upload fails within `BOXD_RETRY_WITHIN` seconds (default 30) of the VM answering after its reboot, then the VM is destroyed and the run is retried once on a fresh VM before any agent has started, printing `retrying once`; a second failure exits 1 with `giving up after one retry`; a later upload failure is not retried; nothing is retried once the agent has run. Each retry, an agent run with no output (no event in the event stream, L21, for the whole run), and an agent or check run whose boxd exec error reports `DeadlineExceeded` (boxd's no-output deadline) are appended to `loop/out/events.log` as `<UTC time> <VM> <phase> <event>`; an agent run with no output and a `DeadlineExceeded` run are recorded and never retried.

**L20 swarm ref per prompt.** Given `loop/boxd.sh swarm review <prompt-file>[@<ref>]...`, then each prompt is reviewed at its own ref, a prompt without `@<ref>` uses `BOXD_REF` (default HEAD) so existing invocations stay valid, an existing file whose name contains `@` is a plain prompt file, and a ref that is not a commit is refused with exit 2 before any VM exists.

**L21 streamed agent run.** Given `loop/boxd.sh build` or `review`, or a `swarm` child, then each event the agent produces is written to the run's event stream, `loop/out/runs/<run>.jsonl` (L17's run name), as it happens, so a run that is producing events is never silent. The verdict, the cost line and L4's pause come from the last event of the stream, which must be a `result` event; an event after a `result` event means the run ended without a result, as below. A run that has produced no event at all is L19's no-output case, and L21 adds nothing to it; in the tests it ends when the `boxd` stub reports `DeadlineExceeded` after 5 s. A run that has produced at least one event and ends before `BOXD_AGENT_TIMEOUT` with no final `result` event exits 1 with `agent ended without a result` naming its event stream; it is treated as a timed-out run is below (no check, a build's diff so far as `.partial.patch`, no verdict, an earlier result file removed), and L4 reads no pause from it. A run that has produced at least one event and is still running at `BOXD_AGENT_TIMEOUT` (default 1800 s) exits 1 with `agent timed out after <s> s` naming its event stream; it does not run the check; a build saves the VM's diff so far as `loop/out/patches/<name>.partial.patch`; a review writes no verdict. A timed-out run removes the `<name>.patch` or `verdicts/<name>.md` an earlier run left, and a later successful build removes `<name>.partial.patch`, so a result file is always from the latest run. The tests use a fake `claude` inside the `boxd` stub and `BOXD_AGENT_TIMEOUT=3`: one that emits an event every second (the first event is in the event stream while the stub still runs, and the run ends with the timeout message and a `.partial.patch`); one whose successful `result` text quotes "usage limit" and "rate limit" (exit 0, no pause, the verdict saved); one whose `result` reports `api_error_status` 429 (exit 75 and `PAUSED`); one whose `result` event reports 429 and is followed by one more event (exit 1 with `agent ended without a result`, no pause); one whose error `result` quotes "usage limit" without a 429 status (exit 75 and `PAUSED`, as L4 says); two runs of the same build name, a timed-out one after a successful one (the `<name>.patch` is removed) and a successful one after a timed-out one (the `.partial.patch` is removed), and the same for a review's `verdicts/<name>.md`; one that emits events and exits with no `result` event (exit 1 with `agent ended without a result`, no pause, a `.partial.patch`); and one that hangs with no event and a stub that reports `DeadlineExceeded` after 5 s (L19's no-output outcome, and no timeout message).

**L22 review keeps the branch's trailers.** Given a ref whose range from the merge-base contains a merge commit, when `loop/boxd.sh review` builds the VM's checkout, then `loop/rules.sh trailers base` run on the VM gives the same exit code and the same findings as it does on the real branch. No trailer is invented: every `Author-Agent` and `Reviewed-by-Agent` on the VM's commits is copied from a real commit of the range, and the newest commit is still the approval commit when the real branch ends in one.

**L23 VM tools.** Given `loop/boxd.sh build`, `review` or a `swarm` child, when the agent starts on a VM, then the VM tools uploaded for it are exactly the entries that `loop/vm-tools.json` (the tool list) names for its role, `builder` for `build` and `reviewer` for `review`, and no file from the laptop's home directory is uploaded for it except what L9 and L15 already upload (the repository archive and the prompt file). Each entry names its source and a pinned commit or version. An entry without a pin, a role other than those two, or a tool list that cannot be read exits 2 before any VM exists, and when that and L6's missing secret both apply the tool list's exit 2 wins, because a usage error is reported before an environment one (as L8 does), and `swarm` checks the tool list before it creates its first VM. An entry's files are placed outside the checkout, so they never appear in a build's patch, or in a review's checkout tree or its `git status` (L9). Every entry's files are scanned for a token shape, meaning a string that matches `TOKEN_PATTERN` in `loop/boxd.sh` (`gho_`, `ghp_`, `github_pat_` or `sk-ant-` followed by 20 or more token characters), and a hit refuses the upload with exit 1 naming the entry; log masking is L15's and is not changed here. The scan covers an entry's files only: it does not scan the repository archive, and the Claude secret is L6's. No byte of a credential used to obtain an entry is uploaded. The run appends `<UTC time> <VM> tools <name>@<pin>` to `loop/out/events.log` for each entry, and when a Claude Code hook (a command Claude Code runs on an event) exits non-zero or cannot run (its file is missing or not executable), `<UTC time> <VM> hook <name> failed: <reason>`; a failed hook is recorded and never skipped silently; in the tests the `boxd` stub runs the fixture hook when the fake `claude` starts. What the `ru-toolchain` snapshot already carries is not claimed here: the Builder's report states it from a real VM. The tests use the `boxd` stub and local fixtures: the uploaded entries for each role and none outside them; a `HOME` that holds a planted skill uploads none of it; an unpinned entry, an unknown role and an unreadable tool list exit 2 with no VM, and for `swarm` before its first VM; a source that needs a planted fake credential is obtained and the credential's bytes appear in no uploaded file; an entry file holding a token shape is refused; no entry file appears in the patch or in `git status`; each entry has its `tools` line; and a fixture hook that exits non-zero, one whose file is missing and one that is not executable each have their `hook … failed` line. Which entries each role lists is recorded in the tool list, not in this scenario.

**L25 design critic run.** Needs L21 (the event stream) on main. Given a PR whose newest commit is a `Reviewed-by-Agent` approval (L2) and a `design-critic` prompt, when `loop/boxd.sh critic <pr> <prompt-file>` runs, then it follows L4, L6, L8, L10 (`<pr>` is digits) and L11 and keeps L17's run log as `review` does, `<pr>` is resolved to its head with `gh` on the laptop, and one isolated VM named `ru-critic-<pr>`, made from the `ru-toolchain` snapshot as L7 says, holds the PR's own commits replayed on `base` as L9 does for a ref; the prompt runs there as the agent. A `<pr>` that is not digits, or a prompt file starting with `-`, exits 2 before any VM or file exists. A PR with no approval exits 2 with `not approved` and makes no VM; that is checked first, so a PR with no approval and no id prints only `not approved`. An approved PR whose title, body and commit subjects name no `U<digits>` exits 2 with `no scenario id`. Those ids are the scenarios the run covers. The run succeeds when `artifacts/ux/<id>/report.md` exists for each id and its first line is `CRITIC: pass` or `CRITIC: fail`, and when every image the report embeds, as `![...](<name>)`, is a `.png` file name with no `/` in it that is a regular file beside it (a symlink or a directory is not). Other text, including a cited path such as `docs/motion.md` or a link that is not an image, is not checked. A report that embeds any other file, a first line that is neither verdict, a missing image, or no report exits 1 naming the id. Only each `report.md` and its named images come back, to `loop/out/critic/<pr>/<id>/`; any other file stays on the VM, and nothing is written under `loop/out/patches/` or `loop/out/verdicts/`. The command never changes the PR and never posts a review: the VM is isolated, so it holds no GitHub credential and `github-app` is not available there (`docs/boxd.md`). The VM is destroyed as in L5. That the critic's exit code gates nothing, and the Merger does not wait for it, is policy of the loop, not something these tests observe. What the prompt checks, and the Todos it files from failures, belong to `.agents/design-critic.md`, not to this scenario; the tests below observe only what the command does with the prompt's output. The tests use the `boxd` stub and fake `claude`: a report with an image, which also cites `docs/motion.md` in prose, with exit 0 and the files in `loop/out/critic/<pr>/<id>/` and nothing else; the stub log shows the reboot and an `exec` answered before the agent runs, a run log under `loop/out/runs`, the PR's head resolved by a fake `gh` call, and the PR's commits replayed on `base` (a fake `git` shows the replay); two ids give two folders; a report naming a missing image, one embedding `../x.patch`, one embedding `a/b.png`, one embedding a symlink `a.png`, one whose first line is `hello`, and one run that writes nothing each exit 1 naming the id; extra files the agent wrote do not come back; a PR with no approval, an approved PR naming no id, a `<pr>` of `x1` and a prompt file `-p` each exit 2 with no VM and no file under `loop/out/`, the first printing only `not approved`; the stub log shows `--isolated`, the `ru-toolchain` snapshot and the name `ru-critic-<pr>`, and one removal; `BOXD_MAX_VMS` VMs or a missing secret stop it as for `review`, and a rate or usage limit pauses it as L4 says; a fake `gh` and `git` record no post and no push, and the PR's head is unchanged.

**L40 the boxd check does not depend on files outside the checkout.** Given a workspace package whose sources use Node types (`process`, `node:fs`) and whose own dependencies do not include `@types/node`, and a directory above the checkout that holds `node_modules/@types/node`, when `loop/boxd.sh check` runs on that tree, then it fails: its exit code is non-zero and the saved log holds the `tsc` error naming the package's file. The same tree with `@types/node` declared in that package passes. The case is real: on 2026-10-02 the `ru-tsc-gate` Builder ran `tsc --listFiles` on a boxd VM and it listed `/node_modules/@types/node` (v26.2.0), outside the checkout (fix PR #142). The tests use the `boxd` stub, which runs the VM's command in a copy of a two-package fixture workspace placed below a directory holding a planted `node_modules/@types/node`: the undeclared package fails with exit non-zero and the error in the saved log, and the declared one passes; the assertions read the saved log, never the shown last 25 lines (L15).

**L28 a stall is detected and owned.** Given any of: (a) the newest run of a required check on `main` has failed, or one required check has failed on every open PR; (b) an approved PR has been open for 20 minutes with no merge; (c) a PR has had three rejects; (d) a file in `loop/out/verdicts/` that holds the full head SHA of an open PR was written 5 minutes ago or more and that PR has no comment holding that SHA and a line starting `VERDICT:`; (e) fewer than the smaller of 8 and `BOXD_MAX_VMS` `ru-` VMs exist while an open PR has no verdict, when `loop/stalls.sh check` runs, then for each condition that holds it writes `loop/out/stalls/<kind>-<subject>` (`<kind>` is `a` to `e`, `<subject>` the PR number, `main`, or `all-prs` for a required check that has failed on every open PR, which needs at least one open PR) holding `since`, `owner` and `deadline`, and exits 1 listing them. The owner is one named role per kind: `Triage` for (a), `Merger` for (b), `Architect` for (c), where the file also holds `except`, the PR author's id, and an Architect with that id is not the owner, `Driver` for (d) and (e). The deadline is `since` plus 30 minutes. A second run leaves an existing file's `since` unchanged; a file whose condition no longer holds is deleted; with no condition holding it prints nothing and exits 0. `gh` or `boxd` failing, or not answering within `BOXD_GH_TIMEOUT` seconds (default 20), exits 4 naming the tool and writes nothing, never a false green. The tests use a fake `gh` and `boxd` with fixed runs, PRs, comments and VM lists, one case per kind and one with every condition false.

**L29 a stall is reported once.** Given stall files written by L28, when `loop/stalls.sh report` runs, then it prints one line per file that it has not printed before, `<kind> <subject> owner <owner> due <UTC time>`, and a second run prints nothing; a stall whose file was removed and then written again is printed again. The tests run `report` twice on the same files, then remove one file, write it again and run it a third time.

**L30 a stall's resolution records its tradeoff.** Given a stall file written by L28, when `loop/stalls.sh resolve <kind>-<subject> --fast <text> --proper <text> --cost <text> --pick fast|proper [--bypass <gate> --user-word <text>]` runs, then the file holds `fast`, `proper`, `cost` (what the fast option costs) and `picked`, and the file is moved to `loop/out/stalls/resolved/<kind>-<subject>-<since>` with those fields added, so L28 no longer lists it; if the condition still holds at the next `check`, a new file with a new `since` is written, and L29 reports it. Each of `--fast`, `--proper`, `--cost` and `--pick` is required, and a missing one, or a `--pick` other than `fast` or `proper`, exits 2 and leaves the file unchanged. A `--bypass` names a gate that is skipped (an admin merge, a skipped check) and needs `--user-word`, the user's own words authorising it, which the file then holds; `--bypass` without it exits 2 and changes nothing. The tests run `resolve` with a complete set of options, with each option missing in turn, with a bad `--pick`, with `--bypass` once without and once with `--user-word`, and with the condition still true afterwards.

**L31 an agent worktree commits with its Author-Agent trailer.** Given `loop/worktree.sh add <agent-id> <path> <branch> [<ref>]`, then it creates the worktree on `<branch>` (from `<ref>`, default `origin/main`) and every commit made in it carries `Author-Agent: <agent-id>`, whatever the commit message says, except as stated below for `Reviewed-by-Agent`: a message with no trailer gets it, a message that already has `Author-Agent: <agent-id>` keeps exactly one, a message with another id keeps that one and gains this id, and `--amend`, `-F`, `--no-verify` and `git cherry-pick` do the same. A message that carries `Reviewed-by-Agent` is left unchanged, because L2's approval commit carries only that trailer. A commit made in the main checkout or in another worktree is untouched. The setup writes `extensions.worktreeConfig` to the repository's shared config, and that changes nothing for the main checkout or for another worktree. An `<agent-id>` outside `^[a-z0-9][a-z0-9-]*$`, a `<path>` that exists, a `<branch>` that exists, or a `<ref>` that is not a commit exits 2 before anything is created. The tests create two worktrees with different ids in a temporary repository and commit in each with `-m` and no trailer, with the trailer already there, with another id, with `--amend`, `-F`, `--no-verify` and a cherry-pick, and with a `Reviewed-by-Agent` message (unchanged), then in the main checkout, and read `git log --format='%(trailers:key=Author-Agent,valueonly)'`.

**L32 an approval survives a merge of main that changes nothing the PR changes.** Given a PR whose newest non-merge commit is an approval (L2) and whose later commits are only merges of `origin/main`, when `loop/rules.sh approval-stands <ref>` runs, then it exits 0 and prints `approval stands: <full sha of the approval commit>` when every file the PR changes against `origin/main` is a document (under `scenarios/`, `docs/`, `.agents/` or `.work/`, or `CONTEXT.md`, `README.md` or `AGENTS.md`) and each of those files has the same content at `<ref>` as at the approval commit. It exits 1 naming the first reason otherwise: `not a document: <file>` for a changed file outside those paths, `changed since approval: <file>` for a file whose content differs (a conflict resolved inside it, or a merge that changed it), `no approval` when the newest non-merge commit is not an approval, `not a merge of main: <sha>` for a later commit that is not a merge of `origin/main`. A ref or a base that does not resolve exits 2. The tests use a temporary repository: a PR approved and then merged with a main that changed other files passes; the same with main changing a file the PR also changes, with a conflict resolved in a PR file, with a changed `.rs` file in the PR, with a commit after the approval that is not a merge, and with no approval each exit 1 with that reason.

**L33 a merge targets main.** Given a PR number, when `loop/rules.sh base <pr>` runs, then it exits 0 when the PR's base ref is `main`, and exits 1 printing `base is <ref>, not main` on stderr when it is any other ref, so a PR stacked on another PR's branch is never merged into that branch by mistake. A `<pr>` that is missing or not all digits exits 2 printing usage, before `gh` runs, so it never falls back to the current branch's PR. If `gh` fails, or runs longer than `BOXD_GH_TIMEOUT` seconds (default 20), it exits 4 naming `gh`, never 0. The tests put a fake `gh` first on `PATH` that reports base `main`, base `architect/x`, a failure and a hang (with `BOXD_GH_TIMEOUT=1`), and assert the exit code and the stderr line for each, plus a call with no `<pr>` and with `12a`.

**L41 tokens.** Given `apps/desktop/src`, when `loop/rules.sh tokens` runs, then it fails and prints `file:line` for each colour literal (`#rgb`, `#rrggbb`, `rgb(`, `rgba(`, `hsl(`, `hsla(`), each `font-size`, `border-radius`, `box-shadow`, `transition-duration` and `animation-duration` value, and each inline `style` attribute or `style={…}` in a `.tsx` file, found anywhere but `apps/desktop/src/tokens.css`. A value of `0`, `inherit`, `transparent`, `currentColor`, `none` or `var(…)` passes, and so does a line in a comment. A missing `tokens.css` fails loudly. It exits 0 when nothing is found. The tests build a throwaway repo with one offence of each kind, and a clean one. They sit in `loop/rules.test.sh`, and `.github/workflows/loop.yml` runs the check. This is U130's literal scan, in CI and without a browser.

**L42 delta.** Given two directories of `<step>.checks.json` files (a step is the file's path under its directory, without the suffix, so `U5/open` names `U5/open.checks.json`), each a map from a check id (`D1` to `D10`) to `{"status": "pass" | "fail", "value": …, "selector": …}`, when `loop/rules.sh delta <base-dir> <head-dir>` runs, then it prints one line per step and check, `<step> <id> fixed | regressed | still-failing | still-passing`, ordered by step then id, and exits 1 when any line is `regressed`. It exits 2, naming the file and the id, when a step has a file on only one side, a check id is missing from one side, or a `status` is neither `pass` nor `fail`; it never reads a missing check as a pass. Run twice on the same input it prints the same lines. The Design critic runs it and pastes its lines unchanged; it judges nothing the script already decided (`docs/design-system.md`, "Baseline protocol").

**L43 squad ranges hold only unused ids.** Given `docs/squads.md` whose table column `New ids it allocates` lists ranges written `<letter><n> to <letter><m>`, separated by commas, each list optionally ending in a parenthetical, and `.work/queue.md`'s id table, the one table in the file whose header row has the cells `Ids` and `Holder` (leading spaces before a row's first `|` are allowed; the file's other tables have other headers and are not read), whose first cell is a comma-separated list of ids and ranges, a range written `<id>–<id>` with an en dash or `<id> to <id>`, a hyphen-minus being no range, when `loop/rules.sh ranges [<base-ref>]` runs (default `origin/main`), then it parses every range in both files to `(letter, start, end)` and for every id in every squad range it prints `<id> is used in <file>` to stderr and exits 1 when that id is a scenario heading (`**<id> ` at the start of a line in a file under `scenarios/`) or lies in a range or equals an id in the first cell of a row of the queue's id table, except a queue range equal to that squad range after parsing (`A20 to A29` in the squads file is the same range as `A20–A29` in the queue). It reads the files at `<base-ref>` and not the working tree, ignores the parenthetical, prints one line per id ordered by id, and exits 0 with no output when no id is used. It exits 2 naming the line or the file for: a range whose two letters differ or whose end is below its start; a first cell it cannot parse; a `docs/squads.md` with no such column; a `docs/squads.md` or `.work/queue.md` missing at `<base-ref>`; and a `<base-ref>` git does not know (a failed read is never an empty file, so it never reads as clean). Run twice on the same input it prints the same lines. The tests build a temporary repository: a range of unused ids exits 0 with no output; a range containing a heading id exits 1 and names the id and its file; one containing a single id and one containing an id inside a range cell of a queue row each exit 1; a squad range equal to a queue range written with an en dash is not a hit, and a queue range that only overlaps it is; an id named only in the parenthetical is not read; a backwards range, mixed letters, a hyphen-minus range and a missing column each exit 2; a queue file with no `Ids`/`Holder` table, or with two, exits 2 naming the file, and the temporary repository's queue holds exactly one such table beside one table with other headers that holds an id and is not read; a missing `docs/squads.md` and an unknown `<base-ref>` each exit 2 naming it; and a second run prints the same lines. A squad that uses ids shrinks its range in the same PR, which is what this check enforces.

**L44 a PR has a class.** Given a PR number, when `loop/rules.sh class <pr>` runs, then it prints `post` and exits 0 only when every file the PR changes (a rename counts both paths) is one of: a file under `docs/` other than `docs/development-loop.md` and `docs/boxd.md`; `.work/queue.md`; a `scenarios/*.md` file other than `loop.md`, `daemon.md`, `rpc.md`, `control.md` and `agents.md`, none of whose added lines matches the content screen. The screen is the case-insensitive regex `secret|token|credential|password|oauth|identity|impersonat|\bcard|daemon|\bloop\b|Author-Agent|Reviewed-by`. In every other case it prints `block` and exits 0, and `block` is the answer whenever the class is uncertain: a file in no list above, a file that is binary or too large to diff, an empty diff, or a screen match. `gh` failing or not answering within `BOXD_GH_TIMEOUT` seconds (default 20) exits 4 naming `gh`, never `post`. The tests put a fake `gh` first on `PATH` that returns changed files and patches, one case per path above, one scenario file with each screen word added, one rename out of `docs/` into `crates/`, a binary file, an empty diff and a failure.

**L45 a round cap is enforced.** Given a PR number, when `loop/rules.sh rounds <pr>` runs, then it counts the PR's comments whose first line starts `VERDICT: reject` and exits 0 printing the count when it is below 4, and exits 1 printing `round cap: <n> rejects, an Architect must pick split, amend or retire` when it is 4 or more and no comment by an Architect, posted after the newest reject, starts `ARCHITECT: split`, `ARCHITECT: amend` or `ARCHITECT: retire`. The count restarts at zero from such a comment. `gh` failing exits 4 naming `gh`. The tests use a fake `gh` with 3 rejects, 4 rejects, 4 rejects then an `ARCHITECT: split` comment, and that comment followed by 4 more rejects.

**L46 a PR is ready to merge by class.** Given a PR number, when `loop/rules.sh merge-ready <pr>` runs, then it exits 0 only when `rounds` (L45) exits 0, `base` (L33) exits 0 and the required checks on the PR's head have passed, and in addition: for class `block` (L44) `trailers` (rule 1) passes, so the approval commit is the newest; for class `post` every non-merge commit carries `Author-Agent` and no approval is needed. Otherwise it exits 1 naming each failing condition, and a failing `gh` exits 4. The tests use a fake `gh` and a temporary repository with a `post` PR and a `block` PR, each with all conditions true and then with each one false in turn, including a `block` PR with no approval commit, which fails, and a `post` PR with no approval commit, which passes.

**L47 a post-merge review is owed within 60 minutes.** Given a merged PR of class `post` (judged on its files at merge) whose merge was 60 minutes ago or more and that has no comment starting `VERDICT:` and holding the PR's full head SHA, when `loop/stalls.sh check` runs, then it writes `loop/out/stalls/f-<pr>` as L28 does for its kinds, with owner `Driver`, and the file is deleted once such a comment exists. The check covers the 50 newest merged PRs. Its owner assigns an independent Reviewer, as step 5 of `docs/development-loop.md` says. The tests use a fake `gh` with a `post` PR merged 59 minutes ago, 61 minutes ago, and 61 minutes ago with a verdict comment, and a `block` PR merged 61 minutes ago with none, which writes nothing.

**L48 an unfixed defect on a merged PR is reverted, not fixed forward.** Given a merged PR of class `post` whose newest verdict comment starts `VERDICT: reject` and was posted 60 minutes ago or more after the merge, and no PR merged after it has a body line `Fixes #<pr>`, when `loop/rules.sh revert-due` runs, then it prints `revert <pr>` for it and exits 1; with none due it prints nothing and exits 0; `gh` failing exits 4 naming `gh`. A verdict that starts `VERDICT: approve` never makes a PR due, whatever notes it carries. The tests use a fake `gh` with a reject at 59 minutes, a reject at 61 minutes, a reject at 61 minutes with a later PR whose body says `Fixes #<pr>`, an approve with a long notes section at 61 minutes, and a `block` PR with a reject, which is not listed because its approval blocked the merge.

**L49 a scenario is not dispatched before its approval.** Given a scenario id (`[A-Z][0-9]+`), when `loop/rules.sh dispatch <id>` runs, then it finds the newest merged PR that changed the line starting `**<id> ` in `scenarios/`, and exits 0 when that PR is of class `block` or has a comment starting `VERDICT: approve` and holding its head SHA, and exits 1 printing `no approval for <id> at <sha>` otherwise; an id with no such line exits 2 naming the id. `loop/boxd.sh build` runs it for each id on a `Scenarios:` line of its prompt file, and exits 2 before creating a VM when one fails. The tests use a fake `gh` and a temporary repository with an id merged in a `block` PR, a `post` PR with an approve comment, a `post` PR with none, a `post` PR whose approve names an older head, and an id that does not exist, and assert that `build` creates no VM in the failing cases.
