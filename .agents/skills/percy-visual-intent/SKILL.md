# Percy Visual Intent

Writes a `## Percy Visual Intent` section into the PR description (or `.percy/intent-<branch>.md` if no PR exists). This is the ground-truth signal `/percy:review` uses to decide whether each Percy diff is an *expected* change or a real issue.

## Operating principle: propose, don't ask

The agent **drafts the intent automatically** from the current session — never stalls waiting for the user to type intent from scratch. The user's role is to *review and edit*, not author. Step 1 (Gather intent) reads conversation context + git diff + PR body to draft a complete first version; Step 4 (Confirm) presents that draft for review with edit-or-accept as the default UX.

Only ask the one-line clarification — "What did you mean to change visually in this PR?" — when conversation context AND the git diff AND the PR body are **all** empty (nothing at all to draft from). If any of the three has substance (e.g. the skill was invoked cold but the diff is right there), draft from the diff + PR body per "propose, don't ask" — a rough draft the user edits beats a question.

## When to run

- Right after the agent finishes a UI change.
- On `git commit` or before `gh pr create`.
- When updating an existing PR with new commits, refresh the section.

## Steps

### 1. Gather intent

Pull from these sources, in order of priority:
1. **Current conversation context** — what the user asked for, what the agent committed to changing. This is the primary signal.
2. **Git diff** — `git diff origin/main...HEAD --stat` for the file list, then `git diff origin/main...HEAD` on UI files (`*.tsx`, `*.jsx`, `*.vue`, `*.svelte`, `*.css`, `*.scss`, `*.html`) — **to ground the DETAILS of what the conversation says (exact colors, selectors, routes), never to expand the intent's scope.**

   > **Scope rule — intent is what was MEANT, not what the diff contains.** If the diff includes a change nobody asked for or mentioned in the session, do **NOT** add it to "Intended visual changes" — and don't interrogate the user about it either. Leaving it out is the design: `/percy:review` exists precisely to catch out-of-intent changes (`unplanned-change` / `likely-bug`). An intent doc that absorbs every diff hunk would launder unintended changes — including bugs — into "intended" and blind the review. (Exception: the mid-stream **backfill** case, where no session context exists at all — there the diff is the only source and the draft carries lower fidelity by nature.)
3. **PR description (existing)** — if a PR is already open, parse its description for non-visual context.

### 2. Build the section

Produce a section in this exact shape. Be specific — generic prose makes the review skill less effective.

```markdown
## Percy Visual Intent

**Intended visual changes:**
- `<route or component>`: <what changes visually, in 1 line>
- ...

**Unchanged (should not diff):**
- `<route or component>`: <why this should still match baseline>
- ...

**Reviewer notes:**
- <edge cases the reviewer should know about: hover states, responsive widths, dark mode, animation timing, etc.>

<!-- percy-visual-intent: generated by percy-visual-testing plugin · do not edit between markers -->
```

Rules for content:
- Routes: use real paths (`/checkout`, `/settings/profile`). Components: real names (`<Button variant="primary">`).
- "Intended visual changes" must be one bullet per affected surface. No vague entries like "Updated UI".
- "Unchanged" lists routes/components the agent did *not* touch but that share files or styles with what changed — these are where Percy is most likely to flag unplanned-change.
- Reviewer notes: only include if there's something genuinely subtle.

### 3. Inject into PR

If a PR exists for the current branch (check via `gh pr view --json url,body`):
1. Fetch the existing PR body.
2. If a `## Percy Visual Intent` section bracketed by the marker comments already exists, **replace it in place** (do not duplicate).
3. If not, append the new section at the end of the body.
4. Update the PR: `gh pr edit <num> --body-file -` (via temp file).

If no PR exists yet, don't demand a second invocation later — offer to do it in one pass:
1. Ask: "No PR yet — want me to `gh pr create` now and inject the intent in one pass? (y/n)"
2. **yes** → draft the PR title/body from the branch's commits, include the intent section in the body, `gh pr create --body-file -` (via temp file), then continue to Step 5 (auto-watch) as if the PR had existed.
3. **no** → write the section to `.percy/intent-<branch>.md` and print: "Saved intent to `.percy/intent-<branch>.md` — run this skill again after `gh pr create` to inject it into the PR description."

### 4. Present for review (proposal-first UX)

Show the user the drafted Intent section and ask **one** question:

```
I've drafted this Visual Intent from our session:

<rendered intent section>

Accept and inject into PR? (yes / edit / regenerate)
```

- **yes** → inject the section as-is (Step 3) and proceed to Step 5.
- **edit** → user provides line-by-line edits; agent updates the draft; ask again.
- **regenerate** → agent re-drafts from scratch (maybe pulling more aggressively from git diff if the first draft over-relied on conversation context).

Do NOT push the section without explicit yes. Do NOT ask the user to type the intent themselves — always draft first, even if it's a rough first version.

### 5. Auto-watch by default

After the intent is injected into a PR, **start `/percy:watch` automatically** — don't make the user opt in. This is the frictionless default: open PR → intent written → watcher armed → gate fires itself when the Percy build lands. Announce it in one line (visible + cancellable) instead of asking:

> Intent written to [PR #<n>](<pr_url>). 👀 Watching the Percy build for this branch — I'll run the gate automatically when it finishes. (Say "stop watching" to cancel.)

- Invoke `/percy:watch` via the Skill tool, passing the current branch / PR number. The watcher tracks **only the Percy check/build** — it never waits on or blocks the repo's other CI checks (see `/percy:watch` Path B) — and auto-invokes `/percy:gate` on completion. The user keeps working.
- Only fall back to *asking* when backgrounding isn't available in the host IDE (an inline watch would block the session — that deserves consent).

Skip the watch if no PR exists yet (Step 3's "no PR" branch). The watcher needs a real build to watch.

## Important

- This section is **machine-read** by `/percy:review`. Keep formatting consistent.
- Do not include screenshots or links to Figma here — the section is for *what should change*, not *how it looks*.
- Refresh the section every time the agent makes a UI commit, not just on PR creation. The `<!-- percy-visual-intent: ... -->` marker comments make in-place replacement safe.
