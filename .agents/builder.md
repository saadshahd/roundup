# Builder (Codex or Claude Code)

Read `AGENTS.md`, `CONTEXT.md` and the scenario you were given. Nothing else defines the work.

1. Work in your own git worktree, on one branch, in one module directory where you can (a guide, not a limit).
2. Write the failing test first, then the code. Run `just check` before you open the PR.
3. Aim for about 2000 changed lines or fewer; a bigger PR is allowed and never fails, the Reviewer notes it. Every commit you make needs the trailer `Author-Agent: <your id>`. (When the Driver runs you in a boxd VM it stamps `Author-Agent: builder` on uncommitted work; you may also commit yourself.)
4. A UI change: read `docs/design-system.md` first. A colour, size, radius, shadow or duration is a Token, never a literal. Write `Moves: D<n>, …` in the PR body. Run `just harness` on the seeds your scenario names and read `window.__checks()` (U137) before you push. Your prompt lists no screens beyond your scenario's; the Design critic runs others.
5. Do not review your own PR and do not edit `.github/`, `contracts/` or `AGENTS.md` unless the scenario says so.
6. Before you push, run `git diff origin/main --stat` after any merge of main: only your own files may appear. Run the loop tests with an empty `HOME` and no git identity, as CI does, so a missing tool or identity fails here and not in CI.
7. Write the PR body in two sections (L53): `## Shape`, the shortest view that makes the change clear (a call tree, a component tree, a file tree, a mermaid sequence or a diff, at most 40 lines, in the `show-me` style), and `## Proof`: the test output for the scenario's tests, and for a change the user can see, before and after screenshots or a short video at the scenario's window size. Save them under `artifacts/ux/<scenario>/` in the `--isolated` VM that ran your head; copy them out with `boxd machine cp` and the Driver (or a normal VM that holds only the files) pushes them to `proof/pr-<n>` and links them. Only a normal VM that ran no unreviewed code pushes by itself.
8. Label the PR when you open it (L57): one `kind:` label, at least one `area:` label and one `lane:` label that matches `loop/rules.sh class <pr>`, for example `gh pr create --label kind:docs --label area:loop --label lane:block`. Add `flag:needs-user` for an `AGENTS.md` or repository-setting edit.
9. Before review, compare each scenario claim with the behavior the surrounding code currently supports. If they conflict, amend the scenario and queue the missing behavior before claiming the PR satisfies it. For a visible change, inspect computed margin, padding and font size against D2, text contrast against D5 and control hit area against D6 at the scenario's viewport; exercise failure text on the densest named seed and measure that it remains visible beside pinned controls. Attach proof captured from the exact code head. For bounded state, exercise the largest accepted input and run the named memory gate. Review the diff for deleted tests that still cover live behavior. Put the measured results in `## Proof` so the Reviewer can check them without reconstructing your setup.
