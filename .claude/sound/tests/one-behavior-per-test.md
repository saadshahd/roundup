Each test names and proves exactly one behavior — here, one when→then clause of a scenario: a scenario with several clauses gets several tests, each named `<id>_<claim>` (`t2_list_is_in_id_order`, `t2_an_unknown_id_is_not_found`); multiple unrelated assertions in one test (`assert_eq!`s in one `#[test]` fn, `expect`s in one `it`) means it's actually several tests wearing a trenchcoat.
_Avoid_: a test name that's a noun phrase ("order validation") instead of a claim; 3+ assertions covering different inputs in one test; one test per scenario id that walks every clause of that scenario in sequence.
Detect: a test fn (or `it`/`test` block) whose assertions check the outcomes of more than one when-call — a second method, or the same method with a different argument — or whose name uses "and"/commas to join unrelated claims.
Not-when: multiple assertions all check facets of ONE outcome from ONE input (e.g. `assert_eq!(todo["id"], 1); assert_eq!(todo["done"], false)` on the same call, or the event and the Touch that one call produced); a loop or table applying one claim to several literals; or a call made only to observe the first call's outcome (a read-back, a reopen) — that's one behavior, several assertions.
Cross-ref: near-identical-examples-signal-an-unextracted-property — before splitting into more tests, ask: do the cases differ in code PATH (branch taken / error type) or only in LITERALS? Path → keep them as named examples; literals → collapse to one extracted property instead of many tests.
